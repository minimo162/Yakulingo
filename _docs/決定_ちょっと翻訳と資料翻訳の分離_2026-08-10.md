# YakuLingo: 「ちょっと翻訳」と「資料翻訳」の分離

決定日: 2026-08-10
対象: V91.61 以降
位置づけ: 本実装の基準。過去のUI案と矛盾する場合は本文書を優先する。

## 1. 結論

~~YakuLingo は、一つの起動ファイルから開く大きな開始画面で用途を選び、その先を二つの
利用者向けアプリ画面に分ける。~~

**2026-08-11 に利用者判断で取り消した。**「画面を一つにするのでokです」。

分けた結果、同じ「訳す」ことが二つのアプリに見え、`ちょっと翻訳`は単位換算・
用語集・保存の有無で `資料翻訳` の劣化版に見えていた。いまは**画面は一つ**で、
その中に**三つの状態**を持つ。

- `選ぶ`: 何から始めるかを選ぶ
- `その場で訳す`: 短い文章を英訳または和訳する。一時利用で保存しない
- `1文ずつ確認する`: Word、Excel、長文を英訳または和訳し、文単位で確認して資料を作る

状態の境界（保存しない・用語集を使わない・過去訳を引かない）は §3.2 のまま変えない。
変わったのは器であって契約ではない。`/quick` は「その場で訳す」状態として残し、
Ctrl+Alt+J・開始画面・チュートリアルの経路を壊さない。

Windows Explorer上の小さな起動ファイルを二つ並べて選ばせない。起動ファイルは従来どおり
一つだけとし、読みやすい説明を持つ開始画面で選択させる。選択後は別アプリとして見せるが、方向判定、数値保護、Copilot送信、数値QC、
プロンプトは一つのPowerShell基盤を共有する。同じ処理を複製しない。

初期実装ではC#を追加しない。将来の小型C#画面は、今回作るJSON APIを呼ぶ薄い
クライアントとして追加できる。~~clipboard常時監視、自動送信、疑似Ctrl+Cは実装しない。~~

**2026-08-11 に利用者判断で一部を変更した。**

- **clipboard 常時監視**: 引き続き実装しない。読むのは Ctrl+Alt+J を押した直後の一度だけ
- **自動送信**: 引き続き実装しない。読み込んだ文章を見せ、Enter を押して初めて送る
- **疑似 Ctrl+C**: **実装する。** ただし Office 以外に限る

理由。Ctrl+Alt+J を「押すだけで訳せる」ものにするには、選択中の文章を自動で
取得する必要がある。2026-08-11 に実測した結果は次のとおり。

| 対象 | UI Automation | Office COM |
| --- | --- | --- |
| Word | TextPattern を1つも公開しない（深さ9まで探索して0個） | 取得できる |
| Excel | 同上 | 取得できる（シート名・番地・セル値） |
| ブラウザ | TextPattern はあるが本文の選択は取れなかった | 無い |

つまり全アプリを1つの仕組みで賄う方法は無い。Office は COM で確実に取れるので
そちらを使い、ブラウザ・Teams など COM を持たないものは疑似 Ctrl+C で取る。

クリップボードが置き換わる点は、利用者判断で受け入れる（2026-08-11、
「普通の人はクリップボードが置き換わることなんて別に気にしないと思う」）。
復元は試みない。Excel 由来の遅延描画形式は原理的に復元できず、
「復元したつもりで壊れている」ほうが悪いため。

守る条件は次のとおり。

- Office（Word・Excel・Outlook・PowerPoint）には疑似 Ctrl+C を使わない。COM で読む
- `GetClipboardSequenceNumber` が変化しなければ中止する。選択が無いときに
  前の中身を送る事故を、原理的に起こさない
- 待ち時間に上限を置く。応答しないアプリでアプリ全体を止めない

## 2. 共通して守る境界

- 公表／非公表、内部／外部、文書種別を利用者に分類させない。
- 数値をマスキングし、保護済み最終promptの検証に成功した場合だけCopilotへ送信する。
- 社名、人名、文章はマスキング対象にしない。この事実を画面に明記する。
- 英訳／和訳は高確度なら自動決定し、曖昧なときだけ利用者に二択を求める。
- 方向が未確定の入力はCopilotへ送らず、CAT projectも作らない。
- 方向、数値・単位・符号、保護記号のQCをQuickとCATで共有する。
- 「完成版」「公表可能」「承認済み」「会社の表現に適合」と断定しない。
- Copilot jobはserver全体で一件だけ実行する。同時要求はqueueせず明示的に止める。

## 3. ちょっと翻訳

### 3.1 用途と画面

メール、Web、会議中の数文などをすぐ訳す。通常画面に方向ラジオを置かない。

- 日本語: `英語の訳案を作る`
- 外国語: `日本語の訳案を作る`
- 曖昧: `どちらに訳しますか？` と英語／日本語の二択

入力を変更したら明示方向を解除し、再判定する。過去の選択を次回へ持ち越さない。

### 3.2 状態と保存

入力、訳文、履歴、artifactをdiskへ保存しない。server process内の一時artifactだけを
最大30分保持し、server再起動で消す。ログ、URL、`server.json`、job stateへ原文・訳文を
書かない。画面を閉じた後の復元機能を持たない。

結果は一つの訳案として表示し、`未確認`を明記する。コピーに失敗しても全文を画面に残す。

Quickでは、過去の翻訳例、翻訳メモリ、コーパスを検索も参照もしない。何を根拠に影響を
受けたか説明できない翻訳を避けるため、過去例をpromptへ入れず、選択肢にも設けない。

### 3.3 資料翻訳への移行

利用者が`資料翻訳で1文ずつ確認する`を押したときだけ、一時artifact IDとrevisionで
CAT projectを作る。clientから原文・訳文を再送しない。

- 文数一致: 訳案を各segmentへ`AI訳・未確認`として配置する。
- 文数不一致: 原文だけを分割し、訳案全文を参照欄へ残す。
- reviewed、QC済み、承認、出力可の状態を継承しない。
- 同じartifactの二重昇格は同じprojectを返す。
- project保存に失敗した場合、artifactを残して再試行できる。

## 4. 資料翻訳

### 4.1 用途

英訳と和訳のどちらも「資料作成」である。日→英を主な利用実態としても、データモデル、
保存、QC、再開、DRAFT出力は`to_en`へ固定しない。

入口は次の三つを主とする。

- Word・Excelを取り込む
- 長い文章を貼り付ける
- 前回の作業を続ける

前回版の利用と過去の日英資料の取込は`そのほかの始め方`へ置く。

### 4.2 project

project作成前に方向を確定し、作成後は変更しない。resumeでは保存済み方向を使う。
すべての変更はexpected revision付きtransactionで保存する。

各segmentは少なくとも次を持つ。

- 原文、訳文
- origin（AI、手直し、用語集、過去訳など）
- `未翻訳／AI訳・未確認／手直し済み・未確認／確認済み／再確認が必要`
- 原文hash、訳文hash、QC contract version、findings

`確認済み`は「この作業で利用者が確認した」ことだけを意味し、社内承認や公表承認を
意味しない。

### 4.3 出力

文章は確認済み訳文をコピーする。Word・Excelは確認用DRAFTを作る。

出力条件:

- 全segmentに訳文がある
- 全segmentが現在の原文・訳文に対して確認済み
- 未保存編集がない
- 現行QCが通っている
- ファイルの対応構造が検証済み

~~ファイル名、文書内、出力前後の画面に`DRAFT／完成版ではない／社外配布不可`を表示する。~~

**2026-08-12 に利用者判断で言い方と回数を変えた。**

> いちいち言われなくても、そのまま社外に送るひとなんていないです。
> 社内確認用のファイルというのもよくわからないです。

- ファイル名の `DRAFT_` と文書内の `DRAFT` の帯は、これまでどおり付ける
- 画面では**出力の前に1回だけ**言う。「原本はそのままで、訳文を入れたコピーを
  作ります。名前の先頭に「DRAFT_」が付きます。」
- 出したあとは、できたファイル名を1行出すだけにする（同じ注意を2度出していた）
- `社内確認用` という呼び方をやめる。何のファイルか伝わっていなかった
- 社外配布を戒める文は出さない。守るのは「完成版に見せないこと」であって、
  利用者の分別を疑うことではない

## 5. 過去訳

利用者へ見せる区分は二つだけとする。

1. `自分が確認した訳`
   - CATで利用者が確認し、project保存とQCが成功した訳。
   - 新しいprojectへ候補として置いても未確認から始める。
2. `過去の翻訳例`
   - 取り込んだ日英資料、前回版、既存の対訳。
   - CATでだけ参考表示し、自動採用・自動確認・Copilot promptへの自動投入をしない。
   - 資料名、ページ、日英原文、一致した語または原文一致度を表示する。
   - 利用者が明示的に挿入したときだけsegmentへ反映し、どの例を挿入したかを記録する。
   - 挿入後に編集した場合も、`翻訳例から挿入後に編集`と追跡できる。

公表／内部／文書種別／会社標準を入力させず、断定もしない。保持する付随情報は、取得
できる場合の出典名・ページと、このアプリ内で確認されたかどうかだけとする。現行UIの`公表訳`、
`公表訳100%`、`会社が公表した言い方`は`過去の翻訳例`へ変更する。

## 6. 実行構成

一つのcmdが同じserverを起動する。serverが無ければ起動し、存在すれば増やさず開始画面を
開く。

- `/`: 説明付きの大きな二択を持つ開始画面。行き先は同じ一つの画面で、選ぶのは始め方
- `/quick`: 一つの画面を「その場で訳す」状態で開く
- `/cat`: 一つの画面を「選ぶ」状態、または `?project=` で「1文ずつ確認する」状態で開く

~~QuickとCATはDOM、画面状態、local storage keyを共有しない。~~
**2026-08-11 に変更。** 同じ DOM に三つの状態が同居する。分けるのは DOM ではなく状態で、
同時にはひとつしか出さない。連携は引き続き一時artifact昇格APIだけで行い、
ブラウザーから本文を送り返す経路は作らない。共通JavaScriptはsession付きHTTP、
エラー整形、job進捗などに限定する。

同一buildのserverが起動済みなら、起動ファイルはそのserverの開始画面を開く。build不一致や
active job中に、別processを強制停止してはならない。

## 7. 初期API

- `POST /api/quick/jobs`: 方向解決後にQuick jobを開始
- `GET /api/quick/artifacts/{id}`: 一時結果を取得
- `POST /api/cat/promote`: artifactを未確認CAT projectへ昇格
- 既存CAT API: 初期実装では互換維持し、順次JSON commandへ整理

job開始時にはowner UI、方向、source fingerprintを固定する。CAT jobはproject ID、revision、
各sourceをapply時に再検証する。

## 8. UIとアクセシビリティ

- `Quick`、`CAT`、classification、revision、QC等の内部語を表示しない。
- 本文17px以上、訳文18px以上、主要操作44px以上。
- `文字を大きく`は両アプリで同じ利用者設定を使ってよい。
- 320px幅、200%表示で横scrollなし。
- 主操作は各画面一つ。詳細、候補、削除は折りたたむ。
- エラー後に原文、訳文、現在行を失わない。
- 曖昧方向、QC失敗、確認成功後は次に必要な場所へfocusする。

## 9. 今回の実装範囲

順にすべて完了させる。

1. 共通方向decision、Quick artifact、promotion、単一job境界
2. 説明付き開始画面と、`/quick`・`/cat`の別画面
3. 双方向CATの保存、再開、QC、出力表示
4. 過去訳の二分類への簡素化と旧断定表示の削除
5. 旧DOM／base64 handoffと旧方向ラジオ経路の削除
6. 回帰、200%／狭幅／keyboard確認、Quick→CAT実機E2E

C#小窓、tray、global hotkey、選択text取得は将来範囲であり、今回の完了条件に含めない。

## 10. 完了条件

- 起動cmdが一つだけで、開始画面から二つの専用画面へ進め、server PID／port／active Copilot jobは一つ。
- Quickは双方向で一つの未確認訳を返し、再起動後に原文・訳文が残らない。
- 方向が曖昧な入力は明示選択までtransport 0回。
- Quick→CATで原文、表示訳、方向が一致し、未確認から始まる。
- CATはtext、Word、Excelを両方向でproject化し、resume後も方向が変わらない。
- 過去訳の通常表示が`自分が確認した訳／過去の翻訳例`だけになる。
- public/internal/文書種別/承認分類を入力させない。
- 数値が最終promptに残る、mask無効、proof不整合なら送信0回。
- 未確認、未保存、QC不一致の状態でDRAFTを出せない。
- Quick／CAT同時jobで一件だけが開始し、別projectへの結果混入がない。
- 既存Horizon 1、Word、VersionUpdate、保存故障注入、encoding、Smokeが合格する。
