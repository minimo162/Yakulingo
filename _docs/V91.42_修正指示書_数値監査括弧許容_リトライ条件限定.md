# YakuLingo V91.42 修正指示書

作成日: 2026-07-21 / ベース: V91.41

対象は「テキスト翻訳の再送多発」の恒久対応。7/21ログで同一文書に対し
attempt=1/3〜2/3 が `NUMERIC_SCALE_MISMATCH_RETRY` で連続失敗し、
毎回2回分のCopilot送信が無駄になる事象（16:24 / 16:56 / 17:13〜17:15 の3件）。

- §1: 数値監査の照合正規表現に括弧形式（▲金額）の許容を追加 — **直接原因の修正**
- §2: リトライ/矯正再送の発火条件を scaleErrors>0 に限定（text・file・cacheの3経路）
- §3: 監査WARNログへの detail 出力追加
- §4: 矯正指示文の missing/scale 分岐（"do not output \<missing\>" の解消）
- §5: FIs の FULL漏出3回目への対応 — fail-open の後処理置換1点のみ
  （検出監査等の追加機構は複雑化リスクにより不採用）

安全方針: 本指示書の全§は「翻訳経路に新たな throw を増やさない」ことを
共通原則とする。§2 は throw 条件の削減、§3 はログのみ、§4 は文言のみ、
§5 は fail-open。唯一挙動が変わる §1 も照合の**緩和**（従来マッチは全て
マッチ維持の上位互換）であり、新たに翻訳を止める経路は存在しない。

## 経緯・真因（実機確定済み）

ログの失敗3件はすべて `checked=28 matched=24 scaleErrors=0` — スケール誤りゼロの
まま4トークンの「出現回数不足」だけで再送が走っていた。実文（ユーザー提供の
最終訳文）を V91.41 実コードの dot-source 再現に掛けると FULL/BRIEF とも
**28/28 で通過**。つまり成功したのは attempt 3 で、attempt 1/2 は別表現だった。

真因は**プロンプトと監査の仕様矛盾**:

1. 原文にはマイナス金額が5件（▲111千円、▲95/▲41/▲45/▲70億円）
2. numeric_rules（PromptBuilder.ps1:566）は「▲は数値のみ括弧:
   `(72) k units, (xxx) oku`」と括弧形式を**指示**している
3. 一方 `Get-YakuTokenOccurrenceCount`（Translation.ps1:384）の照合は
   `95\s+oku` 形式のみで、指示通りの `(95) oku` は **count=0**（実機テスト確定）
4. attempt 1/2 はモデルがルールに忠実に4件を括弧形式で出力→「欠落4件」と
   誤判定→再送。attempt 3 で偶然全件が方向語吸収表現（"a loss of 95 oku"）に
   転び通過

ルール準拠の正しい出力が棄却される構造のため、▲を含む文書では再発が確実。
特に signed breakdown 形式（`tariffs (xxx) oku`）では括弧形式が必須であり、
file経路（単発矯正再送→hard fail）では**ブック全体の翻訳失敗**に直結する。

副次: `Test-YakuNumericIntegrity` の合格判定が `$ok=($mismatches.Count -eq 0)` で、
ScaleError=false の純欠落でも "SCALE_MISMATCH" を名乗る再送を発火する。
V91.36/37 の設計意図（1/10スケール系統誤りの検出）から逸脱した過剰発火。

## §1 Translation.ps1: Get-YakuTokenOccurrenceCount の括弧許容照合

関数全体を以下へ置換（数値部の前後に `\(?\s*` / `\s*\)?` を許容。
トークンを数値部と単位部に分解して組み立てる）:

```powershell
function Get-YakuTokenOccurrenceCount {
    param([AllowNull()][string]$Text,[Parameter(Mandatory=$true)][string]$Token)
    $normalized=([string]$Text).Replace('，',',').Replace('％','%')
    $numPart=$Token; $unitPart=''
    $sep=$Token.IndexOf(' ')
    if ($sep -gt 0) { $numPart=$Token.Substring(0,$sep); $unitPart=$Token.Substring($sep+1) }
    elseif ($Token.EndsWith('%')) { $numPart=$Token.Substring(0,$Token.Length-1); $unitPart='%' }
    $pattern='\(?\s*'+[regex]::Escape($numPart)+'\s*\)?'
    if ($unitPart -eq '%') { $pattern += '\s*%' }
    elseif ($unitPart -ne '') { $pattern += '\s+'+[regex]::Escape($unitPart).Replace('\ ','\s+') }
    return [regex]::Matches($normalized,$pattern,[System.Text.RegularExpressions.RegexOptions]::IgnoreCase).Count
}
```

検証済み（dot-source再現）:
- 単体14ケース全通過: `(95) oku` / `(111) k yen` / `(3) %` / `▲95 oku` /
  `2,135 oku`（カンマ）/ `120 k units`（2語単位）が count=1、
  `9.5 oku` に対する `95 oku`、`95 percent` に対する `95%` は count=0 維持
- E2E: 本件原文×attempt1想定（▲4件を括弧形式化したFULL）が 24/28→**28/28**、
  スケール誤り負例（393→39.3 oku）は **ScaleErrors=1 で引き続き検出**、
  元のFULLは 28/28 のまま

ScaleCandidate の照合も同関数経由のため `(39.3) oku` 型のスケール誤り検出も
自動的に括弧対応になる。file経路（FileTranslation.ps1:1679/1957）も共有関数の
ため §1 だけで両経路の括弧誤判定が解消する。

## §2 リトライ/矯正再送の発火条件を scaleErrors>0 に限定

§1 で本件の直接原因は消えるが、括弧以外の自然な統合（範囲の "10 to 20 oku"、
重複数値の集約等）による純欠落は今後も起こり得る。再送は「スケール誤り検出時
のみ」とし、純欠落は**警告付き受理**へ:

### §2a text経路（Translation.ps1:948付近）

`if ($numericFailures.Count -gt 0) { ... }` ブロックを次の構造へ:

```powershell
if ($numericFailures.Count -gt 0) {
    $scaleErrTotal = 0
    foreach ($f in $numericFailures) { $scaleErrTotal += [int]$f.ScaleErrors }
    $combinedAudit = [pscustomobject]@{ Mismatches=@($numericFailures.ToArray() | ForEach-Object { $_.Mismatches }) }
    $numericDetail = (@($numericFailures.ToArray() | ForEach-Object { $_.Detail }) -join '; ')
    if ($scaleErrTotal -gt 0) {
        $numericCorrectionInstruction = New-YakuNumericCorrectionInstruction -Audit $combinedAudit
        if ($attempt -lt $maxAttempts) { throw "NUMERIC_SCALE_MISMATCH_RETRY: $numericDetail" }
        throw "NUMERIC_SCALE_MISMATCH: $numericDetail"
    }
    try {
        if ($null -ne $Warnings -and (Get-Command Add-YakuWarning -ErrorAction SilentlyContinue)) {
            Add-YakuWarning -Warnings $Warnings -Category 'numeric-integrity' -Location 'FULL/BRIEF' -Details @{ Attempt=[int]$attempt; Detail=$numericDetail } -Message "原文の数値トークンの一部が訳文中に見つかりません。表現の統合による可能性がありますが、該当数値をご確認ください。($numericDetail)"
        }
    } catch {}
}
```

（純欠落時は受理して後続の placeholder/structure 検証へ進む。
`$numericCorrectionInstruction` は scale 時のみセット——従来の attempt>1
プロンプト付加ロジックは無変更で流用可）

### §2b file経路（FileTranslation.ps1:1680 / 1958 の2箇所）

`if (-not [bool]$numericAudit.Ok)` を
`if (-not [bool]$numericAudit.Ok -and [int]$numericAudit.ScaleErrors -gt 0)` へ。
純欠落時は矯正再送せず §2a と同文面の Add-YakuWarning（Category
'numeric-integrity'、Location "ID $($item.Index)"）で受理。
final 側（1958付近）も同様。

### §2c cache検証（Translation.ps1:906）

`if (-not [bool]$cachedNumeric.Ok)` を
`if (-not [bool]$cachedNumeric.Ok -and [int]$cachedNumeric.ScaleErrors -gt 0)` へ
（判定基準を §2a/§2b と統一。純欠落キャッシュの無限discard→再翻訳ループを防ぐ）。

## §4 Translation.ps1: New-YakuNumericCorrectionInstruction の文言分岐

```powershell
function New-YakuNumericCorrectionInstruction {
    param([Parameter(Mandatory=$true)]$Audit)
    $lines=@($Audit.Mismatches|ForEach-Object{
        if([bool]$_.ScaleError){"- $($_.Source): reproduce the token $($_.Expected) exactly; do not output $($_.Observed)."}
        else{"- $($_.Source): include the token $($_.Expected) exactly as written; it is currently missing from the translation."}
    })
    return ("NUMERIC CORRECTION (mandatory): Correct only the following numeric token mismatches while preserving all other wording:`n"+($lines-join "`n"))
}
```

（§2 後は scale 時しか使われないが、file経路の混在監査
（scale+missing同時）で "do not output \<missing\>" が出るのを防ぐ）

## §5 FIs の FULL漏出対応 — 最小構成の決定論的展開（fail-open）

7/21 の text 実行で FULL に "lending reviews by FIs" が露出——V91.41 §5 の
「spell out BRIEF-list abbreviations unless glossary-fixed」追加後も再発
（累計3回目）。プロンプトへの例示追加は確率的で他略語へ汎化しないため不採用。
コード側の後処理置換1点のみとする。プロンプトの既存規則は保険として残置・無変更。

**設計原則: 翻訳経路に新たな throw を一切増やさない。** 後処理は例外時に
原文をそのまま返す fail-open とし、この関数が翻訳を止めることを構造的に不可能にする。

```powershell
function Expand-YakuFullBriefAbbreviations {
    param([AllowNull()][string]$FullText)
    try {
        return [regex]::Replace([string]$FullText, '\bFIs\b', 'financial institutions')
    } catch { return [string]$FullText }
}
```

適用位置は Repair-YakuTextResponsePostParse 内（to_en・Style='full' のみ）。
置換が発生した場合のみ Write-YakuLog（INFO）を既存流儀の `try{}catch{}` 付きで。

注意:
- `\bFIs\b` は大文字小文字区別（既定）のまま——"FIS" 等の固有名詞誤ヒット防止
- 展開対象は BRIEF専用略語のみ。glossary-fixed（OP/VM/W/S/G&A/FM/VP/BEP等）は
  FULL でも正当のため対象外
- 他略語への汎化は**機構ではなく運用**で担保する: 新たな漏出はこれまで通り
  レビューで発見し（3回とも実際そうだった）、確認のつど Replace 行を1行追加。
  検出監査などの追加機構は設けない——コード量とバグ表面積の増加が
  得られる価値に見合わないため
