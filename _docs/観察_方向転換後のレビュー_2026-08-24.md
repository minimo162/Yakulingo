## 2. 実測した欠陥（P0）: 保存済みExcel作業が開けない

`/cat?project=<id>` を開くと、作業面は開くが**行が1件も出ない**。
画面の状態行（`#cat-status`）に出ている文字列を、そのまま写す。

    workspace hidden=false / picker hidden=true
    title = "sample.xlsx"
    rows  = 0
    status = "Cannot set properties of null (setting 'hidden')"

原因は1行で特定できる。`www/assets/cat.js:1163`

    Object.keys(inspectorPanels).forEach(function (name) { el('cat-panel-' + inspectorPanels[name]).hidden = name !== inspectorTab; });

`cat-panel-candidates` などの inspector パネルは #124 / #126 で `cat.html` から削除された。
`cat-panel-` という文字列は、いまリポジトリ全体でこの1か所にしか無い（動的生成もされていない）。
つまり `renderInspector()` は**呼ばれれば必ず投げる**。呼び出しは9か所あり、そのうち
`renderRows()`（`cat.js:1322`）が行の描画そのものなので、行は永久に出ない。

例外が画面に出ないのは、`resume()` の `.catch` が拾って status 行へ流しているためである。
コンソールには何も出ない。**黙って壊れている。**

これは #127 が「現行mainで確認している先行障害」として挙げた
`Cannot set properties of null (setting 'hidden')` と同じ種類で、
場所が `loadRecent()` から `renderInspector()` へ移っただけである。
#128 は「削除済みDOM参照の復旧」を謳ったが、復旧したのは最近の作業の経路だけだった。

## 7. 見えていること

今日の4回は、どれも「どちらを主役にするか」を動かした。動かしていないのは土台である。

    テキスト翻訳側   quick.html 5.9KB + quick-page.js 10.6KB + quick-page.css 7.8KB = 24KB
    Excel 側         cat.html 59KB + cat.js 435KB + cat-workspace.css 138KB
                     + premium-ui.js 64KB + premium-ui.css 120KB = 816KB

主役を入れ替える改修が安いのは、テキスト翻訳側が 24KB しか無いからである。
高いのは Excel 側の 816KB で、そこは 2026-08-22 以前の CAT 作業面のまま残っている。
#123 以降がやったのは、その作業面から**常設 DOM を削ること**だけで、
削られた DOM を触る JS は残った。§2 と §3 はその直接の結果である。

`cat.html` にはいまも配置（`cat-placement-*`）、体裁確認（`cat-preview-*`）、
publication（`cat-publication-*`）、一括収まり（`cat-fit-batch-*`）、
用語・除外（`cat-term-*`）が丸ごと残っている。一方 inspector（候補・点検・文脈・
変更履歴・作業メモ）だけが消えている。**残した基準と消した基準が一致していない。**

だから、いま決めるべき問いは「テキストと Excel のどちらが主役か」ではない。
それは #130 で決まっている。決まっていないのは **Excel 側をどこまで残すか** である。

選択肢は3つある（どれを選んでも §2 と §3 は先に片づく必要がある）。

1. **現状維持** — 2機能を並べたまま。816KB を保守し続ける。
   §3 の 79件は1件ずつ潰す。gate 13本以上を現行 DOM へ再同期する
2. **Excel を「確定対訳の再適用 + 未訳補完 + 書き出し」に絞る**（#127 §B が書いた範囲）。
   配置・体裁・publication・一括収まり・inspector を**実際にコードごと落とす**。
   落とす順は「HTML から消す → JS から消す → gate を消す」であって、
   今回のように HTML だけ先に消さない
3. **Excel から撤退** — テキスト翻訳1本にする。過去訳の資産（TM・用語集）は残す

私の見立ては 2 である。理由は測定に基づく2点だけ。
(a) いま壊れているのは inspector 経路であり、#123 以降どの issue もそれを主導線に置いていない。
つまり**誰も使う予定の無いコードのために製品全体が止まっている**。
(b) 1 を選ぶと §3 の 79件と gate 13本を、まだ方向が固まっていない画面のために保守することになる。
今日4回動いた画面である。

3 を採るなら §5 の 162KB に加えて 816KB も落ちるが、それは #127 が積んだ
「過去の日英版から対訳を作る」という設計を捨てることになる。今日の4回はどれも
そこを否定していないので、測定からは支持できない。
