## 0.【最優先】億円金額の1/10スケール誤りの修正 — numeric_rules

### 現象（実数値での初検証で発見・系統的）
実数付き文書で**全ての億円金額が1/10にスケール**された:
11,577億円→"1,157.7 oku yen"、343→34.3、122→12.2、55→5.5、238→23.8、
250→25.0、(50)→(5.0)、(400)→(40.0)、60→6.0。
千台系（659→659 k units等）・％・符号括弧は全て正常で、億円のみの誤り。
パターンから、Copilotが**billion換算（十億円）の算術を行った上で
oku yen のラベルだけ貼った**と推定される（billion禁止規則にラベルは
従い、数値計算がbillion側に引かれた）。

### 真因の構造（マスク検証の盲点）
これまでの検証例文は金額が全てxxx/XXXマスクで、「数値をそのまま写す」
挙動を一度も数値で実証できていなかった。数値規則の例示も万円換算
（575万2,000円=5,752 k yen）など**変換する例のみ**で、億円の
「無変換・逐語」を実数で示す例が無かった。

### 修正（numeric_rules の Units 行に反例1行、約25語）
```
- 億円: copy the digits verbatim - never rescale or convert to
  billions (連結売上高11,577億円 -> "11,577 oku yen",
  NOT "1,157.7 oku yen"; 122億円 -> "122 oku yen", NOT "12.2").
```
- 総語数上限は 1,290語（現行1,260＋約25語）に更新。

### 回帰テスト資材の常備（同格に重要）
本件を検出した実数付き文書（15年前・非機密化済み）を**実数回帰例文**
として検証セットに常備する。マスク例文では原理的に検証できない
「数値の逐語性」を守る唯一の砦であり、以下も同文書系で同時カバーする:
- 億円の逐語（本件）
- 万台×10のk units換算（先日の未検証事項。同文書に「xxx万台」相当の
  実数行が無ければ、旧開示から1行追加した検証用テキストを作る）
- 受入時は数値の全件突合（原文の数字列と出力の数字列の一致確認）を
  機械的に行う（目視でなくdiff推奨）

## 1.【必須】余剰タブ掃除の共通化 — 「タブ2つ」の解消

### 現象・真因
Edgeはウィンドウを閉じてもプロセス常駐し、翻訳ボタンからの再起動で
セッション復元される（targets 4件残存）。V91.21の余剰タブ掃除
（Closed surplus Copilot tab）は**warmup経路のみ**で実行されるため、
リクエスト経路からのEdge再起動（Starting Edge → 本処理続行）では
走らず、タブ2つが残存する。

### 修正
warmup側の余剰タブ掃除処理を関数として切り出し、**リクエスト経路でも
Edge起動（edgeStarted=True）を検知した直後に1回実行**する。
- 既存ガードは維持: 会話中URL（現在使用中のtargetIdと会話ルートの
  タブ）は閉じない。アイドルなCopilotタブのみclose。
- 実行タイミングは「New Edge window normalized once」の直後が自然。

## 2.【必須】凍結タブ対策 — ping evaluate＋WS再確立（attempt 1の21秒短縮）

### 現象・真因
セッション復元直後のタブはEdgeのスリープ/凍結状態にあり、CDP接続は
成立してもJS実行が応答しない。fillの Runtime.evaluate が
`CDP method receive timeout. TimeoutSeconds=21` で失敗し、attempt 1が
まるごと無駄になった（TRANSLATION_ATTEMPT_FAILED）。

### 修正
target取得直後（baseline取得の前）に**短timeoutのping evaluate**を挟む:
```powershell
# 例: 3秒timeoutで '1+1' を評価。応答が無ければ凍結とみなす
$pingOk = Invoke-YakuCdpEvaluate -Expression '1+1' -TimeoutSeconds 3 -ErrorAction SilentlyContinue
if (-not $pingOk) {
    # Page.bringToFront で凍結解除を促し、WS切断→再接続→target再取得を1回だけ実施
    # 再取得後にもう一度ping。それでも無応答なら従来どおりattempt失敗へ
}
```
- 効果: 21秒の無言タイムアウト待ちが最大3〜6秒の能動回復に短縮され、
  attempt 1が生き残る可能性が高くなる。
- リトライ回数は増やさない（3回のまま）。回復はattempt内で完結させる。

## 3.【必須】fill前の入力欄クリア — 残存テキスト競合の根絶

### 現象・真因
attempt 1でタイムアウトした fill が、タブの凍結解除後に**遅延部分実行**
され、入力欄に70字が残存。これが後続attemptの fresh-state 確認を連続で
落とし（fresh-state-not-confirmed×2→Page.navigateフォールバック）、
さらに navigate 回復後の fill 整合性検証を不一致にした。

### 修正
fill 直前に inputTextLength を確認し、**0でなければ入力欄を全選択削除
してから** insertText を実行する:
- CDPで composer にフォーカス→ Ctrl+A 相当（Input.dispatchKeyEvent）
  → Delete、または execCommand/DOM操作での全消去。実装しやすい方で可。
- クリア後に inputTextLength=0 を確認してから fill。クリアに失敗した
  場合は従来どおり整合性検証で止まる（安全側は不変）。
- 副次効果: fresh-state 確認の失敗要因が減り、navigateフォールバック
  への依存も下がる。

## 4.【必須】誤発報の分離 — INPUT_RESIDUAL_CONFLICT の新設

### 現象・真因
fill整合性不一致が一律 `PROMPT_TRUNCATED_BY_INPUT_LIMIT` で報告され、
今回の実態（残存テキストとの競合）まで「入力上限超過」とラベルされた。
本コードは塩漬け中の入力上限検知（将来Microsoftが上限を変えた時の
保険）専用に保たないと、発報時の判断を誤る。

### 修正
fill整合性検証の分岐を2つに分ける:
```
- beforeInputLength > 0、または afterInputLength > promptLength の場合
  → INPUT_RESIDUAL_CONFLICT（残存テキスト競合。§3のクリア実装後は
    原則発生しないが、クリア失敗時の受け皿として残す）
- beforeInputLength = 0 かつ afterInputLength < promptLength（正規化
  −1を除く）の場合
  → PROMPT_TRUNCATED_BY_INPUT_LIMIT（真の切詰め。従来メッセージ維持）
```
- エラーメッセージも分ける: RESIDUAL側は「入力欄に前回の残存テキストが
  ありクリアに失敗しました。Copilotの画面を一度更新して再実行して
  ください」等、利用者が自己回復できる文言に。

## 5.【任意】リトライ中のUI表示

進捗detailに「再試行中 (attempt x/3)」を表示する。今回のように内部で
回復中でも、利用者には「進まない」に見えたことへの対処。1行の
detail合成で足りる。
