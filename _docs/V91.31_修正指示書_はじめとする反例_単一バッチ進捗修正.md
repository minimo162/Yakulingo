## 2.【必須】進捗の実測ベース化 — CopilotClient.ps1

### 現状の問題（コード確認済み・ユーザー指摘通り）
応答待ち中の進捗は Wait-YakuCopilotResponse 内で
```powershell
$generationProgress = [Math]::Min(88, 42 + ($sliceCount * 4))
```
＝スライス回数（≒経過時間）だけで刻んでおり根拠がない。一方、同じ
ループで応答テキストの実長 `$approxChars` を計算済みなのに未使用。

### 修正 2-1: 応答長ベースの進捗
```powershell
# expectedChars: このバッチの期待応答文字数
#   バッチ1: batch_input_length × 既定係数（settings.copilotAnswerRatio、既定0.6）
#   バッチ2以降: 同ジョブ内の完了バッチ実測比（answerLength / batchCharCount）の平均
$charBased = if ($expectedChars -gt 0) {
    42 + [int][Math]::Floor(46.0 * [Math]::Min(1.0, $approxChars / $expectedChars))
} else { 42 }
# フォールバック: approxCharsが取れない間もバーを止めない緩い時間下限
$timeFloor = [Math]::Min(60, 42 + $sliceCount)      # 従来の1/4速
$generationProgress = [Math]::Min(88, [Math]::Max($charBased, $timeFloor))
```
- 42〜88%の区間は現行踏襲。単調性は既存のmaxクランプで担保済み。
- 実測比の同ジョブ内学習: 各バッチ完了時に
  `actualRatio = answerLength / batchCharCount` を ProgressState に蓄積し
  平均を次バッチの expectedChars に使う（ジョブを跨ぐ永続化はしない。
  文書タイプで比率が変わるため同ジョブ内学習が最も安全）。
- approxChars が最後まで0のケース（Copilot UIが完了まで本文を出さない等）
  でも timeFloor で緩やかに進み、完了時に88→92以降へ接続する。

### 修正 2-2: 単一バッチの区間写像（前版から継続）
Set-YakuCopilotProgressPhase（3493行付近）の条件を分割:
写像は `batchCurrent -ge 1 -and batchEnd -gt batchStart` で常時適用し、
「バッチ x/y」ラベル付与のみ `batchTotal -gt 1` に限定する。
これにより単一バッチでも局所進捗（2-1の実測ベース値）が全体の8〜92%
区間に正しく写像される。

### 受入
1. 単一バッチのテキスト翻訳で、応答生成中にバーが応答量に応じて
   8〜92%区間内を漸進する（時間だけで一定速に進まない／長時間の
   完全停止と末尾の大ジャンプが消える）
2. 複数バッチで、バッチごとの区間・x/yラベルが従来通り
3. approxChars が取れない場合もバーが停止しない（timeFloor動作）
4. 進捗ログ（任意）: バッチ完了時に actualRatio を1行出力し、
   既定係数0.6の妥当性を実測で確認できるようにする
