## §2 未解決の課題

### §2-1 元の問題が解けたか分からない

出発点は「**用語集が網羅的でないのに、それに依存している**」だった。
コーパス翻訳はその答えとして作ったが、**効いているかを確かめていない。**

確かめるのに要るもの:

- 英文短信を数件（いまは1件。1件では候補の絞り込みが働かない）
- 同じ原文を訳して、「参照した社内資料」に出る一節が訳文に反映されているか見る

### §2-2 用語集をプロンプトから外せるか未判断

| 用途 | 判断 |
| --- | --- |
| ファイル翻訳の `cell-exact` | **外せない。** レイアウトの保証だから（`決定_用語集は…` を参照） |
| プロンプトへ渡す GLOSSARY 節 | **未判断。** コーパスで代替できるか比べていない |

比べ方は決めてある（`use_bundled_glossary` を切って訳し比べる、1行の変更）。
実データが要るだけ。

### §2-3 FULL / BRIEF の並列化は「保証」待ち

並列にすると **FULL と BRIEF で訳語が揃う保証が消える**（いまは同じ依頼の中で
連続して書かれるので揃っている）。踏み切る条件は「訳語の統一をアプリ側で
保証できるようになること」。

- 略語 49 件は確定した（`BriefStyle.ps1`）
- **まだ全体は覆えていない。** 残っている揺れがどの語で起きているかを実機で見る必要がある

直列（A-2）は、当初考えたより得るものが小さいと分かった。
テンプレートが `FULL_TEXT:` → `BRIEF_TEXT:` の順を固定しているため、
**モデルは既に自分の FULL 出力を読んで BRIEF を書いている。**

### §2-4 はみ出しの検出そのもの

列幅とフォントから文字幅を実測する案。**この検証環境では確かめられない**
（Windows のフォント描画が要る）。ラベル一覧で運用が回るか見てから判断する。

### §2-5 プロンプトが長い

13,330 字（原文 99 字に対して 134 倍）。ただし**削減の余地は小さい**と分かった。

| 内訳 | 削れるか |
| --- | --- |
| BRIEF 規則 7,276 字 | うち実例 15 組（約 2,300 字）は**削ってはいけない**（研究が効くと示している） |
| 文脈に依る対応（technology / corporate / subsidiaries …） | 削ると壊れる |
| 文脈に依らない略語 | **削除済み**（496 字。当初 2,100 字と見積もったが外れた） |

**長い理由は辞書ではなく、規則と実例そのものだった。**
「プロンプトを短くして往復を増やす」という筋は、思ったほど取れない。

## §3 保留（理由つき）

| 事項 | 理由 |
| --- | --- |
| 段階4 どのデータベースを参照に含めるか | データベースが1つしか無いうちは選ばせる意味がない |
| 段階5 過去 ECM 資料の追加 | 技術的前提（文例の伏せ字）は満たした。**データの判断待ち**。入れば BRIEF の手本になる |
| セルごとの上限文字数の事前提示 | 効果が不確か（研究も数値予算は未検証）。外すと意味が通らない英語を招く |
| 字幕方式（上限超過で再依頼） | **却下済み。** 再依頼は時間がかかるうえ無茶な翻訳になる |
| 測定基盤（`保留_翻訳ロジック最適化…`） | 未着手 |

## §4 次にやること

**実機で段階3を動かす。** それだけで §2-1 §2-2 §2-3 の材料が同時に揃う。

1. 英文短信を数件、原本フォルダへ入れて取り込み → 配布用フォルダ → 共有へコピー
2. テキスト翻訳（JA→EN）を数本流す
3. 見るもの:
   - 「参照した社内資料」に出る一節が、訳文に反映されているか（§2-1）
   - BRIEF の略語が揃っているか（今回のアプリ側適用が効いているか）
   - **残っている訳語の揺れがどの語で起きているか**（§2-3 の材料）
   - 往復が1回増えた体感（許容できるか）

**切り分けのために、順番に見るのが安全。** まずコーパス無しで1本訳し、
次にコーパスを配ってから同じ原文を訳すと、文例の効果だけを見られる。
