# V91.61 修正指示書: 翻訳ロジック最適化 — 局所最適の抑止機構と測定基盤

作成日: 2026-08-04 / 対象: V91.60 / 段階: **0.5**
（`設計方針_翻訳アーキテクチャ見直し.md` §5 の段階0.5）

## この版の位置づけ

**翻訳の挙動を1文字も変えない。** プロンプト・用語集・翻訳経路のコードに触れない。
以降の最適化（段階1〜5）を**判定できる状態**を作ることだけを行う。

そのため退行の危険が構造的に存在せず、実機確認も「起動して1本翻訳が通る」以上を要さない。

### なぜ挙動を変える前にこれを入れるのか

段階0（評価基盤）は「測れる」状態を作ったが、「測った結果に従う」ことは強制しない。
機構が無いまま段階1へ進むと、部分最適の対象がプロンプトから評価セットへ移るだけになる。

依頼の趣旨は「辞書や細かいプロンプトによる局所最適化に陥らない」ことである。
**陥らないための規律ではなく、陥れない仕組みを先に置く。**

## §2 指標の定義

`Measure-YakuEvalResponses.ps1` が出力する指標を確定する。
**すべて機械的に算出できること。** 目視でしか判定できない指標は採用しない。

### §2-1 制約層（違反が1件でもあれば不採用）

| 指標 | 算出 | 既存資産 |
| --- | --- | --- |
| 数値・符号・単位の保全率 | `Test-YakuNumericIntegrity` | あり |
| 数値プレースホルダーの整合 | `Test-YakuNumericMaskIntegrity` | あり（V91.60） |
| 構造保全率（見出し・箇条書き） | `Test-YakuTextStructureIntegrity` | あり |
| 応答契約の充足率 | `Parse-YakuTextTranslationResponse` の成否 | あり |

### §2-2 主目的（忠実性）

| 指標 | 算出 |
| --- | --- |
| 禁止形の出現数 | `must_not_contain` の一致数（`million` / `billion` / 混在略語など） |
| 必須語の充足率 | `must_contain_any` の充足数 |

**忠実性の完全な自動判定はできない。** 事実の欠落・改変を機械的に検出する手段は無い。
本版では上記の代理指標に留め、**限界を明示する**（§8 の「測れないもの」）。

### §2-3 副目的

| 指標 | 算出 | 現状 |
| --- | --- | --- |
| **BRIEF 圧縮率** | BRIEF字数 ÷ FULL字数 | on 0.552 / off 0.750 |
| **FIXED層の略語遵守率** | 用語データが `brief` を指定した語のうち、BRIEF で実際にその表記が使われた割合 | **未実装。本版で追加**（F-6 の見落とし） |
| **用語遵守率** | 注入された用語のうち訳文で使われた割合 | 一部あり |
| **決定表の遵守率** | 決定表の各行について、入力パターンが原文にあるとき出力形が訳文にあるか | **未実装。本版で追加** |

**FIXED層の略語遵守率を最優先で入れる。**
F-6 で `Going fwd.` → `Going forward` の退行を見逃した原因はこの指標の不在である
（設計方針 §9-7）。この指標が無いままでは段階5（BRIEF作り直し）の採否を判定できない。

### §2-4 一般性条件（VDI）

| 記号 | 定義 | 現状 | 目標 |
| --- | --- | --- | --- |
| **VDI-C** | off群の圧縮率平均 − on群の圧縮率平均 | 0.198 | 0.10 以下 |
| **VDI-R** | on群の決定表遵守率 − off群の決定表遵守率 | 未測定 | 0 に近いこと |
| **VDI-F** | on群の忠実性代理指標 − off群の同指標 | 未測定 | 0 |

VDI-C だけ符号が逆（圧縮率は小さいほど良い）である点に注意する。
**出力では「一般性のギャップ」として全て正=悪い向きに揃えて表示する。**

## §3 評価セットの拡張と分割

### §3-1 拡張

現状 18件（on-glossary 4 / off-glossary 4 / 分類なし 10）。

| グループ | 現状 | 拡張後 | 分野 |
| --- | --- | --- | --- |
| on-glossary | 4 | **8** | 損益・為替数量・見通し・キャッシュフロー・販促費・変動利益・固定費・投資 |
| off-glossary | 4 | **12** | 品質・人事・IT・調達・法務・環境・安全・教育（各分野1〜2件） |
| 契約/数値/構造 | 10 | 10（据置） | — |
| **合計** | 18 | **30** | |

**対の作り方（重要）:** on と off は**観点・文長・文体・構文の複雑さを揃え、
語彙のカバレッジだけを変える。** 揃っていない対から出た差は VDI ではなく
単なる難易度差であり、指標として使えない。

各ケースに次を持たせる:

```json
{
  "id": "off-glossary-legal-1",
  "group": "off-glossary",
  "pair": "on-glossary-op",
  "split": "dev",
  "direction": "to_en",
  "source": "…",
  "focus": "…",
  "guards": ["R7"],
  "must_not_contain": [],
  "must_contain_any": []
}
```

- `pair`: 対になるケースのID。対が揃っていることを検査する。
- `split`: `dev` / `holdout`。
- `guards`: このケースが守護している規則ID（§5）。

### §3-2 分割

| セット | 割合 | 件数（目安） |
| --- | --- | --- |
| 開発（`dev`） | 60% | 18 |
| 保留（`holdout`） | 40% | 12 |

**層化する。** グループ（on/off/契約系）と分野が両方に入るようにする。
`pair` を持つケースは**対ごと同じ split へ入れる**。片方だけ保留にすると VDI が計算できない。

### §3-3 保留セットの規律

- 改良中は見ない。ツールは既定で `dev` のみを対象にする。
  保留を含めるには `-IncludeHoldout` を明示的に渡す。
- 開封は**変更を凍結してから**。開封後に手直しして再開封しない。
- 開封のたびに `app/tools/eval/holdout-log.md` へ追記する。

```markdown
| 日付 | 対象（版・変更） | 開封理由 | 結果 |
| --- | --- | --- | --- |
| 2026-08-xx | V91.62 用語データ統合 | 段階1の採否判定 | 採用 / 不採用 |
```

- 開封回数が段階数を大きく超えたら、保留になっていない（設計方針 §9-8）。

### §3-4 ノイズ床の再測定

拡張後に**同一条件のベースラインを3回**回し、次を算出して README へ記録する。

| 単位 | 算出 |
| --- | --- |
| ケース単位 | 3回の各ケースの最大差 |
| グループ平均 | 3回のグループ平均の最大差 |

**この値を採否判定の閾値に使う。** V91.59 の値（±0.14 / ±0.025）は n=4 時点のものであり、
n が増えれば床は下がる。**古い床を使い回さない。**

## §4 層の所有権の検査

### §4-1 検査内容

`app/tools/Test-YakuPromptLayers.ps1`（新規）:

1. `prompts/*.txt` から日本語文字列（2字以上の連続する仮名・漢字）を抽出する。
2. 許可リスト `app/tools/prompt-vocab-allowlist.txt` に無いものを違反とする。
3. 予算（§6）を超えたものを違反とする。

### §4-2 許可リストの形式

```
# <語> <TAB> <分類> <TAB> <理由>
となる	文法形式	R1a。モダリティの中立性。語を差し替えても形が残る
する予定だ	文法形式	R6。意図と見込みの区別
販促費	語彙	V91.61時点の既存。段階1で用語データへ移す（要移行）
```

- 分類は `文法形式` / `語彙` / `契約`。
- **`語彙` と分類したものには「要移行」を付ける。** これが段階1の作業リストになる。
- 新規追加は `文法形式` か `契約` のみ許す。**`語彙` の新規追加は違反。**

### §4-3 初期化

V91.60 時点の実測 34種を1件ずつ判定して許可リストへ入れる。
判定そのものが棚卸しであり、**この作業の出力が段階1の作業量の見積もりになる**。

| ファイル | 種類数 |
| --- | --- |
| `text_translate_to_en.txt` | 22 |
| `file_translate_to_en.txt` | 9 |
| `style_brief_rules.txt` | 2 |
| `text_translate_to_jp.txt` | 1 |

### §4-4 ラチェット

**既存分は違反にしない。増えたら止める。**
掃除は段階1（用語データ統合）で行う。本版は挙動を変えないため。

段階1で `語彙` 分類が減ったら、許可リストからも消す。**戻せないようにする。**

## §5 規則台帳とアブレーション

### §5-1 台帳

`app/tools/rules-registry.tsv`（新規）:

| 列 | 内容 |
| --- | --- |
| `id` | `R1` `R1a` `R3a` `B1`〜`B7` `Q1a` `Q1b` |
| `file` | `text_translate_to_en.txt` / `style_brief_rules.txt` |
| `layer` | `語彙` / `文法形式` / `手続き` / `契約` |
| `origin` | 由来の版と失敗（`V91.31 はじめとする反例`） |
| `guards` | 守護ケースのID（カンマ区切り、1件以上必須） |

**守護ケースの無い規則は登録できない。** 該当する規則は、まず評価セットへケースを足す。
足せない規則は「何を防いでいるか説明できない規則」であり、
**廃止候補として一覧に出す**（削除はしない。判断は §7 を通す）。

由来が追えない規則は `origin` に `不明` と書く。**不明であることを記録に残す。**

### §5-2 アブレーション

`Get-YakuPromptTemplate` に「指定した規則IDの行を落とす」機構を入れる。

- 入口は環境変数 `YAKULINGO_DISABLE_RULES`（カンマ区切りの規則ID）。
- **既定は空。何も落とさない。** 通常経路の挙動は変わらない。
- 設定画面には出さない（V91.60 の `YAKULINGO_NUMERIC_MASKING` と同じ扱い）。
- 行の特定は行頭の `R1.` `B1.` などのIDで行う。
  複数行にまたがる規則（Q1 の (a)(b)）は、次のID行までを1規則として扱う。

### §5-3 アブレーション実行

`app/tools/eval/Invoke-YakuRuleAblation.ps1`（新規）:

台帳の各規則について、その規則を外したプロンプトで守護ケースを評価し、
**規則なしでも通るものを廃止候補として一覧に出す。**

- 自動では消さない。
- 段階の区切りごとに1回まわす。
- 結果は `app/tools/eval/ablation-log.md` へ追記する。

## §7 採否判定の自動化

`Measure-YakuEvalResponses.ps1` に `-Judge` を追加し、
設計方針 §9-6 の7条件を判定して出力する。

```
=== 採否判定: V91.62 用語データ統合 ===
 1. 制約層の違反                     OK    (0件)
 2. 狙った指標の改善                 OK    (off圧縮率 0.750 -> 0.688、床 0.018)
 3. 他グループの退行                 OK    (on 0.552 -> 0.549、床 0.018)
 4. VDI                              OK    (0.198 -> 0.139)
 5. 保留セット                       未実施 -IncludeHoldout を付けて再実行
 6. 予算                             NG    (style_brief_rules.txt 7,940 > 7,800)
 7. 守護ケース                       OK    (追加規則なし)

判定: 不採用（条件6）
```

**判定は必ず出力する。人が総合判断で覆せる余地を作らない。**
覆したい場合は上限改定など**独立した判断として記録に残す**（設計方針 §9-2）。

「有望だが不採用」を正式な結論として扱う。F-6 がその実例である。

## §8 この版で測れないもの（明示する）

**測れないことを測れるふりをしない。** 以下は本版の対象外であり、限界として記録する。

| 側面 | 現状 | 扱い |
| --- | --- | --- |
| 忠実性（事実の欠落・改変） | 機械判定できない | 代理指標（禁止形・必須語・数値・構造）で近似。実機の目視を残す |
| 訳文の自然さ | 機械判定できない | 測らない。**測れないものを目標にしない** |
| 実際の Copilot の挙動 | サブエージェント代替 | 段階の区切りで実機と突き合わせる。**ハーネスの結果を実機の代用と主張しない** |
| 文書全体の一貫性 | 評価は文単位 | 段階4（FULL/BRIEF分離）で扱う |

**ハーネスと実機の乖離を測る手順を用意する。** 段階の区切りで、
評価セットから3件を実機で翻訳し、ハーネスの結果と並べて `app/tools/eval/README.md` へ記録する。
乖離が大きければハーネスの結論を採用しない。

## §9 受容基準

1. **翻訳の挙動が変わらないこと。** `prompts/*.txt`、`glossary.csv`、`prompt_glossary.csv`、
   翻訳経路のコードに差分が無いこと（アブレーション機構の追加を除く）。
2. `YAKULINGO_DISABLE_RULES` が未設定のとき、プロンプトが V91.60 と**バイト単位で一致**すること。
3. `Test-YakuPromptLayers.ps1` が現状の V91.60 を通過すること（ラチェットの初期状態）。
4. プロンプトへ日本語の語を1つ足すと、層の検査が**止めること**。
5. プロンプトを上限より1字多くすると、予算検査が**止めること**。
6. 規則台帳の全行に守護ケースが1件以上あること。書けない規則が一覧に出ること。
7. `YAKULINGO_DISABLE_RULES=R7` で R7 の行がプロンプトから消え、他の行が変わらないこと。
8. 評価セットが30件になり、`pair` を持つケースの対が揃っていること。
9. `pair` を持つケースの対が**同じ split** に入っていること。
10. 既定で `dev` のみが評価対象になり、`-IncludeHoldout` を付けたときだけ保留が入ること。
11. ノイズ床が再測定され、README に記録されていること。
12. `-Judge` が7条件を判定して出力し、1つでも欠ければ「不採用」と表示すること。
13. FIXED層の略語遵守率が算出され、F-6 の `Going fwd.` → `Going forward` が
    **退行として検出されること**（過去の見落としを再現して確かめる）。
14. 既存の回帰（Check-Encoding / 数値マスキング / 設定パス / bootstrap / V91.7 / V91.10 / V91.17）が
    すべて通過すること。

## §10 実装順序

| 段階 | 内容 | 単独で入れられるか |
| --- | --- | --- |
| 1 | 指標の追加（FIXED層遵守率・決定表遵守率・VDI）| 可 |
| 2 | 評価セットの拡張（30件）と `pair` 付与 | 可 |
| 3 | 分割（dev/holdout）と保留の規律・開封ログ | 段階2の後 |
| 4 | ノイズ床の再測定 | 段階1〜3の後 |
| 5 | 層の所有権検査 + 予算検査（`Test-YakuPromptLayers.ps1`） | 可 |
| 6 | 規則台帳（守護ケースの棚卸しを含む） | 段階2の後 |
| 7 | アブレーション機構と実行スクリプト | 段階6の後 |
| 8 | 採否判定 `-Judge` | 段階1〜4の後 |

**段階5（層の所有権 + 予算）は先に入れてよい。** 他と独立しており、
入れた瞬間からプロンプトの肥大が止まる。

**段階1（FIXED層遵守率）を最優先にする。** これが無いと段階5（BRIEF作り直し）の
採否を判定できず、F-6 の見落としを繰り返す。

## §11 触らないもの

- **翻訳経路のコード**（`Invoke-YakuTextTranslation` / `Invoke-YakuFileTranslation`）。
- **数値マスキング**（V91.60）。
