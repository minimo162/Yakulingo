# 決定: セルに収める仕事の設計（2026-08-17）

出発点は利用者の言葉である。

> 表の項目の場合は本当に狭いが、ここは毎年そんなに変わらないので翻訳メモリを活用したい。
> ただ時々新しい項目が追加されるので、そのときは短い訳を提示してあげる必要がある。
> 表の項目は文体で短くするのが難しいので、多少無理なabbreviationになっても仕方がない。
> 一方で文章の方は、毎年同じ文章ということはない。まずは、翻訳した英語が日本語文字数の
> 何倍かを見れば良いかも。（中略）2倍とかそれくらいに収めたい

4つの設計を別々の原理から作り、4つの観点で採点し、そのうえで攻撃した。
**首位の案は落ちた。さらに、4案すべてが共有していた前提も落ちた。**
以下はその結果として残ったものである。

表記の約束。

```
【実測】 このセッションか、記録に残っている実行で測った値
【コード】 ソースを開いて読んだ事実（ファイル:行を併記する。実行はしていない）
【案】   まだ測っていない提案
```

---

## 0. 決めたこと（先に結論）

**段階を分ける。前の段階が通らなければ次へ行かない。**

| 段階 | やること | Copilot 呼び出し | これが通らなければ |
| --- | --- | --- | --- |
| 0 | 幅の物差しを直して、実際のPDFと突き合わせる | 0回 | **以降すべて中止。** 予算が嘘なら、どんなプロンプトでも直らない |
| 1 | 出力側の体裁で収める（ShrinkToFit ほか） | 0回 | 段階2の対象が減らないだけ。中止条件ではない |
| 2 | 残った行にだけ、**幅の数**を渡して短い訳を作る | 1セグメント1回 | 収まる数が動かなければ、短縮そのものを諦めて体裁側へ寄せる |
| 3 | 再送・略語registry・一括処理 | 増える | 段階2の実測で必要と分かってから着手する |

**いま着手するのは段階0である。** 段階1と2の設計はここに書くが、着手は段階0の数字が出てからにする。

## 1. 攻撃が示したこと

### 1-1. 首位案（幅予算と展開往復検算）は成立しない

採点では首位だったが、次の4点で落ちた。いずれもコードを開いて確かめた。

**(a) 一括短縮が既存機構を再利用できない。**
案は「既存の `Invoke-YakuTranslationBatchItems` をそのまま使う」と書いていた。
この関数は `[[ID:n]] n. text` の番号つき契約に溶接されている（`Parse-YakuNumberedBatchResponse`）。
短縮の契約は `COMPACTION_JSON:` で始まる JSON 1個であり、通らない。
さらに `ConvertFrom-YakuPublicationCandidateResponse` も
`Complete-YakuCatPublicationCandidateSet`（`src/Publication.ps1`）も **1セグメント固定**である【コード】。
「既存の再利用」ではなく、外部送信の境界そのものを書き直す変更だった。

**(b) 案が要求する QC が、案が作りたい略語を構造的に禁じている。**
`Invoke-YakuCatSegmentValidation` は、訳文側に原文に無い数値があれば
`numeric-value-extra`（Severity=error）を立てる。免除は
**「利用者が登録した完全一致訳を、アプリが一字一句そのまま写した場合」だけ**である
（`src/CatProject.ps1:678-691`）。そしてその直前の註が、まさにこの問題を書いている【コード】。

> 決算の略語は原文に無い数字を持つ（上期→1H、第1四半期→Q1、2026年度→FY26）。
> これを numeric-value-extra で弾くと（中略）登録した訳が、そのまま確認済みにできなくなる。
> （`src/CatProject.ps1:670-676`）

つまり `上期 → 1H`、`2026年度 → FY26` は、**モデルに作らせても門が落とす。**
案は同時に「発明した略語に数字を含めてはならない」とも書いており、
決算資料でいちばん効く略語の種類を三重に閉じていた。

**(c) 完全一致（cell_exact）の保証を緩めていた。**
`src/CatProject.ps1:824-828` は、完全一致置換が
「用語の一貫性ではなく**列からはみ出さないこと**の保証」であると記録している。
去年その列に収まったから採られた訳語である。案には、その種のセグメントを
短縮の対象から外す規則が無かった。**幅の推定が悲観側に外れたとき、
収まると分かっている訳を、収まらないと判定して置き換えることになる。**

**(d) `copilotPromptCharLimit` を 0 から 8000 にすると、動いていた仕事が死ぬ。**
事前検査は `Invoke-YakuCopilotPromptUnsafe` の中で **throw** する。
ファイル翻訳の catch は送信確認系と沈黙タイムアウトしか拾わないので、
ファイルジョブ全体が落ち、そこまでの翻訳が破棄される。
案が回復手段として挙げた「バッチを半分にして送り直す」分岐は、
**応答が返ってきた後にしか到達しない**【コード】。送る前の throw には効かない。

### 1-2. 4案すべてが共有していた前提が誤り

4つとも「セルの幾何は与えられた入力で、動かせるのは英文だけ」という形をしていた。
名前は違ったが、4つとも同じ関数（幅を読んで、英文が満たすべき数を返す）から始まり、
**幾何を変える関数はどれにも無かった。** これはこのアプリでは誤りである。

- 書き戻しは**写し**に対して行われる（`Copy-Item -LiteralPath $InputPath`、
  `src/FileProcessors.ps1:5132`）。利用者の原本は変わらない【コード】
- その写しに対して、アプリは**既にセルの体裁を変えている**。
  `$cell.Font.Name = $OutputFontName`（`src/FileProcessors.ps1:1750`、ほか1799/2386ほか）【コード】。
  「アプリは体裁に触らない」は、このアプリが守っている制約ではない
- `ShrinkToFit` はリポジトリ全体に **0件**。`AutoFit` も **0件**【実測: grep】。
  どちらも同じ COM オブジェクトの、同じ try/catch の、1行である
- `src/SheetLayout.ps1` は `shrinkToFit` を読んでいない。したがって
  **原本のセルに既に ShrinkToFit が付いていても、アプリからは見えない。**
  そのセルは「はみ出し」と判定され、短縮の対象になる【コード】

**収まらないときの手当ての順序は、こうなっているべきである。**

```
1. 右隣が空ならExcelが勝手に溢れて表示する（0回・情報の欠損なし）
2. ShrinkToFit                                （0回・欠損なし・そのセルだけ）
3. そのセルの文字サイズを1段下げる            （0回・欠損なし・そのセルだけ）
4. 折り返し + 行の高さ                        （0回・欠損なし・行が伸びる）
5. 列幅を広げる                               （0回・欠損なし・右の列がずれる）
6. 登録済み略語をコードで当てる               （0回・可読性を払う）
7. モデルに短い訳を作らせる                   （1〜2回・意味の欠損が起こりうる・人の確認が要る）
```

**4案はすべて 7 から始めていた。** 2〜5 は費用ゼロ・欠損ゼロ・取り消し可能で、
アプリは既にその呼び出し位置に立っている。

### 1-3. 幅の物差しが、出力する書体を見ていない

これが最も効く。3案が「実フォントと合わなかったら」を自分の最悪ケースに挙げ、
運の悪いワークブックの話として扱っていた。**運ではない。既定の構成がそれである。**

```
測る側  www/assets/cat.js:2195   context.font = '14.7px Calibri, Arial, sans-serif'
書く側  src/Settings.ps1:97      output_font_name    = Arial        （和→英）
        src/Settings.ps1:98      output_font_name_jp = MS Pゴシック （英→和）
```

【コード】Office が入っている機械では Calibri が解決するので、Arial には落ちない。
Arial は同じ字上げで Calibri より広い。**したがって予算は甘い側に外れる。**
甘い側の誤りは「収まる」と判定して実際は切れる、という形で出る。
今日それは画面の印を1つ塗るだけだが、案の中では**振り分けと採用の門**になっていた。

`src/SheetLayout.ps1:114-124` にもう1つある。`width` 属性の無い `<col>` は
丸ごと読み飛ばされる。`<col min="5" max="5" hidden="1"/>` と書かれた隠し列は
`columns[]` に現れず、**既定幅 8.43 ぶんの余地があると数えられる**【コード】。
これも甘い側である。

### 1-4. ただし攻撃も1点外している。題材は在る

攻撃は繰り返し「fixture が存在せず、ブリーフの数値はどれも再現できない」と述べた。
**誤りである。** `_docs/比較題材_圧縮された原文_2026-08-17.json`（表のラベル20行）と
`_docs/比較題材_Smartcat通し比較_2026-08-17.json`（散文20文）が入っている。
**今日、全部の数字を再計算して一致した**【実測】。

さらに、攻撃が「復元できない」とした対照の対応づけも、題材から復元できた。

```
幅を伝えたときだけ収まった行   6
伝えなかったときだけ収まった行 0
両方収まった                   5
両方収まらなかった             9
```

【実測】完全に入れ子である。McNemar の正確検定で **p = 0.031**。
n=20 で、差を担いでいるのは6行だけなので薄いが、
**「幅を伝えると収まる数が動く」は偶然では説明しにくい。** この設計はこの1点に乗っている。

## 2. Q1 — 通常のプロンプトに入るもの、短いほうに入るもの、どちらにも入らないもの

### 通常のプロンプト（表のラベルも散文も同じ）

`prompts/cat_translate_to_en.txt` / `cat_translate_to_jp.txt`。
**幅の話を一切入れない。** 中身は現行のまま（契約行、保存規則、`{numeric_rules}`、
`{terminology_rules}`、`{source_list}`）。

理由は3つ。

1. ここで作られる訳が**基準訳**であり、TM・書き出し・QC の対象はこれである。
   幅の圧力をここへ掛けることは、記録そのものへ圧力を掛けることである
2. 18種の QC は基準訳の粒度で較正されている
3. 公表英文自身が散文2.78倍・ラベル3.21倍である【実測】。
   幅で締めた基準訳は「公表訳に近い」から**遠ざかる**。基準訳は近さを取る

**1行だけ直す。** 5行目の "Do not abbreviate, summarize, compress..." は、
同じプロンプトの22行目に差し込まれる `{numeric_rules}` の末尾
「Keep YoY, QoQ, CAGR, 3Q, Jan. to Dec.」（`src/PromptBuilder.ps1:672`）と逆を向いている【コード】。
5行目を**「原文に無い略語を新たに導入しない」**へ限定して、矛盾を解く。
これは幅の変更ではなく、既にある矛盾の訂正である。

### 短い訳のプロンプト（表のラベルだけ。散文には出さない）

既存の `New-YakuCompactionCandidatePrompt`（契約 `compaction-candidate-v1`、
`src/CopilotClient.ps1`）を**差し替えない。2行足すだけにする。**

差し替えない理由は測定ではなく機械的なものである。
`tools/Test-YakuV9170Publication.ps1:21-22` がこのプロンプトの文面を literal で固定している【コード】。
全面差し替えは、この設計と無関係な赤を作る。

足す2行【案】。

```
このセルに入る英字はおよそ N 文字ぶんである。N を超えない候補を返すこと。
正確さを保って N に収まらないなら、候補を返さず cannot_fit_reason を書くこと。
```

いま **N は渡っていない。** sidecar の `placement_budget.max_chars` は
JSON 全体と一緒に数値マスクを通るので、`"max_chars":"40"` は `"max_chars":"[[N7]]"` として
外へ出る（`src/Publication.ps1`、マスクは `\d[\d,]*` を無条件に拾う=`src/Translation.ps1:876`）【コード】。
そのうえで、返ってきた候補は**マスクされていない実数**と突き合わせて裁かれる
（`Complete-YakuCatPublicationCandidateSet`、`.Length -gt $maxChars`）。
**モデルは「予算がある」と言われ、「越えるなら断れ」と言われ、数だけ見せられずに、
後からその数で裁かれている。** N を本文（テンプレートの固定文）側へ出す。§3 に条件を書く。

### 表のラベルと散文で違うところ

| | 幅の予算 | 短縮経路 | 比率 |
| --- | --- | --- | --- |
| 表のラベル | セルから計算して渡す | 出す | 判定に使わない |
| 散文 | **渡さない** | ボタンは残すが予算なしで動く | **報告のみ。門にしない** |

散文に予算を渡さない理由【実測】。公表人手訳が 2.78倍、YakuLingo 2.90倍、
測った5経路のどれも 2.0 に届いていない。散文にはそもそも枠が無く、
2.0 を門にすれば公表訳自身が落ちる。

### どちらにも入れないもの

- `prompts/style_brief_rules.txt`（8,481字）。1つのファイルの中で
  9行目が「Q1 と書くな、the first quarter と書け」、40行目が
  「略語一覧の語は必ず略語を使え」と述べており、間に約2,100字の略語辞書がある【コード】。
  **いま生きた呼び出し口は無い。無いままにする**（削除は §7 の判断事項）
- 24行目の "Length is diagnostic, not a target."。沈黙より有害である。生かさない
- 2.0 という比率をモデルへ渡すこと。比率は症状であって予算ではない。セルごとに違う
- 月名の機械置換（`April Smith → Apr. Smith` を実際に作った）と、
  `rev.` `redn.`（`src/BriefStyle.ps1:55-62` で外し、`Test-YakuV9161SplitRequests.ps1:114-115` が固定している）
- 「固有名詞を守る」という約束。**それを確かめる検査はリポジトリに無い。**
  `src/Translation.ps1:1993` の docstring は、実装が提供しない保証を書いている【コード】。
  実装のほうが正しい（英文の固有名詞を機械で判定するのは当てにならない）。註を消す
- **アプリが検算できない指示は、どちらのプロンプトにも入れない。**

## 3. Q2 — 目標の数。どこから来て、誰が決めるか

### 数はワークブックが決める。誰も打ち込まない

サーバ側で、既に読んで持っている `sheet_layout`（`src/CatProject.ps1` の
プロジェクトビュー、`Get-YakuSheetLayoutFromXlsx`）から計算する【案】。

```
使える幅px = Σ 結合範囲の列（幅 × 7 + 5、1列あたり最低24px）
           + Σ spill_right_display_only の列
           − 8
N（文字数）= 使える幅px ÷ その訳文の字種で測った1文字あたりの幅
```

**`Math.max(24, ...)` の下限を落とさないこと。** 画面側（`www/assets/cat.js:2171-2179`）が
それを持っているので、落とすと狭いセルで画面と判定が食い違う【コード】。

### ただし、今日この式は信用できない

§1-3 のとおり、測る書体と書く書体が違う。**段階0 が終わるまで、この数を
振り分けにも採用の門にも使わない。** 段階0 でやること。

1. `cat.js:2195` の測定を、**訳す向きごとの出力書体**（`output_font_name` /
   `output_font_name_jp`）で行うように直す
2. `src/SheetLayout.ps1` に `shrinkToFit` の読み取りを足し、`width` 属性の無い
   `<col>` を「既定幅」ではなく「不明」として扱う
3. 実ファイル1冊を既存の render-pdf 経路（`src/Server.ps1:2410` →
   `src/Render.ps1:290` の `ExportAsFixedFormat`。本物の Excel が出す）で PDF にし、
   セルごとに「収まると判定した/実際に切れた」を突き合わせる。
   **偽の「収まる」と偽の「はみ出す」を別々に数える。** 向きが全部である

### 外へ出る数の条件（マスクの制約は1行も変えない）

`Assert-YakuNumericPromptProtected` は、**桁数が3未満の値を検査から飛ばす**
（`src/Translation.ps1:743-744`）【コード】。したがって次の規則にする。

- **予算は2桁（99以下）のときだけ送る。**
  100以上なら送らない。その幅のセルは、そもそも収まらない問題ではない
- 予算はテンプレートの固定文へ出す。**保護欄（マスク対象の field）には入れない。**
  保護欄は送信前に再走査され、裸の数字が1つでも残っていれば拒否される
- この形なら、文書由来の数値と衝突しようがない（3桁未満は照合対象外）

**これは制約の緩和ではないが、レイアウト由来の整数が新しく外へ出ることではある。
出してよいかは §7 の判断事項として利用者に上げる。**

### 予算を出さない条件（＝短縮しない）

- `.xlsx` / `.xlsm` 以外、または `sheet_layout` が空（読めなかった）
- 折り返しが有効なセル（縦に伸びるので幅は制約ではない）
- 隠し列（幅0）
- 予算が現訳の長さ以上（はみ出していない）
- 予算が100文字以上、または8文字未満（8未満は短縮ではなく破壊である）
- **完全一致（cell_exact）で入った訳**。去年その列に収まった実績が保証である。
  幅の推定より、そちらの実績を採る

### 同じ原文が違う幅のセルへ入るとき

CAT のワーカーは同じ原文を1回だけ送り、結果を全部の宛先へ配る
（`src/Server.ps1:1138-1148` の `$byText`）【コード】。
**予算は、その原文が入る全セルの最小値にする。** 他の選び方は、
いちばん狭いセルを黙って溢れさせる。

### 誰が決めるか

- 数はワークブックが決め、アプリが計算する
- 利用者が決めるのは「入れるか（機能の入切）」と「安全率」だけ
- **Copilot は数について何も決めない。** `fit_estimate` は記録と表示に使い、
  いかなる分岐にも使わない

## 4. Q3 — 答えが目標を破ったら、送り直すか

### 今回は自動の再送を入れない

理由は回数の節約ではない（設計上の上限は無い）。次の2つである。

1. **すでに1回の応答で複数試している。** 短縮の応答は候補を最大5件受ける
   （`src/Publication.ps1`、`Select-Object -First 5`）【コード】。
   「同じ質問をもう1回する」前に、1回の中で選ぶ余地がある
2. **2回目に効果があるかを測っていない。** 測っているのは「幅を伝えると
   1回目が変わる」だけである（5/20 → 11/20）。2回目の効果は誰も測っていない。
   **効くという証拠の無い往復を、先に配管へ埋め込まない**

### 段階3で入れるときの規則（先に書いておく）【案】

- **1回だけ。** 3回目は無い
- 変えるのは3つだけ。(a) 1回目の答えを CURRENT として渡す、
  (b) 超過ぶんを文字数で伝える、(c) その項目に実際に出てくる登録済み略語だけを列挙する
- 2回目が1回目より悪ければ、**1回目を採る**

### 送り直さない（即停止）条件

| 状況 | 扱い |
| --- | --- |
| QC の error で落ちた | **再送しない。** 数値の落ちた訳は欠陥であり、同じ依頼の繰り返しは賭けである |
| `cannot_fit_reason` が返った | 再送しない。短縮ではなく体裁側の手を画面に出す |
| `PROMPT_TRUNCATED_BY_INPUT_LIMIT` | **同じプロンプトを送り直さない。** バッチを割って送る |
| Copilot が上限超過を返した | 停止（CLAUDE.md） |
| 2回目も収まらない | 停止。基準訳をセルに残す |

### 収まらなかったときに何が起きるか

**必ず基準訳が入る。** 空欄にもエラーにもしない。
画面には既にある印（`is-overflow-risk` / `収まり要確認`）を出す。

**fit は書き出しの停止条件にしない。** 停止条件は3つのまま
（`segment-untranslated` / `segment-qc-failed` / `segment-qc-not-current`）。
増やさないし減らさない。収まらないのはレイアウトの問題であり、
数値が落ちたのは既に `segment-qc-failed` が捕まえている。

## 5. Q4 — 短くする間、品質は何で守るか

**モデルに頼むのではなく、アプリが確かめるもの。すべてサーバ側・決定的。**

1. **セグメント検査を候補の写しに掛ける。** `Invoke-YakuCatSegmentValidation`。
   18種の error 全部。既に `Complete-YakuCatPublicationCandidateSet` がやっている。落とさない
2. **`[[Nn]] の順序**が基準訳と同一であること。個数一致では足りない
   （入れ替わると営業利益の欄に売上高が入る）。この検査は今**死んだ短縮経路にしか無い**
   （`src/Translation.ps1:2101-2103`）【コード】。生きている掲載経路へ移す
3. **収まりを幅で測る。** いまは `.Length -gt $maxChars`、つまり
   プロポーショナル書体に対する**文字数**である（`src/Publication.ps1`）【コード】。
   `WWWWWWWW` と `iiiiiiii` は同じ長さで、幅は3倍近く違う。段階0 の測定に置き換える
4. **収まりは3状態で持つ。** 収まる / はみ出す / **測れない**。
   測れないを「はみ出す」へ畳まない。畳むと道具の故障が対象の欠陥に化ける
   （CLAUDE.md、`Measure-YakuUiFloor.ps1` の 0/1/**3**）
5. **申告されていない略語を落とす。** 基準訳にも原文にも無く、
   `[A-Z]{2,}` か `語+.` の形をしていて、登録済みでもない語があれば、その候補を落とす。
   応答全体は落とさない
6. **人の確認は外さない。** 原文・基準訳・候補の3つを並べ、
   `meaning_preservation_confirmed` を要求する。修飾語や条件節が落ちたことを
   機械で確かめる手段は無い。**無いと書く。あると書かない**
7. **掲載訳は基準訳を上書きしない。** TM に入るのは基準訳のままにする（今回は変えない）

### モデルに聞くが、信じないもの

`fit_estimate` / `claimed_preserved_facts` / `transformations` / 略語の自己申告。
**全部、記録して表示する。どれも門にしない。**
唯一機械で使うのは候補の本文と略語の別名で、その別名は
「実際に本文に出てくるか」を既に確かめている。その検査は残す。

### コードを読んで分かった、動かせない事実が2つある

**(a) 数字を含む略語は、モデルに作らせても通らない。**
`上期 → 1H`、`2026年度 → FY26` は原文に無い数字を訳文へ持ち込むので
`numeric-value-extra`（error）になる。免除は
**「利用者が登録した完全一致訳を、アプリが一字一句そのまま写した場合」だけ**
（`src/CatProject.ps1:678-691`、註は 670-676）【コード】。
したがって利用者の「多少無理な abbreviation でも仕方がない」に対する答えは、
**数字を含む略語については「registry へ登録する道しかない」**である。
これは今回の設計が課す制限ではなく、既にそうなっている事実である。

**(b) 略語の往復が今日壊れている。段階2の前提として直す。**
`allowed_abbreviations` は `entry_id`（32桁の16進）と `version` を載せて送る。
sidecar は JSON 化してから丸ごとマスクされ、マスクは digit の並びを無条件に拾う
（`src/Translation.ps1:876`）。一方、戻ってきた申告は**素の** `entry_id:version` で
作った表と突き合わせ、無ければ `CAT_PUBLICATION_RESPONSE_ABBREVIATION_NOT_ALLOWED` を
**応答全体に対して throw する**（`src/Publication.ps1`）【コード】。
モデルは見せられたもの（マスク済み）しか返せない。
**利用者が最初に略語を登録し、モデルがそれを使ったと申告した瞬間に、候補生成が丸ごと落ちる。**
`tools/Test-YakuV9170Publication.ps1:24` は素の `entry_id` で payload を組むので、
**試験は緑のまま production が落ちる。**

直し方【案】。鍵を `abbreviation` の文字列にする（数字を含まないのでマスクを通らない。
`Register-YakuCatAbbreviationEntry` が重複登録を拒むので一意性もある）。
`entry_id` と `version` を sidecar から外す。throw を「その候補だけ落とす」に変える。
試験の payload を `$request.ProtectedSidecar` から組み直す。

**これは静的な読みであって、実行して再現したわけではない**（§8 の試験で確かめる）。

## 6. アプリが決めることと、モデルに聞くこと

| | 決めるもの |
| --- | --- |
| **アプリ（決定的）** | セルの幅、予算の数、どのセグメントを短縮対象にするか、収まったかの判定、数値・用語・構造・マスク順序の検査、登録済み略語の適用、申告外の略語の排除、書き出しを止めるかどうか |
| **モデル（確率的）** | どの語を削ってよいか、どう言い換えるか、削ると意味が壊れるので断る、という判断 |
| **人** | 意味が保たれたかの最終確認、略語の登録、体裁で逃がすか短縮するかの選択 |

**線がここに在る理由は2つある。**

1. **アプリが検算できないことは、プロンプトに書いても保証にならない。**
   `src/BriefStyle.ps1` 冒頭の判断であり、いまも正しい
2. **アプリが列挙できることは、モデルに聞かない。**
   頭字語・先頭+句点・母音削除は「判定規則」であると同時に「生成規則」でもある。
   基準訳に在る語からその3規則で作れる候補は、アプリが自分で並べて幅で選べる。
   4〜5秒の往復を払う値打ちがあるのは、**「この修飾語は落としてよいか」という
   判断が要る部分だけ**である

**段階1（体裁の手当て）— これも実ファイルで測る。**

  そのときは「モデルに短くさせる」を捨てる判断として記録する

**段階2の前提（先に単独で走らせられる）**

## 9. やらないこと（次の回が同じことを繰り返さないために）

**4つの設計のうちどれかを丸ごと実装すること。**
首位案は §1-1 の4点で落ち、4案すべてが §1-2 の前提を共有していた。
この文書に残っているのは、そこから生き残った部分だけである。

**一括（複数セグメント）の短縮。**
`Invoke-YakuTranslationBatchItems` は番号つき契約に溶接されており、
短縮の応答契約は通らない。掲載候補の解析・完成・適用はすべて1セグメント固定である【コード】。
「既存機構の再利用」ではなく、外部送信の境界の書き直しになる。段階3で、必要と分かってから。

事前検査は throw であり、ファイルジョブ全体が落ちて翻訳が破棄される。

`Invoke-YakuTextShorten` へ入る HTTP 経路は無い（`Start-YakuTranslationJob` の

**モデルの `fit_estimate` を信じること。**

**題材（fixture）を新しく作ること。** 既にある（§8）。数値も再現できる。
