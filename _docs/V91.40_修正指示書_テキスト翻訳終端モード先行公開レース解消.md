# YakuLingo V91.40 修正指示書

作成日: 2026-07-21 / ベース: V91.39（ratio1.7・品質関連費用conflict・実績variant修正版）

対象は1点: テキスト翻訳完了直後に「翻訳結果はまだ保存されていません。出力ファイルは
outputs フォルダに保存されている場合があります。ツールを再起動すると結果を再表示
できます。」が表示され、結果が出ないまま終了する不具合の解消。

---

## 現象と再現ログ（2026-07-21 16:24 テキスト翻訳 jobId=74758ab1）

```
16:24:05.270 Translation job started. kind=text inputLength=1755 warmRunspace=True
16:24:41.490 Text translation attempt failed. attempt=1/3 errorCode=NUMERIC_SCALE_MISMATCH_RETRY
16:25:04.190 Numeric integrity audit. location=text-full checked=28 matched=28   ← attempt2成功
16:25:04.397 Text glossary occurrence audit: checked=38 violated=3
16:25:04.494 Warm translation runspace build started.                            ← ジョブ完了検知後の再ビルド
```

**翻訳パイプライン自体は正常完了している**（監査全件一致・violated=3は表示上の
警告対象で失敗ではない）。ERRORログも例外ログもゼロ。にもかかわらずUIには
上記の警告が出て結果が表示されない。

## 真因: 終端モードの先行公開レース

テキスト翻訳の完了公開が**2箇所から二重に**行われており、順序が壊れている。

1. `Translation.ps1:1375`（`Invoke-YakuTextTranslation` の末尾）が
   `Set-YakuTranslationProgress -Mode 'done'` で**共有state（Synchronized
   hashtable）の mode を先に 'done' にする**
2. その後 return し、呼び出し元の Server.ps1 内ワーカースクリプト（1125行付近）が
   `$JobState['result_json'] = ($result | ConvertTo-Json -Depth 80 -Compress)`
   で結果を格納する

この (1)→(2) の間に UI の1秒間隔ポーリング（`/api/jobs/{id}` →
`Convert-YakuTranslationJobResultJson`）が着弾すると:

- mode は終端（'done'）だが `result_json` は空
- テキストジョブは runspace 実行のため `result_path`（ディスク退避）が**存在しない**
  （fileジョブ専用。Start-YakuFileProcessJob のみが設定: Server.ps1:956）
- → Server.ps1:1285 のフォールバック警告「翻訳結果はまだ保存されていません…」を
  html として返却
- クライアント側 `yakuFinishJob`（app.js:328）は終端modeを受けると**ポーリングを
  恒久停止**するため、直後に result_json が入っても二度と取得されない

レース窓 = `ConvertTo-Json -Depth 80` の所要時間。今回は応答5,931字＋プロンプト
12,429字＋AppliedGlossary 125件＋Batches をネスト直列化するため窓が広がり、
1秒ポーリングに踏まれた。15:57 の同種ジョブ（応答2,350字・glossary違反0）は
窓が狭く偶然すり抜けていた。**発生は確率的で、入力が長いほど高確率**。

裏付け: 16:25:04.494 の warm rebuild は `yakuFinishJob` が発火する
`yaku-history-refresh` リクエスト由来の `Update-YakuTranslationJobs` と整合
（警告html配信→直後の別リクエストで EndInvoke 完了検知、の順）。

なお同じ構造のレースが**エラー経路にもある**: `Translation.ps1:1378` が
`-Mode 'error'` を先行公開し、ワーカーの result_json（Error JSON）格納が後になる。

fileジョブは影響なし（FileWorker が result.json をディスクへ書いてから終端
state.json を公開する設計。Update-YakuTranslationJobs 側にlazy-load装備済み）。

## §1 Translation.ps1: 終端モードの先行公開をやめる（本命修正）

終端化（done/error の公開）は Server.ps1 ワーカー側に**一本化**する。
`Invoke-YakuTextTranslation` 内は非終端の finalizing 表示に変更。

**1375行目**（成功経路）:

```powershell
# 変更前
Set-YakuTranslationProgress -ProgressState $ProgressState -Mode 'done' -Label 'Done' -Progress 100 -Detail 'Translation completed.'
# 変更後
Set-YakuTranslationProgress -ProgressState $ProgressState -Mode 'working' -Label '仕上げ中' -Progress 99 -Detail '結果を保存しています' -Phase 'finalizing'
```

**1378行目**（catch経路）:

```powershell
# 変更前
Set-YakuTranslationProgress -ProgressState $ProgressState -Mode 'error' -Label 'Translation error' -Progress 100 -Detail $_.Exception.Message
# 変更後
Set-YakuTranslationProgress -ProgressState $ProgressState -Mode 'working' -Label 'エラー処理中' -Progress 99 -Detail $_.Exception.Message -Phase 'finalizing'
```

エラー内容は従来どおり戻り値の `Error` プロパティで伝搬し、ワーカーが
mode='error'・result_json を**この順で**確定する（既存ロジックのまま到達可能）。

## §2 Server.ps1 ワーカー: 代入順序の統一（catch経路の残余レース潰し）

ワーカーの catch ブロック（1166〜1174行付近）は現在
`mode='error'` → … → `completed_at` → `result_json` の順で、mode公開が
result_json より先。**result_json を最初、mode を最後**に並べ替える:

```powershell
$JobState['result_json'] = ([pscustomobject]@{ Error=$message; Kind=$Kind } | ConvertTo-Json -Depth 10 -Compress)
$JobState['label'] = 'Translation error'
$JobState['class'] = 'warn'
$JobState['detail'] = $message
$JobState['progress'] = 100
$JobState['completed_at'] = (Get-Date).ToString('s')
$JobState['updated_at'] = (Get-Date).ToString('s')
$JobState['mode'] = 'error'
```

成功経路は既に result_json → mode の順で正しい（変更不要）。ただし
`completed_at` が mode より後に入る箇所があれば mode を最後尾へ移すこと。
不変条件は「**ポーリングが終端modeを観測した時点で result_json は必ず充填済み**」。

## §3 Server.ps1 Convert-YakuTranslationJobResultJson: 二重防御

§1・§2で理論上レースは消えるが、将来 mode を先行公開するコードが混入した場合の
保険として、1285行の警告フォールバックの手前に**ダウングレード判定**を入れる:

```powershell
# 終端modeなのに result_json も result_path も無く、完了時刻も未確定なら
# まだ確定処理中とみなし、終端をクライアントへ公開しない（ポーリング継続）
if ([string]::IsNullOrWhiteSpace($resultJson) -and
    [string]::IsNullOrWhiteSpace($lazyPath) -and
    [string]::IsNullOrWhiteSpace([string]$State['completed_at'])) {
    $mode = 'working'
    $label = '仕上げ中'
    $html = ''
} else {
    $html = New-YakuAlertHtml -Kind warning -Message '翻訳結果はまだ保存されていません。…'（既存文言のまま）
}
```

判定キーに `completed_at` を使う根拠: §2適用後、completed_at は常に
result_json より後・mode より前に確定するため「終端mode ∧ completed_at空」は
先行公開の瞬間しか成立しない。file経路（result_path あり）の既存フォールバックには
影響しない。

## 受入基準

1. 1,800字級の日本語テキスト（今回相当。glossary適用が多いもの）を翻訳し、
   警告なしで結果が表示される。**5回連続**で再現ゼロを確認
   （確率事象のため単発成功では不足）
2. ログ検証: `Translation job started` 〜 warm rebuild の間で、ポーリング応答が
   mode=working(finalizing) を経て done に遷移していること（診断で確認可能なら）
3. エラー経路: 存在しない終端マーカー等で意図的に失敗させ、エラーメッセージが
   正しく表示される（§1変更でエラー伝搬が壊れていないこと）
4. file翻訳のリグレッションなし: 250KBブック再翻訳で従来どおり完走・結果表示

## 応急対応（修正配布前にユーザーへ案内可）

この警告が出た場合、翻訳自体は完了しており履歴にも保存済み。**ページ再読み込み
（F5）**で sessionStorage からジョブが復元され、結果が再表示される
（ジョブstateはメモリに残存しているため。保持期間30分以内）。

## 付記（今回は変更しない）

`Invoke-YakuTextTranslation` 内の進捗係数分岐 `if ($Kind -eq 'text')` は関数の
パラメータではなく、呼び出し元ワーカースクリプトの `$Kind` を動的スコープで
参照している。現行の呼び出し経路（Server.ps1 ワーカーのみ）では正しく動くが、
他所から呼ぶと file 係数(1.7)にフォールバックする脆さがある。次回リファクタ時に
パラメータ化を検討。
