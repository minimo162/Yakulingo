# YakuLingo 要件整理: 汎用翻訳アプリへ向けた現状と選択肢

作成日: 2026-08-04 / 対象: V91.60 時点 / 位置づけ: **設計の前段。実装方針は決めない**

この文書は「何が必要か」「何が使えるか」「何を決めないと進めないか」を並べる。
解決策の比較検討は行うが、採否は決めない。

---

## §1 目的の階層と、その緊張関係

| 層 | 目的 |
| --- | --- |
| 最終 | 社内で**誰でも気軽に、かつセキュアに**使える**汎用**翻訳アプリ |
| 当面 | **財務本部内の ECM 資料**の英訳に役立つこと |

この2つは素直には両立しない。ECM 資料に効かせようとするほど ECM 固有の知識が
増え、その知識が**器のどこに置かれているか**で汎用化の可否が決まる。

### 現状は汎用化できない形になっている

ECM 固有の知識が、いま**プロンプト本文と用語集**に埋め込まれている。

| 固有知識 | いまの置き場所 | 汎用化のとき |
| --- | --- | --- |
| 財務用語の訳語 | `glossary.csv` / `prompt_glossary.csv` | 差し替えられる（データなので） |
| 略語116語・言い換え | `style_brief_rules.txt` に直書き（2,502字） | **差し替えられない** |
| 販促費ラベル9語 | `file_translate_to_en.txt` に直書き | **差し替えられない** |
| oku / k yen / k units の単位方針 | プロンプトとコード | 部署が変われば変わる可能性 |
| BRIEF という出力形式そのもの | プロンプト全体 | ECM 固有の要求 |

**別部署へ持っていくとき、プロンプトを書き換えないと使えない。**
これは「汎用アプリ」ではなく「ECM 専用アプリ」である。

### 分離の原則

> **固有知識はすべてデータへ。器（コード・プロンプト）は分野に依存しない形にする。**

この観点から見ると、**RAG のデータベース選択は「固有知識をデータへ追い出す」仕組みそのもの**である。
別部署はデータベースを差し替えるだけで使える。§5-B の評価はこの点でも肯定的になる。

## §3 満たせていない要件と、その原因

### 3-1 用語集が網羅的でないのに、それに依存している

**利用者の評価（一次情報）:**

- ファイル翻訳の**表項目**は表現が比較的固定されているため、完全一致の用語集が
  それなりに効いている。**ただし表現が変化するため、かなり抜けがある。**
- **それ以外（文中・散文）は、その時々で表現が異なる。**
  トークン化に耐えるだけの用語集を作ることはできない。

**構造上の問題:** 網羅できないものに、網羅を前提とした仕組みを載せている。

| 依存の形 | 前提 | 実態 |
| --- | --- | --- |
| プロンプトへの訳語注入（48件上限） | 用語集が正解を持っている | 持っていない語が大半 |
| 遵守の事後監査 | 守るべき正解が定まっている | 定まっていない |
| 守られなければ再依頼 | 再依頼すれば正解に近づく | 正解が無いので近づかない |
| `style_brief_rules.txt` の略語リスト116語 | リストで圧縮が足りる | リスト外は縮まない |

**実測（V91.59、評価ハーネス）:**

| | BRIEF 圧縮率 |
| --- | --- |
| 用語集がカバーする語彙の文 | 0.55 |
| カバーしない語彙の文 | 0.75 |

同じ業務文書、同じ文長、同じ文体である。**辞書に載っているかどうかだけで品質が変わる。**

そして用語集のために使っている資源は小さくない。プロンプト2,502字、注入枠48件、
遵守監査、再依頼。**網羅できない前提で見ると、この資源は回収できていない。**

### 3-2 FULL と BRIEF を分けていないため、Copilot の処理が曖昧になる

1回の依頼で「自然な業務英語」と「電文体」という**性質の異なる2つ**を同時に作らせている。

- プロンプトの規則の多くが「モード間の混線を防ぐこと」に費やされている
  （R3・R3a、BRIEF側の但し書き）
- 圧縮操作（冠詞削除・名詞句化・複合名詞化）は**英語に対する操作**だが、
  いま日本語を読みながら適用させている。だから語彙照合しか働かず、3-1の実測につながる
- 検証も両モードまとめて行うため、片方の失敗で両方を作り直す

## §4 制約（動かせない前提）

**ここが選択肢を強く絞るため、先に確定させる。**

| 制約 | 内容 | 影響 |
| --- | --- | --- |
| 実行環境 | Windows + **PowerShell 5.1** + Edge + Excel | .NET Framework の範囲で書く |
| 配布 | 共有フォルダ + ローカル複製。**追加インストール不可** | Python・外部ランタイム・DBサーバーを前提にできない |
| 外部接続 | **M365 Copilot のみ**（Edge CDP 経由） | 任意の外部 API を前提にできない |
| 機密 | 数値は外部送信前にマスク（V91.60） | 外部へ出すものは常に審査対象 |
| 利用者 | 財務本部の一般利用者。技術者ではない | 事前準備を要する機能は使われない |

### この制約から直ちに出る結論

**埋め込みモデル（意味検索）を前提にした RAG は、現時点では実装できない。**

- ローカルで埋め込みを計算する → モデルファイルとランタイムの追加インストールが必要
- 外部の埋め込み API を呼ぶ → 調達とセキュリティ審査が別途必要。Copilot 以外の外部接続になる
- Copilot に埋め込みを作らせる → 現実的でない

→ **語彙ベースの検索（BM25 等）なら PowerShell 単体で実装できる。**
詳細は §6-1。**「RAG をやる／やらない」ではなく「どの検索方式でやるか」が論点である。**

## §5 提案されている2つの方向の評価

### §5-A CDP 接続を複数持ち、FULL 専用 / BRIEF 専用に分けて依頼する

**評価: 妥当。** §3-2 の原因に直接効く。所要時間も悪化しない見込み。

**ただし設計が2通りに分かれ、意味が大きく違う。**

| 案 | 流れ | 長所 | 短所 |
| --- | --- | --- | --- |
| **A-1 並列** | 原文 → FULL / 原文 → BRIEF を同時に | 速い（今と同じか短い） | BRIEF はやはり「日本語を読みながら圧縮」。§3-1 の語彙依存は残る |
| **A-2 直列** | 原文 → FULL → BRIEF | BRIEF が**英語→英語の圧縮**になり、圧縮操作が直接効く | 2回が直列なので遅い |

**BRIEF の語彙依存（0.55 対 0.75）は、A-1 では原理的に解消しない。**
一方で、RAG（§5-B）で BRIEF の文例が入るなら、A-1 でも十分になる可能性がある。
**RAG の導入可否と合わせて決める。単独で決めない。**

**副次的な利点:** 接続を分けると会話履歴が混ざらない。現状は同一チャットへ連続で
依頼しているため、前の依頼の内容が後の応答に影響しうる。分離はこれも解消する。

**実装コスト:** 現状は Copilot のターゲット（タブ）を1つだけキャッシュしている
（`$script:YakuCopilotTargetCache` が単一スロット）。WebSocket 側はキー付きの
キャッシュになっているため、**ターゲット管理を1枠から2枠へ広げるのが主作業**。
書き直しではない。

### §5-B RAG 翻訳（日英対訳コーパスから、原文に合った文例を抜粋して渡す）

**評価: 方向として正しい。§3-1 に対する正しい答えである。**

理由:

1. **表現の揺れを吸収できる。** 完全一致ではなく類似で引くため、
   「その時々で表現が異なる」状況に耐える。用語集が構造的にできないことができる。
2. **語だけでなく文体・語順・省略の仕方を同時に伝えられる。**
   いま 7,773字の散文で説明していることが、実例で置き換わる。
3. **作成が「定義する」ではなく「集める」で済む。**
   用語集は1件ずつ人が正解を決める必要があるが、コーパスは既存資料から採取する。
   網羅性の桁が違う。
4. **データベースを選べる = 目的別・部署別に切り替えられる。** §1 の汎用化に直結する。

#### 特に重要な発見: 2つのコーパスが FULL / BRIEF に自然に対応する

| コーパス | 文体 | 対応するモード | マスキング |
| --- | --- | --- | --- |
| 過去の ECM 資料（日 / 英） | 短く詰まった社内様式 | **BRIEF** | **要**（極秘） |
| 英文短信・アニュアルレポート・英文有報 | 正式な開示文体 | **FULL** | 不要（開示済み） |

**BRIEF の様式を説明で伝えるのではなく、過去の ECM 英訳そのもので示せる。**
§3-2 で挙げた「圧縮操作が語彙照合に頼っている」問題に対して、
最も直接的な材料が既に社内に存在していることになる。

## §6 RAG を実装するうえでの論点

**ここが本番である。「RAG にする」だけでは何も決まっていない。**

### §6-1 検索方式 — 3つの選択肢

**「RAG をやるか」ではなく「どの方式でやるか」が論点である。**

| | A. 語彙検索 | B. 埋め込み検索 | C. Agentic RAG |
| --- | --- | --- | --- |
| 仕組み | 文字N-gram + BM25 | ruri v3 でベクトル化して近傍探索 | Copilot に検索語を作らせて `Select-String` |
| 利用者端末に要るもの | **なし** | **モデル + ONNX ランタイム（数百MB）** | **なし** |
| 表現の揺れへの強さ | **弱い**（字面が違うと引けない） | **強い** | **強い**（同義語・言い換えを生成できる） |
| 追加の Copilot 往復 | なし | なし | **+1回** |
| 構築コスト | 低 | **高**（§6-1-2 の未検証点3件） | 中 |
| §4 の制約との相性 | ○ | 要検証 | ○ |

#### §6-1-1 A（語彙検索）が単独では足りない理由

日本語の語彙検索に形態素解析器は不要である。**文字 bi-gram / tri-gram を索引語にすれば
解析器なしで成立する**（日本語検索で実績のある手法）。PowerShell 単体で書ける。

ただし A の弱点は、まさに利用者が指摘した**表現の揺れ**である。
「販売促進費」で索引されたコーパスは「販促費」で引けない。
用語集の完全一致が抜けるのと同じ理由で抜ける。**A だけでは §3-1 を解けない。**

#### §6-1-2 B（埋め込み検索）の実現性 — 事実確認の結果

`cl-nagoya/ruri-v3-30m` を調べた結果:

| 項目 | 値 | 判定 |
| --- | --- | --- |
| ライセンス | **Apache 2.0** | ○ 商用利用可 |
| パラメータ | 37M（うち埋め込み以外 10M） | ○ 小さい |
| 基盤 | ModernBERT-Ja | — |
| トークナイザ | **SentencePiece・100K語彙** | ○ **形態素解析器が不要** |
| 埋め込み次元 | 256 | ○ 索引が小さい |
| 最大長 | 8192 トークン | ○ 十分 |
| 検索時の接頭辞 | `検索クエリ: ` / `検索文書: ` | 実装時に必須。付け忘れると精度が落ちる |
| **ONNX 重み** | **リポジトリに無い** | **自前で変換が必要** |

**残る未検証点が3つある。いずれも PowerShell 5.1 / .NET Framework 環境の話である。**

| # | 未検証点 | 失敗したときの影響 |
| --- | --- | --- |
| 1 | ModernBERT（RoPE・GeGLU・局所/大域交互注意）が ONNX へ正しく書き出せるか | B が成立しない |
| 2 | **SentencePiece トークナイザを .NET Framework 上で動かせるか** | B が成立しない。**ここが最も危ない** |
| 3 | ONNX Runtime を PowerShell 5.1 から読み込めるか（.NET Standard 2.0 対応の版があるか） | B が成立しない |

**B は「不可能」ではなく「未検証の依存が3つある」。**
3つとも通れば有力だが、通らない場合に代案が無い状態で進めてはいけない。

**配布への影響も無視できない。** コーパスのベクトル化は管理者が1回行えばよいが、
**入力文のベクトル化は利用者端末で毎回行う**。つまりモデルとランタイムを
全端末へ配る必要がある。`bootstrap.ps1` は配布物を丸ごとローカルへ複製し
SHA-256 で全件検証するため、起動時間と複製サイズに直接効く。

#### §6-1-3 C（Agentic RAG）— A の弱点をちょうど補う

Copilot に「この原文を検索するならどんな語で引くか」を作らせ、その語で
コーパスを `Select-String` 等で引く。**同義語・言い換えを生成できるため、
埋め込みなしで表現の揺れを越えられる。** 端末に何も要らない。

代償は Copilot 往復が1回増えること。ただし次の2点で緩和できる。

- **検索語の生成はバッチごとではなく翻訳ジョブごとに1回でよい。**
  長文・ファイル翻訳では往復増が1回で済み、相対的な負担は小さい。
- FULL / BRIEF を別接続で並列化する（§5-A）なら、
  「検索語生成 → FULL と BRIEF を並列」で**合計2ラウンド**。
  現状（1ラウンド + 検証失敗時の再試行）と大きくは変わらない見込み。

#### §6-1-4 方針案: A を土台にし、C で補い、B は塞がない

- **A + C の併用から始める。** 通常は A（往復増なし）で引き、
  十分な件数・質が得られないときだけ C で検索語を広げて引き直す。
  **通常時は往復増ゼロ、必要なときだけ +1回**になる。
- **検索層を差し替え可能にする。** 索引の作り方と類似度の計算を分離しておけば、
  §6-1-2 の3点が検証で通ったとき B を後から差し込める。
- **B の検証は先行して行ってよいが、本線を止めない。**

### §6-2 コーパスの作り方 — **ここが最大の作業量**

日本語資料と英語資料は**別々の文書**である。RAG に使うには
**どの日本語文がどの英文に対応するか**を対応づける必要がある（文アライメント）。

**この工数を軽く見ると計画が崩れる。**

| 資料 | アライメントのしやすさ | 手がかり |
| --- | --- | --- |
| 英文短信・有報 | **しやすい** | 見出し・表の構造が日英で対応している |
| 過去 ECM 資料 | しやすい | 同じ資料の日英版が対で存在するなら位置が対応する |
| アニュアルレポート | **難しい** | 構成の自由度が高く、意訳・再構成が入る |

#### このドメイン固有の強み: 数値がアライメントの手がかりになる

財務資料は数字が多く、**日英で同じ数値が現れる文はペアである可能性が高い。**
一般の対訳アライメントより有利な条件がある。

しかも**その数値を抽出する機構は既にある**（V91.60 の数値マスキングと数値整合監査）。
`Convert-YakuNumericUnits` と `Get-YakuNumericAuditExpectations` がそのまま使える。

**現実的な手順:** 自動で候補ペアを出し、人が確認して採否を決める半自動。
全自動にはしない。**誤ったペアは誤った訳を教えるため、コーパスの品質がそのまま訳質になる。**

### §6-3 コーパスの粒度

| 粒度 | 向く用途 | 備考 |
| --- | --- | --- |
| 文 | 散文の翻訳 | 標準的 |
| 段落 | 文脈が要る場合 | 抜粋が長くなる |
| **表項目・ラベル** | Excel のセル | ECM 資料は表が多い。**用語集の完全一致置換と役割が重なる**ので整理が要る |

### §6-4 セキュリティ — **決定済み（2026-08-04）**

| コーパス | Copilot への送信 | 保管場所の制限 |
| --- | --- | --- |
| 英文短信・AR・有報（開示済み） | **可**（マスキング不要） | 制限なし |
| 過去 ECM 資料 | **可。ただし数値をマスキングすること** | **財務本部外へ出せない** |

**この2つは別々の制約である。**「Copilot へ送ってよい」ことと
「社内で共有してよい」ことは一致しない。M365 Copilot はテナント管理下にあるが、
社内の他部署は必要知識の範囲外にある。

#### 設計上の帰結: コーパスは配布物ではなく参照先にする

現在 `bootstrap.ps1` は共有フォルダの配布物を**丸ごとローカルへ複製**する。
コーパスをアプリ配布物の中に置くと、**アプリが行く先すべてにコーパスが行く**。
財務本部外へ配れなくなり、§1 の汎用化とも矛盾する。

| 方針 | 内容 |
| --- | --- |
| アプリ配布物 | **コーパスを含まない。** 配布範囲を制限しなくてよい |
| コーパス | **別の場所に置き、パスで参照する**（設定 `corpus_root`） |
| 既定の置き場所 | 財務本部限定の共有フォルダ |
| コーパスへ到達できないとき | **RAG を無効にしてアプリは動く。** 失敗ではなく機能縮退とする |
| 他部署へ展開するとき | 参照先を差し替えるだけ。アプリは共通 |

**副次的な利点:** コーパスの更新がアプリの版更新と切り離される。
資料が増えるたびに版を上げる運用にならない。

#### コーパスは**マスキング済みで保管する**

過去 ECM 資料は、コーパス化の時点で数値をマスクして保管する（V91.60 の機構を流用）。

- 保管物そのものの機微度が下がる
- 送信のたびにマスクする必要がなくなる
- **入力側もマスク済みで Copilot へ渡るため、文例と入力の形が揃う。**
  モデルは「この形の入力をこの形へ訳す」例をそのまま見ることになる

#### 未解決: プレースホルダーの名前空間が衝突する

入力文のマスクは `【N1】` から採番する。コーパスの文例も `【N1】` を含むと、
**同じ記号が別のものを指す**ことになる。

- モデルが文例側の数値を訳文へ持ち込む恐れがある
- 訳文の整合検証（`Test-YakuNumericMaskIntegrity`）が文例由来のトークンを
  「原文に無いトークンの混入」として誤検出する

→ **文例は別の名前空間にする**（`【E1】` 等）。復元も検証も対象外とする。
設計時に確定させる。

#### 残る検討事項

- コーパスの索引をローカルへキャッシュする場合、その置き場所も財務本部内の端末に限られる
- マスク済みでも、複数の文例を組み合わせて文脈が復元できないか（運用開始後に点検する）

### §6-5 配布と更新

§6-4 の決定により、コーパスは配布物から切り離す。残る論点:

| 論点 | 内容 |
| --- | --- |
| コーパスの単位 | 1データベース = 1フォルダ。名前・版・件数・送信可否・マスク済みかを持つ |
| 索引の作り方 | 管理者が1回作って置く / 利用者端末で起動時に作る。**後者は起動を遅くする** |
| 索引のキャッシュ | コーパスの版を鍵にしてローカルへ保存。版が変われば作り直す |
| サイズ感 | 数百〜数千ペアなら、テキストファイル + 索引で足りる見込み |
| 更新 | 資料が増えるたびに追加する運用。担当者を決める |
| 選択 | 利用者がどのデータベースを使うか選べるようにする（§5-B） |

## §12 日英コーパスの作り方（調査結果 2026-08-04）

利用者から「文アライメントが最大の懸念。必ずしもページ対応していない」との指摘を受け、
公開情報を調査した。**結論から言うと、懸念の中心はアライメントではなく PDF 抽出にある。**

### §12-1 最重要の区別: 構築時と実行時で制約がまったく違う

| | 実行時（利用者端末・毎回） | **構築時（管理者端末・1回きり）** |
| --- | --- | --- |
| 環境 | Windows + PowerShell 5.1 | **制約なし。Python も使える** |
| 追加インストール | **不可** | 可 |
| 制約 | §4 のとおり | 機密資料を扱うため**ローカル完結**（クラウドのアライメント/翻訳サービスは不可） |

**§4 の厳しい制約は、コーパス構築には効かない。**
アライメントは既存資料から対訳ファイルを1度作る作業であり、成果物はプレーンテキストである。
アプリはそれを読むだけで、アライメントの道具は一切同梱しない。

→ **アライメントには現時点で最良の道具を使ってよい。**
§6-1（実行時の検索方式）で悩んだ制約と混同しないこと。

### §12-2 アライメントの道具

| 道具 | 方式 | ライセンス | 日本語 | 評価 |
| --- | --- | --- | --- | --- |
| Gale & Church（vanilla） | 文長のみ | — | 可 | 古典。精度は低い |
| Hunalign | 文長 + 自動生成辞書 | — | 可 | 1万文超でメモリを食う |
| Bleualign | 機械翻訳経由 | — | 可 | 事前に機械翻訳が要る |
| **Vecalign** | **文埋め込み + 動的計画法** | **Apache 2.0** | 埋め込み次第 | **第一候補** |
| Bertalign | 文埋め込み（LaBSE） | GPL v3 | **同梱の文分割器が日本語非対応** | 精度は最高水準（F1 0.936）だが要工夫 |

**Vecalign を第一候補とする理由:**

- Apache 2.0（Bertalign は GPL v3）
- **埋め込みを差し替えられる**（float32 のバイナリを渡すだけの仕様）。
  LaBSE でも **ruri v3**（§6-1-2 で調べたもの）でも使える。
  **構築時なので ONNX 変換は不要**で、Python でそのまま動かせる
- 1対多・多対1に加え、**片方にしかない内容（挿入・削除）を明示的に扱う**

Bertalign は精度が高いが、同梱の文分割器の対応言語に日本語が入っていない。
LaBSE 自体は日本語に対応しているため、**日本語の文分割を別途用意して
`is_split=True` で渡せば使える**。ライセンスと合わせて判断する。

### §12-3 ページ対応は前提にしなくてよい（懸念への回答）

**埋め込み方式のアライナは、文書全体を1つの系列として扱う。**
ページ単位・節単位の対応づけを事前に行う必要はない。

| 状況 | 扱えるか |
| --- | --- |
| 日本語1文 ↔ 英語2文（またはその逆） | **扱える** |
| 片方にしかない段落（挿入・削除） | **扱える** |
| ページ区切りの位置が違う | **扱える**（ページという概念を使わない） |
| **節の順序が入れ替わっている** | **苦手**（単調性を仮定するため） |

したがって残る懸念は「順序の入れ替え」だけである。資料別の見込み:

| 資料 | 見込み |
| --- | --- |
| 決算短信・有価証券報告書 | **成立しやすい。** 様式が定まっており順序が保存される |
| 社内 ECM 資料 | **成立しやすい見込み。** 日英が同一資料の版であれば順序は保たれる |
| アニュアルレポート | **最も難しい。** 再構成・意訳が入りやすい。後回しにする |

### §12-4 日本語の文分割が前工程として要る

Vecalign・Bertalign とも**文単位に分割済みの入力**を前提とする。

日本語を `。` だけで切ると、**括弧内・引用・小数点・箇条書き**で誤る。
**財務資料は括弧と小数点が多く、ここは手を抜けない。**

| 道具 | 方式 | 特徴 |
| --- | --- | --- |
| `ja_sentence_segmenter` | 規則ベース | 高速。括弧・引用の扱いが良い |
| `bunkai` | 機械学習 | 高精度だが遅い |
| `fast-bunkai` | bunkai 互換の高速版 | 40〜250倍速いとされる |

### §12-5 本当の難所は PDF 抽出のほうである

調査の結果、**日本語 PDF からのテキスト抽出は、段組み・表・縦書き・図中テキストで
崩れることが知られている。財務資料は表が多く、最も苦手な形にあたる。**

アライメントは崩れたテキストを直せない。**前工程の品質がすべてを決める。**

→ **「PDF から作る」と決め打ちせず、PDF を経由しない経路を先に探す。**

| 資料 | PDF を避ける経路 |
| --- | --- |
| **社内 ECM 資料** | **元の Excel / PowerPoint があるはず。PDF を経由しない。** 本アプリは既に Excel 抽出機構を持っており流用できる |
| 決算短信・有価証券報告書 | XBRL / HTML（EDINET・TDnet） |
| アニュアルレポート | PDF が多い。制作元に元データがないか確認する価値がある |

**元ファイルが手に入るなら、そちらが桁違いに楽で正確である。**
特に社内 ECM 資料は自社の文書であり、元ファイルが残っている可能性が高い。
**効果が最大のコーパス（§10 段階4）が、同時に最も抽出しやすい可能性がある。**

### §12-6 数値一致による自動検品 — このドメインの強み

**アライメント結果を人が全件確認するのは現実的でない。**
財務資料の性質を使って、**人の確認を「怪しいものだけ」に絞る。**

対になった日本語側と英語側から数値を抽出して突き合わせる
（V91.60 の `Convert-YakuNumericUnits` と `Get-YakuNumericAuditExpectations` を流用）。

| 判定 | 扱い |
| --- | --- |
| 双方に数値があり、一致する | **自動採用** |
| 双方に数値があるが、一致しない | **人が確認**（対応がずれている疑い） |
| 数値を含まない | 長さ比・用語集ヒットの一致で補助判定 |

補助指標: 文長比の外れ値、用語集ヒットの一致数、アライナ自身の信頼度。

**工数の山を削る具体策はここである。** 全件確認と、疑わしいものだけの確認では、
作業量が一桁変わりうる。

### §12-7 既製の日英対訳コーパス（金融・IR 分野）は見つからなかった

- この分野は商用の翻訳サービスが中心である。NICT 系の「みんなの自動翻訳＠KI」は
  IR・金融に特化した**翻訳エンジン**であってコーパスではない
- 公開の汎用対訳コーパスは分野が合わない

→ **自社資料から作る前提でよい。** これは制約であると同時に、
**社内の言い回しをそのまま反映できる**という利点でもある（§5-B の狙いそのもの）。

### §12-8 段階1（開示資料でのコーパス作成）の具体化

| 工程 | 内容 | 判断が要る点 |
| --- | --- | --- |
| 1 | **入力の入手経路を決める**（HTML / XBRL / 元ファイル / PDF） | PDF は最後の手段 |
| 2 | テキスト抽出と正規化（表・見出しの扱い） | 表項目を文として扱うか、別粒度にするか（§6-3） |
| 3 | 日本語・英語の文分割 | §12-4 |
| 4 | 埋め込み計算（LaBSE または ruri v3、ローカル） | どちらを使うか |
| 5 | Vecalign でアライメント | — |
| 6 | **数値一致による自動検品**（§12-6） | 閾値をどこに置くか |
| 7 | 人の確認（疑わしいものだけ） | **担当と工数。ここが未定** |
| 8 | 対訳ファイルとして保存（アプリが読む形式） | 形式の設計 |

**工程1と2で躓くと、以降がすべて崩れる。まずここを小さく試す。**

## §13 LiteParse の実測と、アライメント不要案（2026-08-04）

利用者から3点の指摘を受けた。
(a) 社内 ECM 資料の元 Excel は外部リンク画像等があり簡単には抽出できない、
(b) **embedding を使わずに済むならそのほうがよい。
「このフォルダに PDF を入れれば AI が読み取ってくれます」程度の簡潔さでないと配布できない**、
(c) **翻訳で100点は要らない。利用者に負担をかけない方法を探すこと。**

§12 は「元ファイルを使う」「アライメントして対訳を作る」を前提にしていた。
**(a) でその前提が崩れたため、実測して立て直す。**

### §13-1 LiteParse を実際に動かした（決算短信の日英 PDF）

`liteparse` 2.11.0 を導入し、当セッションで共有された決算短信の日本語版・英語版で実測した。

| 項目 | 結果 |
| --- | --- |
| 動作形態 | **完全ローカル。** クラウド送信なし・APIキー不要・LLM不要（Rust実装） |
| ライセンス | オープンソース（run-llama/liteparse） |
| 速度 | **15ページ 0.13秒**（英語版）／14ページ 0.12秒（日本語版） |
| 出力 | Markdown（見出し・表・リストを空間レイアウトから再構成） |
| 導入 | `pip install liteparse`。CLI `lit` が付く |

**結論: 道具としては要件を満たす。** 機密資料をクラウドへ出さずに済み、速度も問題ない。

#### 実務上の注意

- **テキスト層の無いページで OCR が自動起動し、tessdata を GitHub から取得しようとする。**
  当環境では 403 で失敗した。**社内ネットワークでも同様に失敗する可能性が高い。**
  → `--no-ocr` を既定にするか、`--tessdata-path` で事前配置する。
- Python API は `output_format='markdown'` を渡さないと本文が空になる。CLI は `--format markdown`。

### §13-2 **重要な発見: 日本語側の抽出品質が英語側より明確に低い**

| | 英語版 | 日本語版 |
| --- | --- | --- |
| 表 | **Markdown の表として正しく再構成される** | **表として認識されない箇所が多い。** 36%がコードブロック扱い |
| 散文 | きれいに取れる | **きれいに取れる** |
| 症状 | — | 均等割り付け（`上 場 会 社 名`）でカラム境界の推定が狂い、セルが連結して1行になる |

原因は日本語組版の文字間スペースにあると見られる。**これは LiteParse 固有ではなく、
日本語 PDF 全般の難所**（§12-5 の調査と一致する）。

**ただし散文は日英とも良好に取れる。** 実際に取れた対応箇所:

```
JA: 自己資本比率は、前連結会計年度末より0.7ポイント増加の43.3％
    （劣後特約付ローンの資本性考慮後44.0％）となりました。
EN: Equity ratio increased by 0.7 percentage points from the end of the previous
    fiscal year to 43.3% (Percentage after consideration ...)
```

**RAG で本当に欲しいのは散文（言い回し・文体）であり、表は用語集（完全一致置換）の領域である。**
両者の担当を分ければ、日本語側の表抽出が弱いことは致命傷にならない。

### §13-3 アライメントの実測 — 現状の素朴な方法では足りない

抽出した散文から、数値一致でペアを作れるか試した。

| 項目 | 結果 |
| --- | --- |
| 抽出した散文 | 日本語 31文 / 英語 38文 |
| 数値を2件以上含む日本語文 | 14文 |
| 数値2件以上の一致でペアになった | 4件（29%） |
| **うち妥当なペア** | **2件程度。** 残りは表の残骸が偶然一致したもの |

**素朴な数値一致だけでは精度が足りない。**
原因の大半は §13-2（日本語側で表が散文に混入する）である。
アライメントを本気でやるなら、まず**表と散文の分離**を作り込む必要がある。

**そして 15ページの短信1本から取れる使える散文は 20〜30文程度である。**
意味のあるコーパスにするには文書数がかなり要る。

### §13-4 立て直し: **アライメントをやめる**

(b)(c) の要求と §13-3 の実測を合わせると、結論は一つになる。

> **対訳ペアを作るのをやめ、英語側だけをコーパスにする。**

#### なぜ成立するのか

コーパスの目的は「**社内の英語の言い回しを Copilot に見せること**」である。
そのためには、**関連する英語の文が引ければ足りる。日本語との対応づけは要らない。**

日本語の入力から英語のコーパスを引く橋渡しは、**Copilot に英語の検索語を作らせればよい**
（利用者提案の Agentic RAG）。

```
原文（日本語）
  ↓ ① Copilot: 「この内容を英語資料から探すならどんな語で引くか」
検索語（英語）
  ↓ ② アプリ: 英語コーパスを検索（Select-String / BM25）
関連する英語の段落 数件
  ↓ ③ Copilot: 「社内資料ではこう書いている。これに倣って訳せ」
訳文
```

#### これで消えるもの

| 消えるもの | 理由 |
| --- | --- |
| **文アライメント** | 対応づけが要らない |
| **日本語側の抽出品質の問題** | 英語側しか使わない（§13-2 で英語側は良好と実測済み） |
| **embedding モデルとランタイムの配布** | 検索語は Copilot が作る |
| **人によるペアの確認作業** | ペアを作らない |
| 日本語の文分割 | 英語のみ扱う |

**§12 で「最大の工数」と見積もった作業が、そっくり無くなる。**

#### 品質の割り切り

対訳ペアがあれば「この日本語をこう訳す」を直接示せる。英語側だけでは
「こういう調子で書く」までしか示せない。**その差は認める。**
利用者の (c)「100点は要らない」に沿った判断である。

### §13-5 裏付け: 語彙検索でベクトル検索に迫る（しかも財務分野で上回る）

AAAI 2026 で発表された研究（Amazon）が、この方向を支持している。

- LLM に検索語を作らせる**語彙検索**（grep 等）は、
  ベクトル検索を用いた RAG の**9割超の性能**に到達する
- **FinanceBench（財務文書のベンチマーク）では、語彙検索のほうが 6 ポイント上回った**
  （30.40% 対 24.24%）。同一 LLM・同一データセットで、検索器だけを変えた比較

**財務文書は固有名詞・勘定科目・定型表現が多く、字面が一致しやすい。**
このドメインは語彙検索に有利であり、実測でも埋め込みの優位が出ていない。

**embedding を諦めることは、品質を諦めることを意味しない。**

### §13-6 WASM 版の実動作確認（実測 2026-08-04）

**前版で「LiteParse は Python 実装のためアプリへ同梱できない」と書いたのは誤りだった。**
コアは Rust であり、配布形態が4つある。

| 形態 | サイズ | 必要なもの | ライセンス |
| --- | --- | --- | --- |
| **WASM** `@llamaindex/liteparse-wasm` | **5.2 MB** | **ブラウザのみ。npm 依存ゼロ** | Apache-2.0 |
| Windows ネイティブ (napi) | 24.5 MB | Node.js | Apache-2.0 |
| Python (pip) | 32.8 MB | Python | Apache-2.0 |
| Rust CLI (`cargo install`) | 〜25 MB 想定 | ビルド環境 | Apache-2.0 |

WASM パッケージの中身は **3ファイルのみ**。バンドラも不要である。

```
liteparse_wasm.js        37 KB
liteparse_wasm_bg.wasm  5.3 MB
liteparse_wasm.d.ts      15 KB
```

#### 実測結果

Node 22 と Chromium（Edge と同じエンジン）の両方で、決算短信の日英 PDF を解析した。

| 確認項目 | 結果 |
| --- | --- |
| CLI 版との出力一致 | **ページ区切り記号を除き本文が完全一致**（日英とも） |
| ブラウザでの速度 | **初期化 369ms（初回のみ）＋ 解析 692ms / 15ページ** |
| Node での速度 | 445ms / 15ページ（英語）、329ms / 14ページ（日本語） |
| 抽出量 | 英語 30,821字 / 日本語 16,506字 |
| 散文の取得 | `Equity ratio increased by 0.7 percentage points ...` を確認 |
| **外部通信** | **ゼロ。同一オリジンへの2件（`.wasm` と `.pdf`）のみ** |

**「完全ローカル」は実測で裏づけられた。** ブラウザの通信を監視し、
外部への要求が1件も発生しないことを確認している。

#### OCR の扱い（重要）

`isComplex()` は 15ページ中 **10ページを `needsOcr=true`** と判定した。
しかし **OCR を無効にしたまま全15ページからテキストが取れた**
（最小 667字。200字未満のページはゼロ）。

→ **`needsOcr` は保守的な信号であり、抽出の失敗を意味しない。** 図表を含むページで立つと見られる。

**方針: OCR は既定で無効にし、`needsOcr` は使わない。抽出できた文字数で判断する。**
これにより §13-1 で問題になった **tessdata の自動ダウンロード
（社内網で失敗しうる）を経路ごと回避できる。**

#### API

```js
import init, { LiteParse } from './pkg/liteparse_wasm.js';
await init();                                   // .wasm を同一オリジンから取得
const lp = new LiteParse({ outputFormat: 'markdown', ocrEnabled: false, quiet: true });
const r  = await lp.parse(new Uint8Array(pdfBytes));
const md = r.pages.map(p => p.markdown || '').join('\n\n');
```

### §13-7 配布の姿（WASM 前提）

**このアプリには必要なものが既に揃っている。**

- ローカル HTTP サーバー（PowerShell の `HttpListener`）
- ローカル Web UI（`www/` の HTML/CSS/JS）
- **Edge が必須要件**（CDP で既に使用）

したがって **PDF の解析をアプリ自身の画面の中で、ブラウザの WASM で実行できる。**

```
利用者: アプリ画面へ PDF をドロップ（または参考資料フォルダを指定）
   ↓  ブラウザ内の WASM が解析（完全ローカル・外部通信なし）
Markdown
   ↓  localhost の PowerShell サーバーへ POST
アプリが段落単位で索引を作り、参考資料フォルダへ保存
   ↓
翻訳時: Copilot が英語の検索語を作る → 索引を引く → 文例を注入
```

| 論点 | 結論 |
| --- | --- |
| Python | **不要** |
| 実行ファイル(.exe) | **不要。** 社内では持ち込みに承認が要ることが多く、実務上の利点が大きい |
| インストール作業 | **なし** |
| 管理者による事前変換 | **なし。** 利用者の操作だけで完結する |
| 配布物の増加 | **5.2 MB**（3ファイル）。`bootstrap.ps1` の manifest と SHA-256 検証にそのまま乗る |

**実装上の要点:** PowerShell の `HttpListener` が `.wasm` を
`Content-Type: application/wasm` で配信する必要がある
（`WebAssembly.instantiateStreaming` のため）。
配信できない場合は `ArrayBuffer` 経由の初期化へ落とせるので致命的ではない。

#### 取り込んだ結果の置き場所

Markdown と索引は **財務本部限定の共有フォルダ**（`corpus_root`、§6-4）へ置く。
**誰か1人が取り込めば全員が使える。** 各自が取り込む必要はない。

#### 英語側コーパスにもマスキングが要る場合がある

コーパスは英語側だけだが、**出どころによって扱いが違う。**

| コーパス | マスキング |
| --- | --- |
| 英文短信・AR・有報 | **不要**（開示済み） |
| **過去 ECM 資料の英訳** | **必要**（開示前の社内文書。§6-4 の決定） |

**新しい作業が1つ増える。** V91.60 の数値マスキングは日本語の原文を前提としており、
非マスク対象の判定（年号・「一株当たり」等）が日本語の表記に依存している。
**英語側のマスキングには、英語の表記に対する判定（`FY2026`、`per share` 等）が要る。**

→ **段階1を開示資料から始めれば、この作業を後回しにできる。**

### §13-8 更新した進め方

| 段階 | 内容 | 前提 |
| --- | --- | --- |
| 1 | **WASM 版 LiteParse をアプリへ組み込む。** PDF を Markdown 化して保存する経路 | なし |
| 2 | 段落単位の索引と、素朴な語彙検索。文例注入と効果測定 | 段階1 |
| 3 | Copilot に検索語を作らせる（Agentic）。段階2との比較 | 段階2 |
| 4 | 参考資料フォルダの UI（選択・件数表示・未取込の通知） | 段階2 |
| 5 | **英語側の数値マスキング。** 過去 ECM 英訳をコーパスへ追加 | 段階1〜3 |
| 6 | FULL/BRIEF の接続分離 | 段階3 |
| 保留 | 日本語側コーパス・対訳ペア・embedding | 段階3 の結果を見て判断 |

**段階1〜4 は開示資料だけで進められ、マスキングを必要としない。**

**段階1〜3 で、アライメントにも embedding にも触れずに効果を測れる。**
そこで足りなければ、そのとき初めて対訳ペアを検討する。
