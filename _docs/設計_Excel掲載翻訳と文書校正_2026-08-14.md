## 0. この設計が目指す利用体験

この文書は利用体験と実装契約を一冊にまとめている。機能の全体像を確認する場合は0〜3章、画面を確認する場合は12章、実装順を確認する場合は16・18・19章、まだ決まっていないことを確認する場合は21章を先に読む。4〜15章は実装者向けの詳細である。

利用者向け画面・説明に現れ得る内部語は §0.4 に対応表を置く。保存schemaや実装だけで使い通常画面へ出さない識別子は、この表の対象外とする。

### 0.1 初めて使う人から見たYakuLingo

YakuLingoは、日本語を英語へ変換して終わるツールではない。原文と英訳を見比べ、用語や数字を確認し、Excelでは実際の印刷結果まで確かめるための翻訳作業アプリである。

利用者にCAT等の専門知識を要求しない。開始画面では次の2つだけを示す。

1. `文章を貼り付けて翻訳`
2. `Word・Excelを取り込んで翻訳`

現行の開始画面にはこの2つ以外に、`過去の日本語版・英語版PDFを読み込む`（対訳の取込）、
`前回の資料をもとに、今回の分だけ訳す`（前版からの流用）、再開一覧がある（`www/cat.html`）。
本設計はこれらを廃止しない。主入口を上の2つに絞り、残りは主入口の下の副次操作として
まとめる。前版からの流用と本設計の原本差し替えの関係は §4.1.1 に書く。

翻訳後に、入力形式と作業状況に応じて必要な機能を段階的に表示する。

```text
文章またはファイルを入れる
-> 翻訳先を確認して翻訳
-> 原文と訳文を見比べる
-> 必要な箇所を修正して確認
-> Excelだけ、セルへの入れ方とPDFを確認
-> 文書全体の用語・数字・内容のつながりを確認
-> コピー、確認用ファイル出力、または作業保存
```

最初から全機能、全警告、内部状態を並べない。各画面は `次に行うこと` を一つ示し、詳細な根拠や設定は必要な人だけが開ける。

### 0.2 入力形式ごとの対象範囲

この表の内部語（TM、QC等）は §0.4 の対応表で読み替える。

| 入力 | 翻訳・日英確認 | 用語・TM候補・数字QC | 文書全体校正 | Excelへの配置 | Excel由来PDF確認 |
| --- | --- | --- | --- | --- | --- |
| 貼り付け文章 | 対象 | 対象 | 複数文なら任意 | 対象外 | 対象外 |
| Word（`.docx`） | 対象 | 対象 | 対象 | 対象外 | 本設計の初期対象外 |
| Excel（`.xlsx` / `.xlsm`） | 対象 | 対象 | 対象 | 対象 | 対象 |
| CSV（`.csv`） | 対象 | 対象 | 対象 | 対象外 | 対象外 |

CSVは現行 `Get-YakuCatOutputEligibility` がExcelと同じ書出し経路に載せている（`V91.61/app/src/CatProject.ps1`）が、列幅、結合、印刷設定、図形を持たない。配置とPDFの対象から外し、翻訳・用語・QC・文書校正だけを共有する。ファイル選択欄（`www/cat.html` の `accept`）にCSVを追加するかはPhase 0で決める。

本設計のレイアウト、印刷設定、PDF掲載完全性はExcelを初期対象とする。WordのPDF体裁確認を同時に約束しない。貼り付け文章やWord、CSVでも、翻訳、用語、TM候補、決定論QC、文書全体校正は同じ基盤を使用する。

### 0.3 初見利用者へ必ず説明すること

- Copilotが作った訳は未確認であり、コピーしても確認済みにはならない
- `原文と照合して確認済みにする` と `確認済み訳を翻訳メモリへ追加` は別の操作であり、後者を選んだ訳だけが翻訳メモリへ登録される
- 貼り付け文章は復旧可能な一時作業としてこの端末へ保存され、明示保存しなければ最終更新から7日後に削除される。結果画面から今すぐ削除できる
- 取り込んだWord・Excelの原本コピー、確認用PDF、抽出索引はこの端末の翻訳作業内に保存され、作業一覧から削除できる
- 一時作業を削除しても、別途翻訳メモリへ登録した原文・訳文は自動では消えない。削除時に残すか取り消すかを選ぶ
- 数値は送信前に伏せるが、本文、会社名、人名、製品名等はCopilotへ送られる。Excel・Word・PDFファイルそのものは送らない
- Excelの余白、倍率、印刷範囲等は、利用者が選ぶまで元の設定を変えない
- PDFから文字を読み取れない箇所は欠落と断定せず、画面確認を依頼する
- AIの確認事項が残っていても確認用出力は可能だが、原文対応不能や書戻し不完全等の安全上の問題は出力を停止する

### 0.4 文書内の内部語と画面表示

この設計書は実装用のため内部語を使うが、通常画面には右列の言葉を表示する。

| 内部語 | 利用者向け表示・意味 |
| --- | --- |
| CAT | 表示しない。原文と訳文を見比べて確認する作業画面 |
| TM / Translation Memory | 翻訳メモリ。人が確認した過去訳を今後の候補に使う仕組み |
| QC | 数字、単位、用語、未訳等の機械確認 |
| 決定論QC | 数え上げと突き合わせだけで判定できるQC。AIを使わない |
| Segment | 翻訳する文章 |
| CanonicalTranslation | 内容を確認する訳文 |
| PublicationVariant | Excelに入れる訳文 |
| PlacementPlan | Excelへの配置 |
| RenderProfile | PDFを作るときの印刷設定の組。表示は `確認基準` |
| finding | 確認事項 |
| coverage | どこまで見終えたか。件数ではなく範囲 |
| stale | 元データが変わったため更新が必要 |
| source_faithful | 元の印刷設定をそのまま使用 |
| cannot_fit | 正確さを保ったままでは、その幅に収まらない |
| render_missing | PDFに載っていないと確定した |
| render_unverified | PDFから読み取れず、載ったか確定できない |
| waiver | 問題を確認したうえで、このまま使用 |
| rebase | 日本語版の差し替えに合わせて、既存の訳と配置を対応付け直すこと |
| transient project | 一時作業 |
| saved project | 保存した作業 |
| DRAFT | 実装内部と出力ファイル名の接頭辞。画面では確認状態に応じた `確認用ファイル` |

### 0.5 成果物の位置付け

- 貼り付け文章: 訳文コピー、または保存した翻訳作業
- Word・Excel: 確認状態付きの翻訳作業と `確認用ファイル`
- Excel: 上記に加え、配置・印刷結果を確認するPDF

実装内部でDRAFTと呼ぶ確認用ファイルや確認用PDFは、翻訳内容と掲載状態を確認するための成果物である。通常画面ではcoverageとfinding状態に応じて `確認用ファイル`、`確認用ファイル（未処理の確認事項あり）`、`確認用ファイル（確認できない範囲あり）` を出し分ける。いずれも組織上・法的な正式承認をアプリが付与するものではない。最終的にどのファイルを使用するかは人が判断する。

### 0.6 Excel翻訳の標準的な流れ

1. Excelを選ぶ
   - アプリは原本を変更せず、翻訳作業用コピーを作る
2. 翻訳する
   - 文章が複数セルへ分かれている可能性を表示し、必要なら人が結合・解除する
3. 内容を確認する
   - 日本語と英訳を見比べ、数字、用語、条件、否定等を確認する
4. Excelへの配置を確認する
   - そのまま入れるか、右の空白を使うか、下セルへ分けるか、略語候補を使うかを人が選ぶ
5. PDFを更新する
   - 既定では元の印刷設定を使い、切れ、重なり、印刷範囲外を確認する
6. 文書全体を確認する
   - 訳語、略語、数字、相互参照、英語文書単独の矛盾を確認する
7. 出力する
   - 未確認事項が残れば一覧を示し、確認用ファイルを出すか、修正を続けるかを人が選ぶ

どの段階でも、アプリは人の訳・配置・判断を黙って置き換えない。原本が差し替えられた場合も、以前の人訳を候補として残し、再確認が必要な箇所だけを示す。

### 0.7 貼り付け文章の最短の流れ

Excelの流れは7段階あるが、メールやチャットを訳すだけの人はここまで通らない。
起動直後の着地点は貼り付け欄で、そこから最短2操作で訳文にたどり着く。

```text
起動する（貼り付け欄に入力位置がある）
-> 貼る
-> Ctrl+Enter（翻訳先が自動で決まらないときだけ、先に英語／日本語を選ぶ）
-> 原文と訳文が並んだ確認画面
-> 「訳文をコピー」して終わり
```

この経路で作られる作業は一時作業であり、コピーしただけでは確認済みにも翻訳メモリ登録にもならない（§2.6）。用語、翻訳メモリ候補、数字QC、文書全体校正は、必要になったときに同じ画面でそのまま使える。

## 1. 結論

YakuLingoは、セル単位の翻訳ツールから、次の3つを区別して扱う翻訳作業環境へ拡張する。

1. **意味の正本**: 原文の文章単位と、情報を保った基準訳
2. **掲載方法**: 基準訳を、略語、簡潔表現、右側空白、下側セルへの分割等でExcelへ配置する計画
3. **読者に届く結果**: Excelから実際に出力されたPDF

```text
SourceArtifact
  -> SemanticSegment + CanonicalTranslation
      -> PlacementPlan + PublicationVariant
          -> RenderedArtifact (PDF)
              -> DocumentReview + HumanDecision
```

設計の中心は「セルに文字が入っているか」ではない。日本語原文の情報が、最終PDFを読む人へ届いているかである。

ただし、アプリが意味、略語、体裁、リスクを最終決定してはならない。自動化するのは測定、検出、比較、候補作成、根拠の整理までとし、採用と最終判断は人に残す。

## 2. 今回確定する設計判断

### 2.1 既存CATを中核にする

新しい文章ブロック基盤を別に作らない。現行の `Segment` を意味単位として拡張する。

現行にはすでに以下がある。

- 同列の連続セルを文章として自動結合する
- 利用者が隣接セグメントを結合・解除する
- 元セルを `BlockIds` と `Cells` で保持する
- 原文・訳文hash、原文revision、QC契約、用語snapshotで確認の鮮度を判定する
- 訳文編集、用語変更、結合・分割でQCと確認を失効させる
- 出力時に原本を再読込し、元セルとの対応を再検証する

根拠:

- `V91.61/app/src/CellSegments.ps1`
- `V91.61/app/src/CatProject.ps1`
- `V91.61/app/src/SheetLayout.ps1`

### 2.2 意味上の結合と掲載セルへの分配を分ける

現行の結合セグメントは、出力時に原文セルの文字数を重みとして訳文を再分割する。この方法は初期候補には使えるが、人が調整した最終配置を表現できない。

今後は次を分離する。

- `Segment.Cells`: 原文が存在したセル。意味単位を構成する
- `PlacementPlan.Destinations`: 英訳を実際に書くセルと文字列
- `PlacementPlan.DisplayRegions`: 値は書かないが、右への表示上のはみ出しに使用する空白領域

右側の空白セルは原文の一部ではないため、`Segment.Cells` へ追加しない。

### 2.3 基準訳と掲載訳は必要時だけ分ける

常に二重の訳文を管理すると、確認負担が増える。通常は基準訳をそのまま掲載訳として扱う。

略語、電文調、句の組替え等、意味のある表現変更が必要な場合だけ `PublicationVariant` を作る疎なモデルとする。

- `CanonicalTranslation`: 情報保持を確認する基準訳
- `PublicationVariant`: 特定の文書・配置向け掲載訳
- `PlacementPlan`: 掲載訳をセルへ分配する方法

翻訳メモリへ自動登録するのは、人が確認した `CanonicalTranslation` だけとする。掲載訳、分割片、未承認略語を通常の翻訳メモリへ混入させない。

### 2.4 PDFは見た目の最終確認対象だが、唯一の機械判定根拠ではない

PDFは読者に届く成果物として最終確認する。一方で、PDFのテキスト抽出はフォント、合字、図形、読み順によって失敗する。

したがって、PDF抽出に見つからないだけで「印刷欠落」と断定しない。

- 高確度で対応できた欠落: `render_missing`
- 抽出または対応が不確実: `render_unverified`
- 画像上で人が確認した: 人間確認イベントを記録

### 2.5 製品間の実行時依存を作らない

ReportBinderとPdfKoseiAssistをYakuLingoから起動したり、各製品のサーバーAPIへ依存したりしない。

- ReportBinderからはExcel PDF出力、ウォッチドッグ、PDF表示・差分の設計パターンを移植する
- PdfKoseiAssistからは観点別校正、根拠契約、coverage、finding統合に加え、`masked-text` の送信方式も参考にして移植する

共有巨大フレームワークは作らず、YakuLingo内の小さい責務別モジュールとして実装する。

#### 2.5.1 制御可能なPDF描画部品は現行YakuLingoに無い

**現行YakuLingoはPDF.jsを持っていない。** PDFから文字を取る部品は
`www/assets/pdf-extract.js` と `www/assets/vendor/liteparse`（Rust/WASM）で、
これは**抽出専用であり、ページを描いて見せる機能はない**。
ReportBinderが持つ `app/web/pdfjs/pdf.min.mjs` に相当するものは無い。

実装方式は、ローカル同梱したPDF.jsを使う方式へ決定した。保護PDFは既存session headerを付けたsame-origin fetchで取得し、`application/pdf`、Range 200/206、`no-store`、`.mjs` MIMEを専用endpointで扱う。既定のXFO/CSPを全体で緩和せず、取得したbytesはblob URLで表示する。native viewer用の無認証URLや一回限りtokenは使用しない。

PDF文字抽出は、PDF.jsの専用workerで行う。workerはPDF bytesと抽出結果だけを扱い、Copilot送信口へ接続しない。入力bytes上限・page上限を持ち、文書本体・PDF・座標はローカルに留める。既存WASM取込は別用途であり、同じ `cat.html?import=1` をPDF校正の隔離境界とはみなさない。

抽出の正本はコードファイル名ではなくversion付き `PdfTextExtractor` 契約とする。1つのRenderSnapshotでは1つのextractor結果だけを使う。LiteParseがpage box・rotationを含む十分な座標を公開できる場合は既存adapterを拡張し、足りなければvendorした描画部品の抽出実装へ置き換える。同じsnapshotで異なるextractorの本文・座標を混用しない。

PDF表示と抽出器の決定事項は§8.5へ集約する。将来抽出器を置き換える場合も、同一RenderSnapshot内で異なる抽出器結果を混用しない。

これらの製品名は設計資料と開発者向け参照にだけ使用する。利用者向け画面、エラー、進捗、成果物名、QAレポートには表示せず、`PDF確認`、`文書全体の校正`、`元の印刷設定` のように機能と結果だけを示す。

### 2.6 貼り付け翻訳もCATへ一本化する

`その場で翻訳` という別モード、別job、別結果画面は廃止する。貼り付けは入力形式であって別の翻訳製品ではない。短文・長文・Word・Excelを、開始時から同じCAT project、用語、TM候補、数値マスク、QC、確認状態で扱う。

現状は `/quick` と `/cat` が同じ `cat.html` を返す一方、画面内に保存しないQuick経路とCAT保存経路が併存し、`quick.js` のQuick job、`/api/quick/jobs`、ツアー説明も食い違っている。入口だけ統合済みに見えて処理契約が二重であるため、機能活用と初回理解の妨げになっている。

実装で確認した現状（`V91.61/app`）:

- `Server.ps1` の `GET /quick` と `GET /cat` はどちらも `cat.html` を返す
- 同じ `quick-form` に主ボタンが2つある。`quick-submit` は `POST /api/quick/jobs`
  （保存せず、用語も過去訳も参照しない）、`quick-save-submit` は `POST /api/cat/open`
  （作業として保存し確認画面へ移る）
- 画面の説明は `この画面に訳を出します。作業や翻訳メモリには残しません。`
- 一方 `tour.js` は `押すと1行ずつ確認する画面に移り、保存されます。` と案内する。
  主ボタンの実際の動きと逆である
- `Start-YakuTranslationJob` の `-Kind` は `text|quick|revise|shorten|cat`。
  Quick経路の廃止は、この `quick` kindと `CachePolicy 'none'` /
  `ReferencePolicy 'none'` の組も併せて外すことを意味する
- 保護済みprompt側の `Kind`（`text|revision|shorten|cat|corpus|alignment|selftest`）は
  別のValidateSetであり、`quick` は元から無い。混同しない

ただし、貼ってすぐ訳してコピーする短時間利用は残す。

```text
文章を貼り付ける
-> 翻訳先を確認
-> 「英語に訳して確認」または「日本語に訳して確認」
-> CAT projectを作り、同じ操作で翻訳開始
-> 原文・訳文の確認画面
```

貼付け後は1操作、言語方向が不明な場合でも方向選択を含め2操作以内で開始する。貼付け、初期focus、`Ctrl+Enter`、方向判定、Copilot準備前予約、取消、再試行、長文分割、全文コピー、改行復元をCAT入口へ移す。

`Ctrl+Enter` は現在2つの意味を持つ。貼付け欄では「送信」、確認画面では「確認して次へ」である（`www/cat.html` のキー操作一覧、`quick.js`）。一本化しても意味は統合しない。**入力位置がどこにあるかで決める。**

| 入力位置 | `Ctrl+Enter` |
| --- | --- |
| 開始画面の貼付け欄 | 翻訳を開始する |
| 確認画面の訳文欄 | この行を確認して次の行へ |

同じ画面に両方が同時に存在する状態を作らない。開始画面から確認画面へ移った時点で、貼付け欄は画面から外す。

確認操作の名前は `確認して次へ` に統一し、原文と訳文の照合済み状態だけを更新する。翻訳メモリ登録は `確認済み訳を翻訳メモリへ追加` という別操作にする。一括操作を置く場合も `確認して、翻訳メモリにも追加` と副作用を常時表示し、既定で黙って登録しない。

機械訳生成、ローカル保存、人の確認、TM登録を別状態にする。翻訳完了、コピー、人の確認だけではTM登録済みにしない。現在の原文・訳文に対するQCが有効で、利用者が確認済み訳を明示登録した場合だけTM outboxを作る。

貼付け開始projectは通常CATと同じモデル・APIを使い、`lifecycle: transient | saved | deleting | deleted` だけを持つ。`transient` も用語、TM候補、QC、文書校正を利用できるためQuickの再実装ではない。通常の再開一覧を埋めず、`この作業を残す` で `saved` へ昇格できる。`コピーして終了` または明示された保持期間後に削除し、コピーだけではTMへ登録しない。`deleted` は削除完了を示す最小tombstoneだけを残し、project本文・訳文・一時artifactは保持しない。tombstoneは現行 `Get-YakuCatTombstonePath`（`V91.61/app/src/CatProject.ps1`）の仕組みを再利用し、別形式を新設しない。

旧 `/quick` は `/cat` の互換aliasとして残しても別挙動を持たせない。新規翻訳は `/api/quick/jobs` を使用しない。旧タブには移行期間だけ再読込案内を返し、旧Quick jobをshimで再現しない。

project lifecycleとsegment確認・TM登録は独立させる。

| 操作 | project lifecycle | 確認・TM |
| --- | --- | --- |
| 貼付け開始 | `transient` | 未確認、TM登録なし |
| 訳文をコピー | `transient` | 状態を変えない |
| 確認して次へ | `transient` のまま | QCと確認eventをcommit。TM登録なし |
| 確認済み訳を翻訳メモリへ追加 | `transient` のまま | TM登録eventとoutboxをcommit後に同期 |
| この作業を残す | `saved` | 確認状態を変えない |
| コピーして終了 | `deleting -> deleted` | 未同期TM outboxがあれば削除せず再試行表示 |

transient削除後も、同期済みTM記録は残る。確認済み化だけで再開一覧へ昇格させない。削除時は `翻訳メモリの訳を残して作業を削除` と `翻訳メモリ登録を取り消して作業を削除` を明示選択させ、残る原文・訳文を説明する。各遷移は `expected_revision` によるCASとし、実行中jobまたは開いている編集tabがある間は自動削除しない。誤操作や翌日の再開に備え、既定保持時間は最終更新から7日間とし、開始時とproject close後にcleanupする。画面に `一時作業は○月○日に削除されます` と表示し、`この作業を残す` と `今すぐ削除` を用意する。

削除は、本文ディレクトリを直接消す一操作にはしない。project lock内でdisk manifestの `revision + active_generation_id + lifecycle + retention_until` を再検査し、まず `lifecycle=deleting` とTM保持方針を新generationへCAS commitする。以後の保存、期限延長、新しい編集lease、job開始を拒否してから、必要なTM tombstoneを同期的に作成し、artifactを削除して既存tombstoneへ移す。途中失敗は `deleting` として再開可能にし、cleanupが読んだ後に保存・延長されたprojectを削除しない。編集leaseはプロセス内の期限付き情報なので、サーバー再起動直後は少なくともlease TTLと再接続猶予が過ぎるまで期限cleanupを開始しない。開いたままのタブが新しいserverへpresenceを再送できる前に一時作業を削除しない。

TM登録取消しを選んだ場合は、対象TM event IDに対する取消eventと必要最小限のTM識別子だけをproject本文から独立したoutboxへ原子的に移し、project本文・訳文・artifactは直ちに削除できるようにする。取消し同期が未完なら `翻訳メモリの削除処理中` と表示し、「すべて削除済み」と表示しない。TMを残す場合は同期済みの最小TM記録だけを残し、project artifactと未同期promptを削除する。

## 3. 解くべき実務上の問題

### 3.1 Excelの変則的な文章配置

次の使い方を正規の入力として受け止める。

- 右側を空白にして、セル値を表示上だけ横へはみ出させる
- 収まらない文章の続きを下のセルへ手入力する
- セル結合を使わず、複数セルを見た目上の一段落として使う
- 見た目は空でも、数式、罫線、入力規則、非表示情報等の意味を持つセルがある
- 結合、折り返し、縮小表示、固定行高、印刷倍率を混在させる

### 3.2 「短くする」による情報欠落

長さだけを目標にすると、Copilotは条件、限定、原因、主体等を削ることがある。一方、印刷されなければ情報は読者へ届かない。

必要なのは「削除禁止」だけではなく、次の候補を比較する収容最適化である。

- 冗長表現の簡潔化
- 承認済み略語
- 文書内で定義済みの略語
- 句・節単位の下セル分割
- 右側の表示領域利用
- 折り返し、行高、フォント等の体裁調整
- 正確性を保ったまま収容できないという判断

### 3.3 単文を越えた品質

個々の訳が正しくても、文書全体では次の問題が起こる。

- 同じ概念、名称、役職、製品、会計用語の訳語揺れ
- 同じ略語を異なる意味で使用
- 略語を定義前に使用
- 表、見出し、本文、注記の数値や名称が不一致
- `above`、`below`、`the following table` 等の参照先が存在しない
- 英語文書単独で主語、参照先、期間、増減方向が矛盾する
- Excelには存在するが、PDFでは切れ、重なり、印刷範囲外で消える

### 4.1 SourceInventoryService

原本から次を不変スナップショットとして取得する。

- ブック・シート識別子
- セル番地、値、数式有無、型
- 結合範囲
- 列幅、行高、非表示行列
- wrap、shrink-to-fit、配置、フォント名・サイズ・太字
- 罫線、塗り、保護、入力規則の有無
- 印刷範囲、印刷タイトル、行列改ページ、向き、倍率、用紙サイズ、余白
- 印刷順序、グリッド線、行列見出し、白黒、ドラフト、先頭ページ番号
- ヘッダー／フッター文字列・画像参照、printer settings relationship
- 図形、グラフ等の既存対応要素

原本は変更しない。プレビュー、PDF、出力は必ずプロジェクト専用コピーから作る。

印刷設定fingerprintは生XMLのバイト列ではなく意味値を正規化して計算する。現行 `Get-YakuSheetLayoutFromXlsx` は構造プレビュー用の限定情報であり、SourceInventoryの正本にはしない。新inventoryはworkbook relationshipsと各partを辿り、取得不能項目を `unknown` として保持する。

実装追跡: SourceSnapshotの不変原本copy、block/cell構造・layout・OOXML印刷依存のhashは実装済みである。全sheetの図形、chart/textbox、入力規則、完全な印刷領域を一つのinventory artifactとして列挙する部分は未完了であり、現状のhashを完成版SourceInventoryと呼ばない。

### 4.1.1 原本差し替えと3-way rebase

原本差し替えは既存ファイルへの上書きではなく、新しい不変 `SourceSnapshot` の採用として扱う。

```text
Base    現在採用中の日本語原本snapshot
Ours    Base上で人が作った基準訳・掲載訳・配置・判断
Theirs  新しく受け取った日本語Excel
```

`SourceRebaseService` はBase→Theirsのblock・layout・print差分と、Base→Oursの作業状態を3-wayで対応付ける。現在projectを直接変更せず、最初に読み取り専用 `RebasePlan` を作る。

対応順は、現行 `Resolve-YakuCatExportBlocks`（`V91.61/app/src/CatProject.ps1`）の実装と同じ順にする。実装は次の順で確定している。

1. 同名かつ両側のCodeNameが矛盾しないシート
2. Worksheet `CodeName` の一意一致（改名されたシート）
3. CodeNameが取れない場合だけ、一意な原文blockをアンカーにした最長増加部分列で、
   両側カバレッジ0.8以上かつアンカー3件以上、しかも最上位が単独である候補
4. 一意な原文blockをアンカーにしたblock単位の順序対応
5. 一意でなければ `ambiguous` として停止

rebaseのために対応順を独自に変えない。**同じシート対応・アンカー対応を2か所に実装しない。** 現行関数から純粋な対応付けprimitiveを抽出し、出力側とrebase側が共有する。

CodeName単独一致はsheet候補の絞込みにしか使わない。別ブックで `Sheet1` 等が再利用され得るため、変更block、PlacementPlan、確認状態の自動transferには親SourceSnapshotのlineage、または一意な内容anchorとsemantic contextの追加証拠を必須とする。追加証拠がなければ `needs_review` とする。

- 出力側の `Resolve-YakuCatExportBlocks` は、従来どおりexactな書戻し安全ゲートとして使用する
- rebase側は共有primitiveを使うが、変更、数値変更、split、merge等を分類する別契約を持つ
- exact対応専用の `Resolve-YakuCatExportBlocks` 全体を、そのまま変更blockのrebase engineとして呼ばない
- rebase結果があっても、出力直前のexactゲートを省略・緩和しない

PDFの完全一致は、上のどれとも独立した**補助証拠**であり、単独では対応を確定させない。

番地一致だけで同じ文章と判断しない。現行 `Resolve-YakuCatExportBlocks` の完全一致・fail closed条件は出力安全ゲートとして維持し、rebase推測で迂回しない。

#### 既存の「前回の資料をもとに、今回の分だけ訳す」との関係

現行には近い機能が既にある。`POST /api/cat/from-prior-version` →
`New-YakuCatProjectFromPriorVersion`（`V91.61/app/src/VersionUpdate.ps1`）である。
Phase 4まではこの入口を維持する。Phase 4の入口で利用実績を確認してUI統合の可否を決めるが、処理契約は次の点で異なる。

| | 既存 `from-prior-version` | 本設計の原本差し替え |
| --- | --- | --- |
| 入力 | 旧日本語・旧英語・新日本語を**貼り付けたテキスト** | 新しい**Excelファイル**（Wordは初期対象外） |
| 結果 | **新しいproject**を作る | 既存projectのsourceを差し替える |
| 対応単位 | 1行（1段落）の日英対 | シート、block、segment、配置 |
| 体裁・印刷設定 | 扱わない | 扱う |
| 旧訳の自動流用 | `PriorEvidence` が `verified_release` または `verified_internal` のときだけ | §4.1.1 の変更種別表による |

**既存の `PriorEvidence` ゲートを弱めない。** 出所が確認されていない旧訳を自動で
流用しないという条件は、本設計の3-way rebaseでも維持する。旧英語の出所が
`reference_only` または `none` の場合、`完全一致` であっても基準訳の自動再利用は
行わず、旧訳候補として示すだけにする。

rebase時のOursには、現在project内の訳の来歴を次のenumで付ける。
`reviewed_current_project | verified_release | verified_internal | reference_only | machine_unreviewed | none`。
現在のdependency fingerprintに一致するtranslation確認eventを持つ基準訳だけを
`reviewed_current_project` とする。TM候補を挿入しただけの訳、Copilot生成だけの訳、
失効した確認は自動再利用しない。既存 `PriorEvidence` はこのenumへ明示変換し、
経路をUI統合しても自動再利用ゲートは維持する。

`Try-YakuVersionNumericUpdate` も既存の実装をそのまま呼ぶ。引数の順は
`(PriorJa, PriorEn, CurrentJa)` であり、本設計の
`(Base日本語, Oursの現在英訳, Theirs日本語)` はこれに対応する。

変更種別と扱い:

| 種別 | 扱い |
| --- | --- |
| 完全一致 | 原文、semantic context、用語・QC依存が一致する場合だけ基準訳と行ローカル確認を再利用可能 |
| 移動のみ | semantic contextが一致すれば訳を再利用し、配置・PDFを再確認。文脈変更なら旧訳候補 |
| 数値のみ | `Try-YakuVersionNumericUpdate(Base日本語, Oursの現在英訳, Theirs日本語)` が安全条件を満たす場合だけ未確認候補 |
| 文言変更 | 人が編集した現訳を旧訳候補として保護し、active訳はstale |
| 追加 | 新規未訳 |
| 削除 | 訳と配置をarchiveし、確認済みなら削除確認を要求 |
| split / merge / ambiguous | 自動確定せず構造競合として人へ戻す |
| layout / printのみ | 意味確認を維持し、影響する配置・PDF確認を失効 |

新版の原本設定を正として読み直し、旧版の印刷設定や空白セル利用を無条件に持ち越さない。人の訳を黙って削除せず、未解決競合を残して作業を続けられるようにする。ただし誤掲載・欠落につながる競合が残る範囲はDRAFT Excel出力対象にしない。

### 4.2 SemanticSegmentService

現行 `Segment` を意味の正本として保つ。自動グループ化は候補であり、人が修正できることを前提とする。

結合・分割時は次を行う。

- `source_revision` を更新
- 基準訳、掲載訳、QC、関連承認を失効
- 元セルと判断根拠を保持
- 待機中の旧Copilot結果を適用しない

### 4.3 PlacementService

意味単位とExcelへの書込みを切り離す。

初期対応モード:

- `anchor_spill_right`: 先頭セルへ書き、右側空白を表示領域として利用
- `split_down`: 複数セルへ明示的に句・節を分配
- `existing_wrap`: 既存折り返し設定を利用
- `manual`: 人がセル別文字列を確定

後続候補:

- 行高変更
- フォント変更
- 列幅変更
- 印刷設定変更

列幅・印刷設定は他の領域へ波及するため、初期段階では自動提案も適用もしない。

### 4.4 RenderJobService

Excel COMは同期停止し得るため、ブラウザ用PowerShellサーバーの外部プロセスで動かす。

処理:

1. 原本hashとproject revisionを確認
2. 一時コピーを作成
3. 全PlacementPlanのdestination、display corridor、結合領域、保護、入力規則、array/spill範囲のpreconditionを一括検証してから適用
4. 書戻し後のExcel構造を再読込して検証
5. Excel `ExportAsFixedFormat` でPDF化
6. PDF署名、サイズ、ページ数、読取可否を検証
7. `RenderSnapshot` として公開

preconditionは最初の書込み前に全件検査し、1件でも不一致なら一時コピーを破棄する。書戻し後の再読込検証が成功するまで、DRAFT ExcelとPDFを成果物として公開しない。

一時コピーを `UpdateLinks=0`、`AutomationSecurity=ForceDisable`、`DisplayAlerts=false` で開き、マクロを実行せず外部リンクを更新しない。元ファイルへ保存しない。失敗時に終了してよいのはYakuLingoが起動しPIDと開始時刻を記録したExcelだけとする。

`ExportAsFixedFormat` は `IgnorePrintAreas=false` 等の引数をcontract versionで固定する。Excel version、font、printer環境はRenderSnapshotの入力fingerprintへ含める。

Excelの所有PIDと開始時刻を記録し、外部ウォッチドッグはYakuLingoが起動したExcelだけを対象にする。自動再試行は新しいExcelプロセスで1回までとする。

Excelで生成できない場合、別レンダラーへ黙って切り替えない。利用者がExcelから出力したPDFを読み込む代替経路を用意する。

#### 4.4.1 PDF体裁はRenderProfileとして分離する

ReportBinderのExcel PDF化は、単なる原本プレビューではない。作業用コピーに対して次を適用している。

- 上下余白0.8cm、左右余白1.2cm
- 水平方向中央、垂直方向は中央にしない
- `Zoom=false`、横1ページ、縦1ページへ収容
- ヘッダー、フッター、同画像を除去
- 最終結合時に奇数・偶数ページをパンチ側へ0.2cm移動
- 指定ページへページ番号を下中央に付与

複数資料を一冊へ揃える用途ではこの標準化が有効だが、YakuLingoの利用者が別製品の概念を知っているとは限らない。既定の合否基準は「元の印刷設定をそのまま使用」とし、提出用の標準化は具体的な変更内容を理解して選べる補助機能にする。

初回PDF作成時の内部正本は `source_faithful` とする。利用者が通常意識する選択肢は次の3つだけにする。

1. `source_faithful`（表示名: 元の印刷設定をそのまま使用）
2. `single_page_standardized`（表示名: 1シートを1ページに縮小。文字が小さくなる場合があります）
3. 管理された任意のプロファイル（表示名: 指定された提出用設定を使用）

プロジェクト開始時に提出先の知識を要求しない。PDF確認画面の詳細設定から変更でき、選択後はプロジェクト内で保持する。

YakuLingoは用途の異なる次のRenderProfileを持つ。

- `source_faithful`: 原本の印刷範囲、余白、用紙、向き、倍率、改ページ、中央配置、ヘッダー／フッターを保持する。既定の掲載QAと体裁確認の基準にする。忠実なのは印刷設定であり、訳文による文字量・折返し・ページ数の一致は保証しない。
- `single_page_standardized`: 上下0.8cm、左右1.2cm、水平中央、垂直中央なし、縦横1ページ化、指定されたヘッダー／フッター方針を適用する。利用者が明示選択した場合だけ合否基準にする。
- `assisted_fit`: 単体提出向けに、利用者が選んだ設定だけを一時コピーへ適用する。
- `organization_preset`: 管理された提出規程を適用する。

すべて一時コピーにだけ適用し、原本Excelは変更しない。合否判定に用いた確認基準はPDF内容へ書き込まず、ブラウザの固定UI、`RenderSnapshot` manifest、QAレポートへ記録する。確認対象PDFへラベル、透かし、注記、独自ページ番号を合成しない。

#### 4.4.2 外部で冊子化する場合の責務境界

外部アプリで複数資料を冊子化する場合は、Excel本文の正規化と、冊子全体の後処理を分ける。

```text
YakuLingo
  掲載訳をExcelへ配置
  -> 選択された確認基準でプレビュー（既定は元の印刷設定）
  -> 収容、欠落、可読性を確認
  -> 訳文Excelを引き渡す

外部の冊子化アプリ
  同じ本文条件でcontent PDFを生成
  -> ページ順を編成
  -> パンチ側移動、ページ番号を最終合成
  -> 提出PDFを確定
```

YakuLingoの `single_page_standardized` では、余白、水平中央、縦横1ページ化、ヘッダー／フッター方針までを再現できる。奇数・偶数ページのパンチ側移動と冊子通番は適用しない。これらは最終的に冊子化するアプリだけが一度適用する。

初期実装は訳文Excelの引渡しまでとし、外部連携契約は将来検討とする。外部アプリまたは利用者が最終PDFを再生成した場合、YakuLingo内の確認PDFは提出前確認に留まる。最終PDFを再取込し、そのhash、ページ数、掲載完全性を確認するまで最終確認済みにはしない。

#### 4.4.3 自動で変えてよい体裁と、人へ戻す体裁

利用者が選んだ提出用設定は自動適用してよい。ただし、その結果を自動承認してはならない。`FitToPagesTall=1` で過度に縮小された場合は、設定から外れて勝手に複数ページ化せず、可読性警告を出して掲載訳、セル配置、原稿側体裁のどれを直すか人へ戻す。

単体提出の補助候補では、特に次を一括適用しない。

- `FitToPagesTall=1`: 長いシート全体を過度に縮小し、文字が読めなくなる
- ヘッダー／フッター除去: 版番号、機密区分、注記、ページ番号を失う可能性がある
- 印刷範囲変更: 情報をPDFから落とす危険がある
- 垂直中央: 複数ページ間で本文位置が揺れ、比較しにくくなる
- 列幅・行高・フォントの全体変更: 別領域の折返しや図形位置へ波及する

候補または提出契約ごとに `原本 → 提出体裁`、ページ数、最小実効フォント相当、収容できたsegment、なお収まらないsegmentを示す。正式採用は人が行う。

required artifactとdependencyは入力形式からサーバーが決める。Excelでは引渡すExcelと、その生成物集合を確認したPDFを同じmanifestへ束縛する。提出用コピーはRenderSnapshotの `output_xlsx` を隣接一時ファイルへbyte-for-byteコピーし、SHA-256検証後にだけ原子的に公開する。deliverable SHA-256が `output_xlsx_sha256` と一致しないExcelとPDFの組合せを拒否する。PDFがないWord、CSV、貼付け文章へPDF fieldを要求しない。PDF未確認のExcelは `render_reviewed` とせず、画面とレポートへ `PDF未確認の確認用Excel` と表示する。

利用者が出力ダイアログで確認記録を選んだ時点で、成果物作成前にrequired review profileを照会する。機械比較、Copilot確認、長文書等の人確認、ExcelのPDF目視の未完項目があればチェックを戻し、点検一覧への導線と必要な順序を表示する。内部のprofile keyやAPIエラーを、出力後に初めて見せない。

`review_decision_set_hash` は採用ReviewRunとtarget universe、coverage itemの状態・人判断event、finding revision/fingerprint/status/disposition event、および最終判断以外の関連HumanDecision eventを正規化して作る。findingの再open、waiver取消し、coverage判断変更、掲載訳をA→B→Aへ戻す操作でも旧最終判断をcurrentへ復活させない。

## 6. 文章単位と表示領域の推定

### 6.1 既定の文章ブロック候補として自動生成してよい範囲

現行の保守的な縦方向結合を維持する。

- 同じ列
- 次の行
- 両方の行が単独占有
- 文字セル
- 結合セルではない
- 前セルが文末で閉じていない
- 次セルが箇条書き等の新項目ではない
- 最大結合数を超えない

自動結合結果は `grouping.human_reviewed=false` とし、画面に見せ、人が解除できる状態を維持する。自動生成だけで意味境界、翻訳、最終出力を確定しない。

### 6.2 候補提示に留める範囲

- 空白行を挟む継続
- 列やインデントが少しずれた継続
- 書式は同じだが文章構造が曖昧
- 罫線を越える結合
- 表、注記、脚注らしい領域

低確信度候補を自動結合しない。「前文が未完」「同じ書式」「次行が近い列」等の理由を表示して人へ渡す。

### 6.3 右側表示領域

右側空白へのはみ出しは、文章ブロック推定とは別に判定する。

静的候補の条件:

- 隣接セルに値・数式がない
- 結合、wrap、非表示列、保護等と矛盾しない
- 図形や別要素との衝突が見つからない
- 印刷範囲内にある

これは保証ではない。`estimated_fit` に留め、実PDFで確認する。

現行実装では利用者が右1～3セルを明示選択した場合だけ `spill_right_display_only` を作る。右セルへ値は書かず、空白・数式・非表示・結合・wrapを確認してcorridor fingerprintへ束縛する。静的確認後もPDF目視を必須とする。

### 6.4 空白の下セルへの続きを配置

利用者が下1～3セルを明示選択した場合だけ `use_confirmed_empty` destinationを作る。選択した空白セルは意味単位やTM単位へ昇格させず、同じ掲載訳を構成するsliceとして扱う。

- すべてのsliceを読順に連結すると掲載訳へ完全復元できること
- 値、数式、配列、動的spill、結合、保護、入力規則、非表示行列、図形重なりを実Workbookで確認できること
- 取得不能な安全項目は `unknown` としてfail closedすること
- 全destinationのpreflight完了前には1セルも書き込まないこと
- 掲載変更で基準訳、翻訳確認、TM登録状態を変更しないこと

を不変条件とする。利用者がセル数を減らした場合は、除いたsliceを残存欄へ戻し、黙って情報を捨てない。

## 7. 収容最適化とCopilot契約

### 7.1 目的関数

最適化の優先順位を次に固定する。

1. 原文情報との対応
2. 数字、単位、符号、条件、否定、例外、主体、モダリティ
3. 登録用語と文書内一貫性
4. 読者が解釈できる略語
5. 対象読者が一義的に理解できる最低可読性
6. 印刷領域への収容
7. 制約内での自然さと読みやすさ

収容を満たすために1〜5を破らない。満たした候補が収まらない場合は `cannot_fit` とし、別配置または人の判断へ送る。

### 7.2 候補生成

「短くして」の一文指示を廃止し、次の入力を持つ候補生成タスクとする。

```text
CompactionCandidateRequest
  segment_id
  masked_source
  masked_canonical_translation
  masked_allowed_abbreviations[]
  masked_required_terms[]
  masked_protected_facts[]
  placement_budget
  masked_surrounding_context
  response_contract_version
```

応答:

```text
CompactionCandidateResponse
  candidates[]
    text
    used_abbreviations[]
    transformations[]
    claimed_preserved_facts[]
    fit_estimate
    warnings[]
  cannot_fit_reason?
```

Copilotの自己申告は証明にしない。候補採用前に、決定論QCと独立した対訳校正を行う。

個別フィールドを直接送信せず、job単位の共通Maskerでsource、canonical translation、context、用語、factsを役割別に変換した後、payload全体へ漏えい検査を行う。失敗したpayloadは送信しない。派生indexは検証済みpayloadからだけ生成する。

### 7.3 略語の検査

- 数字、単位、否定語は厳密照合
- 承認済み略語は正式名称へ展開して意味比較
- 初出定義を採用RenderProfileによる最終PDFのページ・読み順で確認
- 同じ略語に複数の意味がないか確認
- 固有名詞、商品名、義務・禁止を曖昧にする略語を高危険度扱い
- 未承認略語は採用ボタンを押しても、辞書登録は別操作

PDF読み順を一意に確定できない場合、初出定義を自動確認済みにせず人へ送る。

## 8. 校正設計

### 8.1 3つの内容を相互比較する

| 比較 | 検出する問題 |
| --- | --- |
| 日本語原文 ↔ 基準訳 | 誤訳、訳抜け、条件・範囲・モダリティの変化 |
| 基準訳 ↔ 掲載訳・PlacementPlan | 略語化、簡潔化、セル分割による欠落・重複 |
| 掲載予定文字 ↔ 最終PDF | 切れ、重なり、印刷範囲外、抽出不能 |
| 日本語原文 ↔ 最終PDF掲載文 | 読者へ届く成果物としての最終対訳整合 |

### 8.2 校正レンズ

PdfKoseiAssistの観点別passを、YakuLingoの構造へ適用する。

1. `bilingual_block`: 文章単位の日英整合
2. `numbers_dates_units`: 数字、符号、単位、日付、期間
3. `names_terms_abbreviations`: 固有名詞、用語、略語
4. `translation_consistency`: 文書全体の訳語・名称一貫性
5. `target_document_consistency`: 英語文書単独の矛盾・参照・構造
6. `structure_notes`: 見出し、表、注記、脚注、相互参照
7. `rendered_output_completeness`: PDF掲載完全性
8. `gap`: 小さい注記等、既存passで見落としやすい箇所

### 8.3 PdfKoseiAssistから継承する原則

- 英文単独校正と原文比較をscopeで分ける
- 原文比較の指摘には原文側の実在引用を要求する
- 掲載文側にも実在引用と位置を要求する
- 根拠品質と読取確信度を持つ
- 対象範囲のcoverageを記録する
- 指摘0件と検査完了を区別する
- 完全重複だけを削除する
- 同じ箇所の異なる修正案は候補群として残す
- モデルの自己矛盾や数値誤検出を決定論的に除外する

### 8.4 保護済みmasked-text原則を継承する

PdfKoseiAssistも、マスキング有効時は原本PDFをCopilotへ添付しない。クライアントで `pdf_base64` とPDF名を空にし、原本文書データとしては日英の役割ごとに数値をマスクしたTEXT sidecarだけを送る。実際の添付は校正指示書 `PROMPT_*.txt` とマスク済み `TEXT_*.txt` の2点である。サーバーは `attach_mode=masked-text` のときPDFを保存せず、ジョブ実行側も `pdf_path` を添付対象へ含めない。これはYakuLingoが参考にすべき直接の先行実装である。

YakuLingoでは、現行 `New-YakuProtectedPromptPackage` → `Invoke-YakuProtectedCopilotPrompt` の `protected-prompt-v2` を送信の正本として維持し、次のように適用する。

現行authorityには文書校正kindがないため、専用 `review` kindと固定builderをauthority内へ追加する。全可変本文をProtectionReceiptへ束縛し、応答schema、review contract version、期待scopeをEnvelopeへ含め、送信前と応答取込時の両方で検証する。既存 `cat` kindの流用、Envelope生成後のprompt追記、authority外でのreview prompt組立てを禁止する。

- 原本Excel、原文PDF、訳文PDFはローカルでレンダリング・表示・抽出する
- 初期実装は検証済みのマスク済み文章ブロックと短い観点別契約を一つの保護済みprompt内へ構造化して送る。PDFは送らない
- 同一の正規化済み数値を日英で比較できるよう、レビューjob内のsource/targetマスク処理でplaceholder辞書を共有する。原値を含む辞書はローカルjob内だけに置き、Copilotへ送らない
- source、target等の役割ごとに言語を分けてsidecarをマスクし、送信前の漏えい検証を通す。見出しindex等の派生情報は、その検証済みsidecarから生成する
- 複数言語を一括で通しがけして単位scaleを壊したり、未マスク本文から派生indexを作ったりしない
- マスキング有効時はPDF名だけを残さず、存在しない添付をモデルへ探させない
- PDF未添付のTEXT校正では、字形、フォント、罫線、桁揃え、レイアウトをAI findingの根拠にさせない
- 見た目の検査はローカルのPDF描画・抽出部品（§2.5.1）、画像差分、予定掲載文字との照合、人の目視で行う
- マスク監査、送信先URL、応答契約は既存の保護済み送信口を通す

別添付方式は、入力上限または実測品質から必要性が確認された場合だけ、専用の監査済み契約として後から追加する。

#### 8.4.1 入力上限と分割契約

「一つの保護済みprompt内へ構造化して送る」は、**文書全体を一度に送るという意味ではない。**
現行実装には次の硬い上限がある。

- `Invoke-YakuProtectedCopilotPrompt` は、prompt長が設定 `copilotPromptCharLimit` を
  超えると `PROMPT_TRUNCATED_BY_INPUT_LIMIT` を投げて終了する
  （`V91.61/app/src/CopilotClient.ps1`）
- 翻訳側の1依頼あたりの文字数は `max_chars_per_batch_file`（既定3000、上限20000）
- **上限超過での再依頼はしない**（`CLAUDE.md` の制約）

したがって文書校正は、最初から**複数依頼に分けることを前提**に設計する。

- 1つのReviewRunは複数のreview requestからなる。1 requestに載せる文章ブロックは、
  固定契約部を含めた見積り長が上限に収まる範囲までとする
- 分割は送信前に決める。送ってから切り詰めたり、超過して再依頼したりしない
- 分割の境目は文章ブロックの境目に置く。ブロックを途中で割らない
- `translation_consistency` と `target_document_consistency` は文書全体を見る必要が
  あるが、全文を1 requestへ載せない。ローカルで全occurrenceを列挙した
  `DocumentIndexSnapshot`（§5.11）から、同一原文、繰り返す名称・用語候補、先頭anchor付き
  文書windowのgroupを作り、group単位で送る。20 segment超でrequestをまたぐ文書単独整合性は、
  全体比較を実行したと偽らず `whole_document_cross_group` を人の確認待ちとして残す
- 表面形、用語ID、略語ID、位置等の列挙は決定論的に行う。同一概念・同一実体への
  group化は決定論的規則、マスク済みCopilot候補、人の確認を区別し、AI候補を確定扱いしない
- このレンズのcoverageは全文そのものではなく、索引へ列挙した全occurrenceと候補groupを
  母集団として記録する。未group・未送信のoccurrenceを黙ってcoverage済みにしない
- 各requestがどのsegment・ページ・occurrence groupを見たかを、scope/lens付きの
  `ReviewRun.coverage_items[]` へ記録し、完了状態はrequest横断・scope/lens別に判定する。
  **1 requestが上限で入りきらず落とした範囲は `skipped(reason=input_limit)` として残し、
  黙って除外しない**
- 見積りが上限を超え、ブロック境目でも分けられない単一ブロックがある場合は、
  その範囲を `skipped(reason=single_block_over_limit)` として人へ戻す。
  `unreadable_or_unmapped` は文字抽出不能または対応不能の場合だけに使う

プライバシー境界を誤解させない。原本Excel・PDF・PDF画像は送らない一方、校正に必要な本文、固有名詞、製品名、役職名、用語等は既定ではTEXTとしてCopilotへ送られる。既定マスクで伏せる対象と残る対象、実際に送るpromptを送信前に確認できるようにする。固有名詞等の匿名化は別契約とし、実装していない保護を示唆しない。ローカル削除では送信済みデータを取り消せないことも説明する。

したがってPdfKoseiAssistからは、校正契約だけでなく、ローカルPDFからsidecarを作成し、マスク済みTEXTだけを送って、回答中のplaceholderを人が読める表記へ戻す一連の方式も参考にする。製品間の実行時依存は作らず、YakuLingoのPowerShell/ブラウザ構成と既存マスク契約へ移植する。

### 8.5 PDF掲載検査

ページ文字と座標をローカルで抽出し、PlacementPlanの掲載予定文字列を照合する。実装の正本はローカル同梱PDF.jsの `pdfjs-text-v2@5.7.284` とし、正確なversion、`page_count`、page box、rotation、crop box、各text itemの4隅をviewport変換したbboxを同じ抽出結果に含める。サーバーはversion完全一致と `page_count == pages.length` を必須にする。RenderSnapshotのPDF hashと抽出器versionが一致しない結果を再利用しない。同一snapshot内で別extractorの結果を混用しない。

- 数字、単位、否定語、略語: 厳密一致
- 通常語: 改行、連続空白、ハイフン、合字を正規化した順序付きトークン
- 文字存在: PDF内に一致が1件だけでも、期待したsheet/cellの掲載結果との対応が証明できなければ `text_present_but_position_unassociated` として `unmapped` のまま人へ戻す。複数一致も `unmapped` とする。文字抽出は候補位置の提示であり、`render_reviewed` には全掲載対象へ束縛した `human_visual_reviewed` eventを必須にする。将来sheet-page map、周辺見出し、近傍語で一意化する
- 一意に対応しない: `render_unverified`
- テキスト抽出不能: ページ画像を表示し、人間確認へ送る

初期段階ではセルとPDF座標の完全な双方向マッピングを要件にしない。sheet/pageと関連セル一覧までを確実にし、座標対応はconfidence付きの追加情報とする。

`render_missing` は、対象シート・ページ対応が一意で、当該ページの文字抽出が正常に完了し、十分に識別可能な数字・単位・固有トークンまたは一意な順序付きトークン列が存在せず、別ページへの移動も否定できる場合だけ使用する。印刷範囲外をinventoryから決定論的に証明できる場合を除き、それ以外は `render_unverified` とする。

最終PDF掲載文をCopilotで対訳確認する場合も、PDFそのものは送らない。

```text
最終PDFをローカル抽出
-> PlacementPlanと対応付け
-> 抽出済み掲載文と日本語原文をsidecar化
-> マスク・漏えい検査
-> Copilot対訳校正
```

抽出不能・対応不能箇所をCopilotへ推測させず、人間確認へ送る。

## 9. 人と自動化の境界

| アプリが自動実行 | 候補だけ提示 | 人が確定 |
| --- | --- | --- |
| 原本inventory、hash、差分 | 低確信度の文章結合 | 意味単位の境界 |
| 数字・単位・符号QC | 短縮・略語候補 | 掲載訳 |
| 配置の欠落・重複検査 | セル別分割案 | 空白セルを使用するか |
| PDF生成・抽出・coverage | 体裁調整案 | 略語の妥当性と登録範囲 |
| 文書索引と一貫性候補 | 校正findingと修正案 | 指摘の採否・例外・リスク許容 |
| 変更影響範囲の計算 | 一括修正の対象一覧 | 残存指摘を確認して出力する判断 |

Copilot候補を直接確定反映しない。採用後も通常の編集として扱い、関連検査を再実行する。

## 10. 確認状態と失効

既存 `confirmed` 一つで完成状態を表さない。

```text
translation_reviewed  日英の意味を確認
placement_reviewed    Excelへの配置を確認
render_reviewed       PDF掲載を確認
document_reviewed     文書全体の一貫性・整合性を確認
final_review_acknowledged  残存指摘と対象成果物を確認して出力を選択
```

変更ごとの失効範囲:

| 変更 | 失効するもの |
| --- | --- |
| 原本snapshot変更 | exactかつ一意に再対応できたsegmentの意味確認は継承可能。変更segment、配置、PDF掲載QA、文書全体QA、最終判断は影響範囲に応じて失効 |
| 原文の文言変更 | 該当基準訳をstale候補化し、掲載訳、関連QA、配置、PDF確認、最終判断を失効 |
| 原文追加・削除・split・merge・ambiguous | 自動継承せず、人の対応確認。文書全体QAと最終判断を失効 |
| 基準訳変更 | 基準訳QA、掲載訳の基準、配置、PDF確認、最終判断 |
| 掲載訳変更 | 掲載差分QA、関連文書一貫性、PDF確認、最終判断 |
| 文章結合・分割 | 構成セルに関係する全翻訳・配置・確認 |
| 用語・略語変更 | 該当する全使用箇所と文書一貫性 |
| セル分配変更 | 掲載差分QA、PDF確認、最終判断 |
| 余白・中央配置変更 | 対象シートのPDF体裁確認、最終判断 |
| Zoom・Fit設定変更 | PDF体裁、可読性、ページ対応、最終判断 |
| 用紙サイズ・向き変更 | PDF体裁、ページ対応、最終判断 |
| 印刷範囲変更 | 掲載完全性、文書全体確認、PDF確認、最終判断 |
| 印刷タイトル・手動改ページ変更 | ページ対応、相互参照、PDF確認、最終判断 |
| ヘッダー／フッター変更 | 掲載完全性、ページ番号、文書単独整合性、最終判断 |
| 行高・列幅・フォント・折返し変更 | PlacementPlan、掲載完全性、PDF確認、最終判断 |
| PDF再生成 | 旧PDFに対する掲載確認、最終判断 |
| 校正契約・モデル変更 | 自動校正結果を再実行推奨。人の明示判断を自動取消ししない |

文書の一部変更で全確認を消さず、dependency fingerprintから影響箇所だけを失効させる。ただしsource snapshot変更時のPDF掲載QA、文書全体QA、最終判断は新版で必ず再実行する。

余白や用紙だけが変わっても翻訳の意味確認は失効させない。一方、印刷範囲やヘッダー／フッターは情報そのものを消し得るため、掲載完全性と文書確認まで失効させる。

## 11. 確認事項（finding）の人間処理

利用者が選ぶ処理:

- 修正する
- 修正済みを確認
- 正しい表現として確認
- 意図した訳し分けとして確認
- 今回だけ略語・代替表現を承認
- 略語辞書・用語集へ明示登録
- 誤検出
- 問題を確認したうえで、このまま使用
- 判断保留

高危険度findingが残っていてもDRAFT出力は可能にする。最終判断時は、未解決内容を見ずに通過できないよう一覧化し、人が明示的に処理または理由付きで許容する。

AI findingだけで技術的な出力blockerを増やさない。現行の空訳、数字欠落、原文再対応付け失敗等、決定論的に証明できる安全停止は維持する。

waiverは理由コードと説明を必須にし、対象finding revisionとdependency fingerprintへ束縛する。原文、掲載訳、配置、用語、略語、PDFの関連hashが変われば失効する。`この指摘は当てはまらない` と `問題はあるがこのまま使用` を別actionにし、waiverをTM・用語・略語辞書へ自動登録しない。source mapping失敗や書戻し不完全等のintegrity errorはwaiver対象外とする。

## 12. UI設計

### 12.1 CATを作業の中心に保つ

別アプリ風の入口を増やさず、同じ翻訳作業画面へ次の作業モードを追加する。貼り付け文章やWordではExcel専用モードを表示しない。

- `翻訳`: 現行の原文・訳文編集
- `Excelへの配置`: Excel入力時だけ表示。内容を確認する英訳、Excelに入れる英訳、セル別分配、略語
- `PDF`: Excel作業だけに表示。アプリ生成PDF、または利用者がそのExcelから出力して関連付けたPDFを、日本語版・英訳版の確認に使う。過去の日英PDF取込は抽出文だけをprojectへ渡す別入口であり、このタブの表示条件にしない
- `最終確認`: 文書全体finding一覧

PDFは狭いサイドバーへ押し込まず、全幅または左右分割表示にする。

現行には既に `体裁で見る` がある（`cat-preview-dialog`。`sheet_layout` の列幅・折り返し・結合からHTMLの表を組んで見せる。Excelも起動せずPDFも作らない）。これは**廃止せず、`Excelへの配置` タブの中の即時プレビューとして残す。** 役割を次のように固定し、2つの「体裁」を利用者へ同時に見せない。

| | 既存 `体裁で見る`（HTML） | 新設 `PDF` |
| --- | --- | --- |
| 元 | `Get-YakuSheetLayoutFromXlsx` の限定情報 | 実際に出力したPDF |
| 速さ | 即時。編集のたびに更新してよい | 明示的な「更新」が要る |
| 位置付け | **見当をつけるための下書き**。合否基準ではない | **合否基準** |
| 画面の言葉 | `目安のプレビュー` | `確認基準: 元の印刷設定` 等 |

`estimated_fit`（§6.3）はHTMLプレビュー側の結果であり、`rendered_fit` はPDF側の結果である。画面でもこの2つを同じ印で表さない。

開始画面の主入口は一つの `文章を貼り付けて翻訳` とし、別の「その場で翻訳」と「保存して確認」を並べない。ファイル入口は `Word・Excelを取り込んで翻訳` として並列に置く。

貼付け翻訳後は `訳文をコピー`、`確認して次へ`、`確認済み訳を翻訳メモリへ追加`、`この作業を残す`、`コピーして終了` を用意する。`transient` や `CAT project` 等の内部語は表示せず、`この文章は一時作業です。確認しただけ、またはコピーしただけでは翻訳メモリへ登録されません` と説明する。削除確認には、翻訳メモリ内の原文・訳文を残すか取り消すかを必ず表示する。

初回表示では専門的な状態一覧を出さず、次の順で一つずつ案内する。

1. 未翻訳なら `翻訳を開始`
2. 機械訳ができたら `原文と訳文を確認`
3. Excelなら `Excelへの配置を確認`
4. Excelの配置後は `PDFを更新して確認`
5. 複数の文章を含む資料なら `文書全体を確認`
6. 最後に `コピー`、`確認用ファイルを出力`、`この作業を残す`

エラーコード、hash、fingerprint、coverage等は通常画面へ出さず、`元データが変わったためPDFの更新が必要です` のように、原因と次の操作へ翻訳して表示する。

### 12.2 Excelへの配置画面

表示内容:

- 内容を確認する英訳
- Excelに入れる英訳

### 12.3 PDF確認画面

- 同一renderから生成した `原文PDF` と `訳文PDF（元の印刷設定）` の切替
- 原文PDFと訳文PDFをそれぞれhashでmanifestへ束縛

### 12.4 原文ファイルの差し替え画面

これは既存の `前回の資料をもとに、今回の分だけ訳す`（新規projectを作る貼付け経路）とは別の操作である（§4.1.1）。開いている作業の中から呼び、同じprojectのまま原本を差し替える。翻訳方向に依存しない `原文ファイルを差し替える` という表示を使う。

1. 原文との違い

## 13. APIとジョブ

初期実装は現行Serverの `/api/cat/{action}`、body内id・`expected_revision`、revision action統制へ合わせる。REST階層への全面変更は本機能へ混ぜない。

```text
POST /api/cat/open                 貼付け・ファイルのCAT開始
POST /api/cat/project-save         transientからsavedへ昇格
POST /api/cat/project-close-delete コピー後のtransient削除
POST /api/cat/project-retain       保持期限延長
POST /api/cat/project-presence     編集tabの期限付きlease更新
POST /api/cat/translation-confirm  原文・訳文の確認
POST /api/cat/tm-register          確認済み訳のTM登録
POST /api/cat/publication-candidates
POST /api/cat/publication-apply
POST /api/cat/publication-revert
POST /api/cat/placement
POST /api/cat/render-start
POST /api/cat/render-import
POST /api/cat/review-start
GET  /api/cat/findings
POST /api/cat/finding-decision
POST /api/cat/final-review-decision
POST /api/cat/source-update-preview
POST /api/cat/source-update-decision
POST /api/cat/source-update-apply
```

長時間処理は `202 Accepted + job_id` とし、状態取得は既存 `GET /api/jobs/{job_id}` に統一する。job resultは `result_kind: render | review | rebase_preview | publication_candidates`、`result_id`、開始・完了dependency fingerprint、`application_status: current | stale` を返す。読取GETのidはpathまたはquery、更新POSTのidはbodyで渡す。projectを変更する更新は `expected_revision`、endpointごとに定めた対象hash、idempotency keyを持つ。競合はtyped 409 errorを返し、同じidempotency keyの再送は最初と同じresultを返す。期限付きpresence heartbeatはproject revisionを増やさず、`client_id + lease sequence` で冪等化する。source update applyは後述するRebasePlan/RebaseResolutionの全CAS項目を必須とする。ジョブ開始時と完了時のdependency fingerprintが違えばstale結果として保存し、自動適用しない。render profile省略時は必ず `source_faithful` を使用する。

初期のendpoint固有CASは次を必須とする。

| action | 対象binding |
| --- | --- |
| `publication-apply` | candidate set ID、candidate ID、candidate text hash、dependency fingerprint |
| `publication-revert` | active variant ID、revision、variant hash |
| `abbreviation-register` | 現在のabbreviation registry hash、正規化entry payload hash |
| `source-update-apply` | §13記載のplan・resolution・source lineage一式 |

これらはrequest hashへ含める。project全体responseを過去状態として保存するのではなく、operation resultとcommitted revisionの安定projectionをreceiptへ保存する。現在projectの再取得は別に行う。

`source-update-apply` は `rebase_id`、`plan_hash`、`resolution_id`、`resolution_hash`、`base_source_id/hash`、`target_source_id/hash`、`base_project_revision`、`expected_revision`、idempotency keyの全一致を必須とする。曖昧な `target_hash` 名は使わない。preview再計算または人の競合判断変更後は旧plan/resolutionをstaleとして拒否する。

編集tabは `project_id, client_id, observed_revision, expires_at` の期限付きleaseを更新する。cleanupと明示削除はactive job、未期限lease、未同期outboxがあればskipまたはtyped 409とし、cleanup自身も読取revisionでCASする。

## 14. 永続化

既存のgeneration単位保存を拡張する。

```text
project/
  project.json
  source/
    revisions/<source-id>/original.ext
    revisions/<source-id>/manifest.json
    text/normalized-raw.txt
  rebases/<rebase-id>.json
  rebase-resolutions/<resolution-id>.json
  rebase-checkpoints/<revision>/
  generations/<generation-id>/
    segments.jsonl
    blocks.jsonl
    qc.jsonl
    publication-variants.jsonl
    placements.jsonl
    document-findings.jsonl
    review-runs.jsonl
    document-index.json
    human-decisions.jsonl
    tm-outbox.jsonl
    mutation-receipts.jsonl
  renders/
    <render-id>/manifest.json
    <render-id>/preview.pdf
    <render-id>/text-index.jsonl
  review-events.jsonl  # active generationから再生成できる索引
```

project削除時のTM取消しは、削除を確定する前に対象TM記録へ冪等tombstoneを作成する。失敗時はprojectを残して再実行可能にする。将来、project削除後も非同期継続させる場合だけ、project外の `<CATストア>/tm-outbox/<event-id>.json` へ必要最小限のTM識別子を移す。本文、訳文、prompt、placeholder辞書は含めない。

`rebase-checkpoints/` は `checkpoints/` と名付けない。現行の `checkpoint` は**別の概念**であり、バッチ翻訳が途中で切れたときの復帰用として、projectの外（`<CATストア>/checkpoints/<projectId>.json`）に1件だけ置かれている（`Get-YakuCatCheckpointPath`、`Save-YakuCatBatchCheckpoint`）。同じ語を2つの意味で使わない。

commit manifestは `active_source_id`、`active_generation_id`、`applied_rebase_id?`、`project_revision` を一つの組として持つ。新SourceSnapshot、rebased generation、RebaseRecordをstageへ作成・検証してから、このmanifest一つだけをCASでatomic replaceする。途中失敗時は旧原本と旧projectを完全に維持する。完全なVCSや任意branchは作らず、線形source lineageと少数のrebase前checkpointだけを保持する。

通常の確認mutationも、project state、HumanDecision、必要なTM outboxを新generationへ同時にstageし、同じcommit manifestのCASで一括可視化する。TM同期はcommit後だけ実行し、event IDで冪等化する。復旧時はactive generationの未同期outboxだけを再送し、索引ファイルの有無から確認状態を推測しない。

貼付け開始projectは `lifecycle`、`retention_until?`、`promoted_at?` を持つ。transientでもクラッシュ回復に必要な最小世代は保存するが、通常の再開一覧から分離する。自動削除条件は利用者へ表示し、`この作業を残す` だけがsavedへ昇格する。確認済み化とTM同期はlifecycleを変更しない。

PDFと抽出索引は原本・訳文を含むため、プロジェクトartifactとして利用者が削除できるようにする。通常ログへ本文、訳文、PDF抽出本文を残さない。

placeholder辞書はjob memoryだけに保持してjob終了時に破棄する。送信用promptとraw応答は検証済みprojectデータへ投影した時点で削除し、既定では保存projectにも残さない。保持するのはProtectionReceipt、契約version、prompt/response hash、正規化済み訳・findingだけとする。一時添付もjob終了時に削除する。通常ログ、tombstone、診断情報へ本文、原値、辞書を残さない。利用者が明示的に診断bundleを保存する将来機能を設ける場合は、含有データと期限を表示する別契約にする。送信済みデータはローカル削除で取り消せない。

## 15. 性能・回復

- 編集中はOOXML/既存inventoryによる静的見積りだけを更新
- 毎キー入力でPDF化・Copilot全文校正をしない
- PDFは明示的な「プレビュー更新」を基本とする
- 通常確認は変更シートだけ、最終確認はブック全体
- Excel処理はSTAの単一キューで実行し、重複要求は最新だけ残す
- PDF描画は表示ページと前後ページだけ
- キャッシュキーは原本hash、placement set hash、対象シート、印刷設定hash
- Copilotは変更文章ブロックを局所再検査し、最終時だけ全文coverageを取る
- 同じモデルを維持し、校正のためのモデル切替を毎回行わない
- 固定校正指示は契約version付きの短い共通部と、観点別の短い追加部に分ける

Excel COM障害は次を区別して利用者へ示す。

- Excel未導入
- 対話セッション不足
- ファイルロック
- ダイアログ待ち
- タイムアウト
- RPC/COM異常
- PDF生成済みだが文字照合不能

PDF生成失敗で翻訳作業全体を失敗にしない。PDF未確認を明示し、人が外部作成PDFを読み込むか、未確認として判断できるようにする。

## 18. 受入基準

### 意味と掲載

- 複数セルの原文を一つの意味単位として確認できる
- 意味単位と掲載先セルを別々に編集できる
- 掲載片の連結が掲載訳と一致し、欠落・重複を検出できる
- 人が調整したセル分割を出力時に上書きしない
- 基準訳と掲載訳の差を常に確認できる

### 略語と短文化

- Copilotが未承認略語を自動採用しない
- 略語の展開、意味、初出規則、scopeを確認できる
- 略語を展開した状態で原文との意味対応を校正する
- 収容不能を正しい結果として返せる

### PDF

- 原本を変更せず、一時コピーからPDFを生成する
- profile未指定時は必ず `source_faithful` を使用する
- 利用者が選択するまで余白、倍率、用紙、向き、印刷範囲、改ページ、中央配置、ヘッダー／フッターを変えない
- 重要print fieldを全取得できる場合、元の印刷設定によるexpected/actual fingerprintが一致する
- unknownがある場合はknown subset一致と `unverified` 表示を必須とし、既知不一致は `violated` として成果物公開を停止する
- 明示選択時は1シート1ページの標準体裁を掲載QAと体裁確認の基準にできる
- 元の印刷設定によるPDFと提出用設定によるPDFを明確に区別できる
- 提出体裁の変更項目、ページ数、縮尺、可読性への影響を採用前に比較できる
- YakuLingoと外部の冊子化アプリでパンチ移動やページ番号を二重適用しない
- 縦1ページ化、印刷範囲変更、ヘッダー／フッター除去を黙って適用しない
- PDF内容へプロファイル名、透かし、内部注記を合成しない
- 古いPDFをstaleと表示し、正式確認へ使わない
- PDF抽出不能を欠落確定と誤表示しない
- PDF生成に失敗してもCAT編集とDRAFT Excel経路は継続できる
- 利用者作成PDFを読み込んで確認を続行できる
- 外部で最終PDFを生成した場合、そのPDFを再取込して確認するまで最終確認済みにしない

### 原本差し替え

- 一意対応できないシート、block、掲載先を自動移行しない
- 行挿入やシート改名後もCodeNameを候補絞込みに使い、lineageまたは一意な原文アンカーとsemantic contextの追加証拠で正しく対応できる
- 空白セル・右側表示領域のpreconditionが崩れた場合は再利用を停止する
- 変更原文へ旧確認状態を自動継承せず、人が編集した現訳を候補として保護する
- 原文本文が同じでもsemantic contextが異なれば旧訳は候補に留め、意味確認を継承しない
- 未変更の意味確認と、失効した配置・PDF確認を区別できる
- 文書変更後はPDF掲載QA、文書全体QA、最終判断を再実行する
- rebase適用失敗後も旧原本・旧projectが使用できる
- rebase後も出力直前の原文block完全一致検査を通過しなければ書戻しを停止する

### 貼付け翻訳のCAT一本化

- 開始画面の主操作が一つで、貼付け後1操作でCAT翻訳を開始できる
- `Ctrl+Enter`、準備前予約、取消、長文分割、全文コピー、draft復元が回帰しない
- 新規翻訳で `/api/quick/jobs` を呼ばない
- コピーや確認だけではTM・用語集へ登録せず、確認済み訳を明示登録した場合だけ既存QCを通して登録する
- `確認済み・TM未登録` と `確認済み・TM登録済み` を区別できる
- transient作業は通常の再開一覧を埋めず、保存または削除を選べる
- 元の段落、改行、箇条書きを全文コピー時に復元できる
- 画面、tutorial、tourがローカル保存、TM登録、Copilot送信を同じ意味で説明する

### 文書校正

- 単文日英、翻訳一貫性、英語文書単独、PDF掲載完全性を別scopeで扱う
- 文書横断findingが複数の根拠位置を持てる
- 指摘0件とcoverage完了を区別する
- 同一問題の異なる修正案を失わない
- 修正した影響範囲だけを再確認できる
- 送信前に実際の保護済みpromptと、伏せる情報・残る情報を確認できる
- Copilotが見ていないPDFの視覚事実をAI findingの根拠にしない

### 人間承認

- 自動候補が人の操作なしに確定訳、辞書、TMへ昇格しない
- DRAFT出力と最終判断を分ける
- 未解決findingを確認し、理由付きで許容できる
- 判断と失効理由がappend-onlyで追跡できる
- 最終責任をアプリやCopilotが代行したように表示しない

## 19. 実装開始時の優先順位

最初に着手するのは校正プロンプトではない。以下の順とする。

1. fixtureとデータ不変条件
2. 貼付け翻訳をCAT経路へ一本化し、Quick専用経路を段階廃止
3. SourceSnapshotと原本設定による一時Excel・PDF生成
4. PDF表示とfingerprintによるstale管理
5. PlacementPlanを追加し、文字数比再分割を候補生成へ限定
6. 原本差し替え3-way rebaseと安全停止
7. 掲載予定文字とPDFの決定論照合
8. DocumentFinding、ReviewRun、HumanDecision
9. 文書索引とローカル一貫性検査
10. 保護済み単一promptによるCopilot校正
11. 制約付き収容候補と略語レジストリ

この順序なら、Copilot校正がなくても「何が印刷されたか」を先に実機で確認でき、その上に根拠付き校正を安全に載せられる。

## 20. 設計レビュー結果

本設計は、次の3観点による独立レビューを統合した。

- 製品全体アーキテクチャと段階導入
- PdfKoseiAssist型校正、人間承認、確認失効、監査
- Excel変則レイアウト、PDF掲載検査、ReportBinder再利用境界

3観点で共通した結論は以下である。

- 既存CATを作り直さない
- Segmentを意味の正本として残す
- PlacementPlanを別データにする
- PDFを最終確認対象にするが、抽出結果を過信しない
- 行ローカルQCと文書全体findingを分ける
- 自動化は候補・測定・根拠整理までに留める
- DRAFT出力と人の最終判断を分ける
- 貼付けを別翻訳モードにせずCAT品質基盤へ統合する
- 原本差し替えを上書きでなく3-way rebaseとして扱う
- 元の印刷設定を既定にし、確認情報をPDF内容へ合成しない
- まずPDF実出力と配置モデルを実証し、その後に全文書AI校正を載せる
