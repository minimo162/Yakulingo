# V91.61 段階2: 参考資料コーパスの検索

作成 2026-08-05 / 改訂 2026-08-05（転置索引を廃止）

段階1（`_docs/V91.61_修正指示書_参考資料コーパスの作成と配布.md`）で、
英語資料の Markdown がローカルへ配布されるところまで動いた。
段階2 は、それを**引ける形にする**ところまでを担う。

**この段階では翻訳経路へ差し込まない。** 差し込みは段階3（Agentic 検索）で行う。
ここで作るのは検索器と、それが実データで機能しているかを管理者が確かめる手段だけである。

---

## §2 **転置索引をやめた経緯**（この文書の要点）

最初の実装は転置索引（TSV）を作って引いていた。動きはしたが、**測ったら索引なしのほうが速かった。**

検証環境は PowerShell 7.4 / Linux。**実機の Windows PowerShell 5.1 では 2〜3 倍を見込む。**

方式を比べたときの数字（試作。順位づけは粗い）:

| 方式 | 資料100件 | 資料600件 | 索引作成 | 配布・保存 |
| --- | --- | --- | --- | --- |
| 転置索引（TSV） | 415ms | 2,357ms | 9.9〜47秒 | 10〜65MB |
| 索引なし・2段構え（試作） | 173ms | 557ms | なし | なし |
| 索引なし・C# へ降ろす | 89ms | 544ms | なし | 初回 3.1 秒のコンパイル |
| 索引をメモリに持ち回る | 436ms | 1,904ms | — | — |

**出荷する実装での実測**（BM25 と差し替え用の関数境界を入れた後）:

| 資料数 | コーパス | 検索1回 | 転置索引だったとき | データディレクトリへの書き込み |
| --- | --- | --- | --- | --- |
| 100件 | 6.5MB | **456ms** | 415ms | 0 件 |
| 300件 | 19.5MB | **593ms** | 1,175ms | 0 件 |
| 600件 | 39.1MB | **875ms** | 2,357ms | 0 件 |

試作より遅いのは、**順位づけを BM25 にし、差し替えられるよう関数へ分けたぶん**である。
資料100件では転置索引とほぼ互角（41ms 差）で、300件から先は 2〜2.7 倍速い。
**互角の規模でも、索引作成・索引ファイル・鮮度判定がまるごと消えるほうを採る。**

### なぜ索引が遅かったのか

**読み込みではない。** 索引ファイルの読み込みは全体の 1〜8%（27〜175ms）しか
占めていなかった。「メモリに持ち回る」がほとんど効かないのがその証拠である。

遅いのは、6,000〜36,000 行の転置を **PowerShell で解釈しながら回す**部分だった。
直引きは `String.IndexOf` に丸投げするため、繰り返しが .NET の中で完結する。

> **この環境では「賢いデータ構造を自前で回す」より
> 「素朴な処理を .NET へ投げる」ほうが速い。**

C# へ降ろしても速くならなかった（89ms 対 90ms）。つまり残りの時間は
**ファイル読み込みと小文字化そのもの**であり、そこが「毎回コーパスを読む」設計の下限である。
`Add-Type` は初回 3.1 秒（Windows PowerShell 5.1 の csc.exe はさらに遅い）かかるため割に合わない。

### 索引をやめて消えたもの

- 利用者側の索引作成（資料600件で最大2分）
- 索引ファイル 10〜65MB
- 鮮度の判定、書式の版管理、置き場所の議論
- 「索引を配布物に含めるか」という未解決の問い

### 検討して却下した他の選択肢

| 案 | 却下理由 |
| --- | --- |
| **SQLite + FTS5** | .NET Framework に SQLite は無い。`SQLite.Interop.dll`（ネイティブ、x86/x64 別）が要る。FTS5 は標準パッケージでは既定で無効で、`System.Data.SQLite.Core.FTS5` か実行時 `LoadExtension` が必要。いまの配布物にネイティブは1つも無く、`%LOCALAPPDATA%` 配下のネイティブ DLL 読み込みは AppLocker / WDAC / EDR が止めに来る。検証環境（Linux / PowerShell 7）では再現できない |
| **ESENT / ManagedEsent**（`esent.dll` は Windows 同梱） | ISAM のキー値ストアで全文検索が無い。転置を自前で回すことになり、今回遅かったのと同じ場所へ戻る |
| **Windows Search**（`Search.CollatorDSO`、OS 同梱） | 索引の範囲とタイミングが制御外。`%LOCALAPPDATA%` が索引対象とは限らず、結果をコーパスの版で固定できない |
| **Lucene.NET**（純マネージド、ネイティブ不要） | 順位づけは最も確か。ただし PowerShell からの呼び出し回数そのものが費用であることが今回の測定で分かっており、数MBの DLL と beta 継続を背負う価値が現時点で無い |
| **メモリ常駐 / MemoryMappedFile** | 測定で否定。読み込みは全体の 1〜8% しか占めていない |

**乗り換える条件**（先に決めておく）:

- 資料が **300件を超えた**、または実機で検索が **3秒を超えた**
- 毎週資料が増え、**差分更新**が要るようになった

そのときの第一候補は SQLite + FTS5、次点で Lucene.NET。
`Search-YakuCorpus` が唯一の入口なので、中身だけ差し替えられる。

## §3 作ったもの

### §3-1 `app/src/CorpusSearch.ps1`

| 関数 | 役割 |
| --- | --- |
| `Get-YakuCorpusSearchDir` | 引く先を決める。配布済みコーパス → 無ければ管理者の `corpus-build` |
| `Get-YakuCorpusTokens` | 英語の文を検索語へ分ける |
| `Split-YakuCorpusPassages` | Markdown を「引ける単位」へ切る |
| `Measure-YakuCorpusTermHits` | 出現数を数える。**`String.IndexOf` だけを使う** |
| `Get-YakuCorpusDocumentMatches` | 段階①。資料を読み、出現数と文書頻度を出す |
| `Get-YakuCorpusBm25Score` | **順位づけ。ここだけ差し替えれば方式を変えられる** |
| `Search-YakuCorpus` | 検索の入口。**呼び出し側はこの戻り値だけを見る** |
| `Remove-YakuCorpusLegacyIndex` | 索引を作っていた版の残骸を片付ける |

### §3-2 2段構え

```
① .md を読み、検索語の出現数を数えて資料を絞る
     ここで各語の「文書頻度」が無料で手に入る → IDF に使える
     繰り返しは資料の数ぶん（一節の数ではない）
② 残った上位8件の資料だけを一節へ切り、BM25 で順位づけする
```

`DocFreq` は「その語を含む**資料**の数」であり、一節の数ではない。
一節ごとの文書頻度を数えるには全一節を走査する必要があり、それは索引を作るのと同じ費用になる。
資料単位の粗い値でも「どの資料にも出る語を軽くする」という IDF の役目は果たせる。

一節の長さの正規化には固定値（900字）を使う。標本から平均を出すと、
絞り込んだ数件に引きずられて基準が動くため。

### §3-3 一節への切り方

- **ページ境界（`<!--yaku-page:N-->`）を越えない。** どの資料の何ページから引いたかを示すため。
- 空行で段落へ切り、目安 900 字までまとめる。1行だけの見出しや表の1行は文例にならない。
- 60 字に満たない一節は捨てる。

### §3-4 検索語の取り方

- 小文字化し、英数字以外で切る。**日本語の形態素解析も文字 N-gram も要らない**（英語だけなので）。
- **数字だけの語は落とす。** 「2026」で引いても言い回しは見つからない。雑音になる。
  （翻訳経路の数値は V91.60 でマスクされるため、検索語にも現れない）
- 英語の機能語（the / of / and …）は落とす。財務資料は定型表現が多く、
  残すとどの一節も同じくらい当たってしまう。
- 照合は**部分一致**。`ratio` は `ratios` にも当たる。英語では簡易な語幹処理として働く。

### §3-5 管理画面「引けるか試す」

`-Admin` のときだけ `/api/admin/corpus/search` を登録する。
**一般利用者の画面には出さない**（利用者向けの表示は段階4 で初めて検討する）。

走査した資料数・所要時間・**実際に使われた検索語**を返す。
機能語や数字が落ちるため、入れた語とは違うことがある。それが見えないと結果を読めない。

## §4 実装で踏んだ落とし穴

すべて **PowerShell 側の処理量**の話である。.NET へ渡した処理は速い。

| 落とし穴 | 実測 | 対処 |
| --- | --- | --- |
| **繰り返しの中の `\| Out-Null`** | `List.Add` 72万回で **100 秒**（`[void]` なら 1.7 秒） | 繰り返しの中は `[void]`。理由をファイル冒頭に明記 |
| 語ごとに正規表現を回す | 120 万語で数十秒 | 切り分けは正規表現1回、語ごとは文字比較 |
| 行ごとに正規表現を当てる | 資料8件（480一節）の切り分けで 202ms | 文書ごとに `Regex.Split` 1回にする |
| **`[Parameter()]` つきの引数束縛** | 480回で 66ms（属性なしなら 39ms） | 一節ごとに呼ぶ関数には属性を付けない |
| **一節ごとに `PSCustomObject` を作る** | 出現数を返すだけで 480回 169ms（`int[]` だけ返せば大幅減） | 戻り値を素の配列にする |
| **`$Top` と `$top` は同じ変数** | `[int]$Top` に配列を代入して型変換エラー | PowerShell の変数名は大文字小文字を区別しない。紛らわしい名前を避ける（同じ罠を `$n` と `$N` でも踏んだ） |
| 文字と文字列の暗黙比較 | 検証環境（PowerShell 7）と実機（5.1）で差が出うる | `[char]'0'` と明示する |

## §5 受容基準

1. **索引を作らない**こと（データディレクトリにもコーパスの中にも書かない）
2. ページ境界を越えた一節ができないこと
3. 数字だけの語・機能語が検索語にならないこと
4. 出典（データベース・資料・ページ）が必ず付くこと
5. 得点の高い順に並び、同点でも順序が揺れないこと
6. 珍しい語ほど重く、出現数が多いほど重く、同じ出現数なら短い一節を優先すること
7. データベースで絞り込めること（括弧・半角カナを含む名前でも）。**絞ったら読む資料も減る**こと
8. 当たらないときに**0 件を返す**こと（作り話をしない）
9. コーパスが無い / 読めないときに**0 件を返し、落ちないこと**
10. コーパスを変えたら**次の検索へ即座に反映される**こと（作り直しが要らない）
11. 索引を作っていた版の残骸を片付けること。**見覚えのないものが混じっていたら触らない**こと
12. `-Admin` を付けないとき、検索の経路が**登録されない**こと
13. **翻訳経路（`Translation.ps1` / `FileTranslation.ps1`）に差し込まれていない**こと
14. 一般利用者の画面に現れないこと
15. 既存の回帰がすべて通ること

回帰は `app/tools/Test-YakuV9161CorpusSearch.ps1`。

## §6 段階3 へ引き渡すもの

```
原文（日本語）
  ↓ ① Copilot: 「この内容を英語資料から探すならどんな語で引くか」   ← 段階3
検索語（英語）
  ↓ ② Search-YakuCorpus                                          ← 段階2（ここまで完了）
関連する英語の一節 数件（出典つき）
  ↓ ③ Copilot: 「社内資料ではこう書いている。これに倣って訳せ」      ← 段階3
訳文
```

段階3 は実装済み。`_docs/V91.61_段階3_コーパス翻訳.md` を参照。
適用範囲は**テキスト翻訳の JA→EN のみ**になった。ファイル翻訳のバッチは
文字数で切られた無関係なセル片の寄せ集めで、1つの検索語では代表できないため。

当初この段階で決めるとしていたこと:

- 検索語の生成を**翻訳ジョブごとに1回**にする（要件整理 §6-1-3）。バッチごとにしない。
  **毎回コーパスを読み直す設計なので、この前提は索引があったときより重い。**
- 引けなかったときに**素通しで従来どおり訳す**こと。コーパスは足しであって前提ではない。
- 文例をプロンプトへ入れる形（何件・何字まで・出典を見せるか）。

## §7 積み残し

| 事項 | 判断 |
| --- | --- |
| **順位の質は未検証** | 合成コーパスでは判定できない。**実データで確かめる**。管理画面「引けるか試す」がその場 |
| 検索のたびにコーパス全体を読む | 実測 0.46〜0.88 秒（実機で 2〜3 倍）。ジョブごとに1回なら許容。§2 の乗り換え条件を超えたら再考 |
| 一節へ切る資料を上位8件に限っている | `-DocumentCandidates` で変えられる。増やすと段階②の費用だけ増える（読み込みは全件で済んでいる）。**適切な値は実データを見てから決める** |
| 同義語・言い換えへの弱さ | **段階3 の Agentic 検索で補う**のが元の設計（要件整理 §6-1-4） |
| 埋め込み検索 | 塞いでいない。`Get-YakuCorpusBm25Score` の対を足せば差し込める |
| 日本語側の資料 | 扱わない。英語側だけという決定は動かさない |
