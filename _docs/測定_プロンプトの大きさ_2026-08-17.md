# 測定: Copilot へ実際に出ているプロンプトの大きさ（2026-08-17）

利用者から「5,500字は長すぎるので精査して不要な情報を落とさないと Copilot が
処理に時間がかかる」という指摘があった。**数えたら 5,500 ではなかった。**
そして**「長いと遅い」のほうは、アプリ自身のログでは見えなかった。**
それでも削る理由は別にある。順に書く。

---

## 1. 実際の大きさ（雛形を足し算せず、組み上がったものを測った）

10文字の見出し（`四半期連結損益計算書`）1本を渡したときに出るプロンプト。

```
短くする依頼    11,469字   ← うち 8,481字（74%）が style_brief_rules.txt 丸ごと
電文体の翻訳     6,151字
通常の翻訳       3,176字
```

雛形そのものの大きさは次のとおり。

```
style_brief_rules.txt            8,481字
text_translate_brief_to_en.txt   5,590字
text_shorten_to_en.txt           2,226字
cat_translate_to_en.txt          1,728字
text_translate_full_to_en.txt    2,515字
```

**「5,500字」は `text_translate_brief_to_en.txt` を指していた。**
実際に出ていく最大は**その2倍の 11,469字**である。
測り方は `scratchpad/Measure-PromptSize.ps1`（雛形を読んで足すのではなく、
`New-YakuShortenPrompt` などを呼んで出来上がった文字列を数える）。

## 2. 実装が、自分の註と反対のことをしている

`src/PromptBuilder.ps1:936-937` にこう書いてある。

> 圧縮の手口だけを渡す。文体の規則集を丸ごと再掲しない。
> 既に良い訳が入力なのに、それを産んだ規則を全部見せると
> 「一から作り直す」を誘発する（独立評価 2026-08-08）

**その3行下（:940）が丸ごと再掲している。**

```powershell
try { $briefRules = Get-YakuPromptTemplate -Root $Root -Name 'style_brief_rules.txt' } catch { $briefRules = '' }
```

註は 2026-08-08 の独立評価という**測定に基づく決定**を記録している。実装はそれを
実施していない。**これは制約文と実装の食い違い（実装を採る）ではなく、
決定と実装の食い違いである。** 決定のほうが測定に基づいているので、直すのは実装側。

ただし**直せば出力が変わる**ので、変えてから測るのではなく、測ってから変える。

## 3. 条件分岐はほとんど効いていない

`Get-YakuBriefConditionalSections` は「原文に引き金が無い節は出さない」ための仕組み
だが、実測では効き幅が小さい。

```
ただの見出し（10字）        -> 6,151字
数値と比率を含む原文        -> 6,169字
                               差は 18字
```

**6,000字のうち 18字しか動かない。** 節の出し分けは、大きさの対策になっていない。

## 4. 「長いと遅い」は、ログでは見えなかった

`~/.yakulingo-ps/logs/yakulingo.log` の `promptLength=` と、直後の
`Copilot wait result` の `elapsedMs=` / `answerLength=` を突き合わせた（14件）。

```
prompt   157字  -> 1,737 / 1,748 / 1,750 / 2,213 / 2,222 / 3,256 / 3,595 / 3,624 / 4,088 ms （応答 95字）
prompt 2,515字  -> 1,113 ms （応答 64字）      ← 標本中いちばん速い
prompt 3,430字  -> 2,202 / 2,662 ms （応答 506字）
prompt 5,970字  -> 3,135 / 3,648 ms （応答 6,247 / 6,399字）
```

**時間は応答の長さに付いていく。** 同じ157字のプロンプトで 1,737〜4,088ms、
**2.4倍のばらつき**がある。プロンプト長で説明できる幅より、この揺れのほうが大きい。
いちばん速かったのは 2,515字の依頼だった。

**ただし「長さは効かない」とは言えない。**

- 14件しかない
- プロンプト長と応答長が交絡している（長い依頼は長い応答を求めている）
- **いちばん大きい 11,469字の短縮依頼が、この標本に1件も入っていない**

前提を確かめずに削り始めなかった、という記録である。速さを理由に削るなら、
**短縮依頼を長短2版で走らせて時間を測る**のが先。

## 5. それでも削る理由（速さではない）

§2 の食い違いがそれである。**入力が既に良い英訳なのに、その英訳を産んだ規則集を
全部見せると「一から作り直す」を誘発する** という、測定に基づく判断が記録に
残っていて、実装がそれに反している。効くのは速度ではなく**出力の質**である。

## 6. 何をどう削るか（案。まだ測っていない）

`style_brief_rules.txt` の内訳（43行、8,481字）。

| 区分 | 行 | 字数 | 短縮依頼に要るか |
| --- | --- | --- | --- |
| 伏せた数値トークンの保存 | 1-5 | 393 | **要る**（原文と現訳の両方にトークンが居る） |
| 電文体とは何か・優先順位 | 6-7 | 225 | 疑わしい（現訳は既に電文体） |
| B1〜B7 圧縮の手口 | 8-14 | 1,796 | **要る**（これが「手口」そのもの） |
| Q1 引用の扱い | 15-17 | 380 | 要る（外すと崩れた実測が `PromptBuilder.ps1:721` にある） |
| 標準略語の一覧 | 18-20 | 1,857 | **要る**（短くする手段そのもの） |
| 言い換え・符号付き内訳・表記統一 | 21-23 | 879 | 要る |
| 長さは目標でなく診断 | 24 | 107 | 疑わしい |
| FULL→BRIEF の作例 | 25-39 | 2,455 | **疑わしい**（FULL から作る手順を教える。現訳は既に BRIEF） |
| 最終確認・句読点・略称・短いラベル | 40-43 | 1,011 | 要る |

**落とせる候補は「作例」「電文体とは何か」「長さは診断」で、合わせて約 2,787字**
（8,481字の33%）。短縮依頼は 11,469 → 約 8,700字になる。

**これは案であって、実施はしていない。** `PromptBuilder.ps1:721` に「引用の事例を
外すと電文体そのものが崩れた（文に戻った）」という実測が残っている。**作例を外すのは
同じ種類の変更である。** 外す版と外さない版で同じ題材を走らせ、
(a) 圧縮後の長さ (b) 数値の残存 (c) 事実の残存 を測ってから決める。

## 7. 併せて分かったこと（測定の土台のほう）

利用者の指摘。

> 今測っているのは公表資料だから原文はかなり綺麗なはず。これはAI翻訳にとって有利で、
> ちゃんとした翻訳がしやすい。実際はもっと圧縮された訳しにくい原文を翻訳する場合もある。
> （中略）翻訳文も短くしないとスペースに収まらず、そうした短くした翻訳文の
> クオリティが鍵になる

そのとおりで、`_docs/測定_通し比較_2026-08-17.md` の20文は**易しい半分**である。
圧縮された原文の題材を作った（`_docs/比較題材_圧縮された原文_2026-08-17.json`、20行。
表の見出し・節のラベル・セルの見出し）。

**作ってすぐ分かったことが1つある。「枠に収まるか」の物差しに公表訳は使えない。**
原文の幅を2倍（CJK1字≒ラテン2字）としたとき、**公表英文自身が収まるのは 20行中5行**
だった。

```
5字  年間配当金                  -> Dividends Per Share            19字（枠10字）
10字 四半期連結損益計算書        -> Quarterly Consolidated Statements of Operations  47字（枠20字）
13字 41 DX／AXの取り組み         -> 41 Digital Transformation and AI Transformation Initiatives  59字（枠26字）
```

紙面には横幅の自由があったので、公表訳は縮めていない。**セルに収める判定には、
利用者の実ファイルの実際の列幅が要る。** 題材だけ先に用意し、判定の物差しは
保留にしてある。
