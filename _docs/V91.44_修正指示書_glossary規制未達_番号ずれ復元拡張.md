## 背景

### §1の背景: 規制コンプライアンス文脈の意味反転（事実系）

オーストラリアCO2規制文書の実訳レビュー（2026-07-22）で2件の誤訳を確認:

1. 「CY26以降も未達の計画」→ "plans to remain **below the targets**"
   CO2規制文脈の「未達」は排出量が規制値を**超過**しコンプライアンス未達成の意味だが、
   英語の "below the targets" は「規制値を下回る＝達成」と**逆方向**に読める。
   FULL/BRIEF両出力で同一の反転が発生。事実系（規制遵守状態の誤伝達）。
2. 「未購入クレジット契約（購入先RIVIAN）」→ "(**purchased from** RIVIAN)"
   未購入契約に過去分詞を使用し、購入済みと読める。事実系（取引状態の誤伝達）。

いずれもドメイン語彙の欠落であり、規則の欠陥ではない。凍結を維持し
prompt_glossary.csv（文中参考訳語）への追記で対応する。

### §2の背景: 番号連番オフセットの発生機構（特定済み）

症状: 原文に 1. 2. 3. の番号があるとき、FULLは 1,2,3 だがBRIEFが**それに続いて
4,5,6** になることがある（今回文書では非発生、過去に発生実績あり）。

機構（コード確認済み）:

1. モデルはR8どおりFULL/BRIEF両方で正しく「1. 2. 3.」を出力している（プロンプト非起因）
2. CopilotはMarkdownレンダリングで「1.」等を `<ol><li>` に変換し、番号の
   リテラルテキストはDOMから消える
3. FULLとBRIEFの間の `BRIEF_TEXT:` 行がMarkdownのlazy continuationでリスト項目に
   吸収されると、**両リストが単一の`<ol>`（6項目）にマージ**される
4. CopilotClient.ps1 の extractText はレンダリング結果に忠実に
   `start属性 + 連番index` で番号を再構成するため、BRIEF側が 4,5,6 になる
   （FULL/BRIEF間の空行の有無でマージ有無が変わるため「時々起きる」症状と一致）

つまり原文番号の情報は**Copilotのレンダリング段階で失われており**、抽出側では
原理的に復元できない。復元の正解は原文（SourceText）との照合であり、その仕組みは
既に Repair-YakuNumberedHeadingSequence（Translation.ps1:270）として存在する。

現行の発動条件と欠落:

- 現行は「訳文の番号がすべて同一（例: 1,1,1）」のケース**のみ**復元
  （`if ($targetNumbers.Count -ne 1) { return $result }` のガード）
- 4,5,6 の連番オフセットはユニーク数3のためこのガードで**素通り**する

呼び出し（Translation.ps1:462）はfull/briefの各optionに対して個別実行のため、
BRIEF単独で target=[4,5,6] vs source=[1,2,3] の照合になり、FULL/BRIEF境界の
判定は不要。ガード条件の拡張だけで完結する。R8により「訳文の番号列＝原文の番号列」
が仕様なので、件数一致下での位置復元は常に正しい（「数値の正しさをプロンプト遵守に
賭けない」方針のコード側保証層に相当）。

## §2 Translation.ps1: Repair-YakuNumberedHeadingSequence の復元条件拡張

関数全体（270行目〜）を以下へ置換する。変更点は (a) 「訳文番号すべて同一」ガードを
「位置ごとの番号列が原文と不一致」へ一般化 (b) 原文番号列のユニーク数チェック削除
（位置復元は原文が 1,1,2 のような列でも定義可能） (c) ログに両番号列を出力。
count不一致時のskip＋WARN、repeatedTargetWithoutSourceの診断WARN、
全角ピリオド `．` 対応の正規表現は**現行のまま維持**する。

```powershell
function Repair-YakuNumberedHeadingSequence {
    param(
        [Parameter(Mandatory=$true)][string]$SourceText,
        [AllowNull()][string]$TranslatedText,
        [Parameter(Mandatory=$true)][string]$Style
    )
    $source = @(Get-YakuNumberedHeadingSequence -Text $SourceText)
    $target = @(Get-YakuNumberedHeadingSequence -Text $TranslatedText)
    $result = [pscustomobject]@{ Text=[string]$TranslatedText; Restored=$false; Detail="numberedHeadings source=$($source.Count) target=$($target.Count)" }
    if ($source.Count -lt 2 -or $target.Count -ne $source.Count) {
        $targetNumbersForSkip = @($target | ForEach-Object { [string]$_.Number } | Select-Object -Unique)
        $repeatedTargetWithoutSource = ($source.Count -eq 0 -and $target.Count -ge 2 -and $targetNumbersForSkip.Count -eq 1)
        if (($source.Count -gt 0 -and $target.Count -ne $source.Count) -or $repeatedTargetWithoutSource) {
            try { Write-YakuLog "Text numbered headings mismatch; restore skipped. style=$Style source=$($source.Count) target=$($target.Count) repeatedTarget=$repeatedTargetWithoutSource" 'WARN' } catch {}
        }
        return $result
    }
    $sourceNumbers = @($source | ForEach-Object { [string]$_.Number })
    $targetNumbers = @($target | ForEach-Object { [string]$_.Number })
    if (($sourceNumbers -join ',') -eq ($targetNumbers -join ',')) { return $result }
    $lines = @(([string]$TranslatedText).Replace("`r`n","`n").Replace("`r","`n") -split "`n")
    for ($i = 0; $i -lt $target.Count; $i++) {
        $lineIndex = [int]$target[$i].LineIndex
        $headingPrefixRegex = New-Object System.Text.RegularExpressions.Regex('^(\s*(?:#{1,6}\s+)?)\d+([\.．])(\s+)')
        $lines[$lineIndex] = $headingPrefixRegex.Replace([string]$lines[$lineIndex], ('${1}' + [string]$source[$i].Number + '${2}${3}'), 1)
    }
    $restoredText = ($lines -join "`n")
    try { Write-YakuLog "Text numbered headings restored from source. style=$Style count=$($source.Count) sourceNumbers=$($sourceNumbers -join ',') targetNumbers=$($targetNumbers -join ',')" 'WARN' } catch {}
    return [pscustomobject]@{ Text=$restoredText; Restored=$true; Detail="numberedHeadings restored=$($source.Count)" }
}
```

補足:

- 改行の正規化・置換ロジック・呼び出し側（:462、full/brief各optionへの個別適用）は
  無変更。関数のガード条件と復元ログのみが差分
- 挙動が変わるのは「件数一致かつ番号列不一致」の領域のみ。従来復元していた
  repeated（1,1,1）ケースは新条件（列不一致）に包含され、回帰しない
- file経路は対象外（[[ID:n]]マーカーによる別機構で項目番号を保証済み、R8相当なし）
- to_jp経路（style='jp'）も同ループを通るが、原文番号の位置復元という意味論は
  方向非依存のためそのまま適用してよい
