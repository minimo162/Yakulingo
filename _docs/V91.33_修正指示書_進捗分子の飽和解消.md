# V91.33 修正指示書（改訂版）— 進捗分子の常時2,000固定の解消

ベース: V91.32（期待応答長実測校正版）
対象: CopilotClient.ps1（スライスJSのヘルパー化＋数値フィールド追加、PS側1行）
症状: 進捗detailの分子が応答の長短にかかわらず常に2,000
     （短文でも 2000/285 のような表示。ユーザー観測で確定）

---

## 0. 真因（コード確認済み・改訂）

- スライスJSの各return: `mainTail: mainText().slice(-diagnosticTailLength)`
  — **ページ全体のmainテキスト末尾2,000字**であり、ベースライン
  （送信前長）を引いていない。
- Copilot画面には送信直後から**プロンプトのエコー（約9,700字）**が
  表示されるため、応答0字の時点で mainText は既に2,000字超
  → 分子（mainTail長）は**最初のスライスから常に2,000**。
- 前版指示書の「応答2,000字超で飽和」は不完全な診断だった。正しくは
  「開始直後から定数」。
- 注意: 単純に `mainText長 − baseline長` へ変えると、今度は
  プロンプトエコー分が分子に乗る（別の過大計上）。エコー除去が必須。

## 1.【必須】応答実長ヘルパーの共通化 — スライスJS

既存の latestFromCopilotTail が持つ「ベースライン以降を取り、
echoEndMarkers（'SOURCE_END:' / '===END_INPUT_TEXT:' /
'SOURCE_ITEMS_END'）までを切り捨てる」処理をヘルパーに抽出し、
テキスト抽出と進捗計測で共用する:

```javascript
const responseTextSoFar = () => {
  const t = mainText();
  let after = t.length > Math.max(0, baseline.mainTextLength || 0)
    ? t.substring(Math.max(0, baseline.mainTextLength || 0)) : '';
  let cutIndex = -1, cutLen = 0;
  for (const m of echoEndMarkers) {
    const idx = after.lastIndexOf(m);
    if (idx > cutIndex) { cutIndex = idx; cutLen = m.length; }
  }
  // マーカー未出現＝プロンプトエコー描画中で応答未開始 → 0扱い
  if (cutIndex < 0) return '';
  return after.slice(cutIndex + cutLen);
};
const answerLengthSoFar = () => responseTextSoFar().length;
```

- latestFromCopilotTail 内の同一ロジックは responseTextSoFar() 呼び出し
  に置換（重複排除）。
- 各return経路（ok / timeout / stopped）に
  `answerLengthSoFar: answerLengthSoFar()` を数値で追加。
- マーカー未出現時に0を返す設計により、エコー描画中の過大計上を防ぐ
  （その間は timeFloor がバーを緩やかに進める）。
- mainTail（診断用末尾抜粋）と diagnosticTailLength は変更しない。

## 2-2.【必須】expectedChars／ratio計測のファイル翻訳経路への移植 — FileTranslation.ps1

### 現象（ログで確認）
V91.32のファイル翻訳ジョブ（2バッチ）に "Copilot answer ratio measured"
が1行も出ない。batch_expected_chars 設定とratio計測が Translation.ps1
（テキスト経路）のみの実装で、FileTranslation.ps1 のバッチループは
未対応。結果、ファイル翻訳の進捗は charBased が常に0扱い＝timeFloor
（時間刻み）だけで動き、file係数の校正データも取得できない。

### 修正
Translation.ps1 と同じ2箇所をファイル翻訳のバッチループへ移植する:
1. バッチ開始時: `batch_expected_chars = max(1, base + バッチ入力文字数
   × ratio)`（kind=file の係数: copilotAnswerRatioFile 既定1.5 /
   copilotAnswerBaseFile 既定0）。バッチ入力文字数はアイテム連結後の
   送信テキスト長を使う。
2. バッチ完了時: actualRatio（answerChars/inputChars）のINFOログ出力
   （テキスト経路と同一書式。kind=file であることが分かるよう
   jobId併記のままでよい）。
同ジョブ内学習（バッチ2以降を実測比平均で上書き）も同様に移植する。

## 受入基準

1. 短文（100字未満）のテキスト翻訳で、分子が0から始まり応答量に応じて
   増える（2000固定が消える）
2. 長文（入力1,000字以上）で分子が2,000を超えて伸び、バーが50%前後で
   頭打ちにならず8〜92%区間を漸進する
3. プロンプトエコー描画中（送信直後）に分子が跳ね上がらない
   （マーカー未出現→0の動作確認）
4. ファイル翻訳（numbered）でジョブ中に "answer ratio measured" が
   バッチごとに出力され、進捗が charBased で漸進する。実測 actualRatio
   が暫定係数1.5と大きく乖離する場合は設定キーで校正
5. （任意）glossary.csv の品質関連費用の表記を "Warranty Exp." に揃えて
   occurrence conflict（ピリオド有無の別キー化疑い）が消えることを確認
