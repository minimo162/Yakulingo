# YakuLingo V91.60 修正指示書（Copilot送信前の数値プレースホルダー化）

作成日: 2026-08-03 / 改訂: 2026-08-03（符号の保持と4件の方針決定を反映） / ベース: V91.59

利用者からの依頼:

- **Copilot への依頼は外部サーバーへの送信になるため、年号や「1株当たり」のような
  機密性のない数値を除き、数値はプレースホルダーに置き換えて送信し、受信後に復元する。**
- **数値がプラスかマイナスかという情報は保持してよい。**

本版は送信内容の機密性に関わる変更であり、翻訳品質契約より優先される。

## 背景: 現状で外部へ出ている数値

実装を確認した結果は次のとおり。仕様はこの事実の上に組む。

### 送信経路は2つ

| 経路 | 前処理 | 該当箇所 |
| --- | --- | --- |
| テキスト翻訳 | `Convert-YakuNumericUnits` → バッチ分割 → プロンプト | `Translation.ps1:1282` |
| ファイル翻訳 | 項目ごとに `Convert-YakuNumericUnits` → バッチ → プロンプト | `FileTranslation.ps1:1881` |

### Excelの数値セルは送信されていない

`Test-YakuShouldTranslateCell`（`FileProcessors.ps1:80-104`）が、数値・記号だけの
セル、日付、通貨表記、メール、URL、型式風トークンを翻訳対象から除外している。
`to_en` では日本語を含むセルだけが対象になる。

したがって**露出しているのは「日本語テキストの中に埋め込まれた数値」だけ**である。
表の数値セルはもともと送信されていない。本版の対象はこの埋め込み数値に限られる。

### 既存の数値前処理は「単位の英語化」であって秘匿ではない

`Convert-YakuNumericUnits`（`Translation.ps1:315-360`）は `72億円` → `72 oku`、
`1,234万円` → `12,340 k yen`、`5万台` → `50 k units` のように**単位だけ**を英語化する。
数値そのものは平文のまま送信される。

### 既存のマスキングは利用者の手作業

`Get-YakuMaskingPlaceholderTokens`（`Translation.ps1:300-303`）が拾うのは
`【…非開示】` という**利用者が自分で書いた**印である。`Convert-YakuNumericUnits` が
受け付ける `xx` / `xxx` も同様に手入力を想定している。
`Test-YakuMaskingPlaceholderIntegrity` はそれが往復で保たれたかを検証するだけで、
自動でマスクする機構は存在しない。

### 再試行時に平文数値をプロンプトへ載せている（要対処）

`New-YakuNumericCorrectionInstruction`（`Translation.ps1:414-421`）は
「`72 oku` というトークンを正確に出力せよ」という指示文を組み立て、
`Translation.ps1:962`、`FileTranslation.ps1:1684`、`FileTranslation.ps1:1967` から
**再送プロンプトへ連結している**。

本文をマスクしても、この経路から平文数値が出る。§6で必ず塞ぐ。

### 記法の衝突に注意すべき既存要素

| 記法 | 用途 | 該当箇所 |
| --- | --- | --- |
| `[[ID:n]]` | ファイル一括送信の項目ID | `FileTranslation.ps1:145` |
| `【…非開示】` | 利用者による手動マスク | `Translation.ps1:302` |
| `{key}` | プロンプトテンプレート変数 | `PromptBuilder.ps1:584` |
| `＜＞`（全角） | 見出し構造の照合。半角 `<>` はCopilotのレンダラーがHTMLタグとして隠す（V91.1） | README |

## §1 マスク対象と非対象の定義

### マスクしない

| 種別 | 例 | 備考 |
| --- | --- | --- |
| **符号** | `+`、`▲`、`△`、`マイナス` | 依頼元の許可により保持（決定事項#1） |
| **単位・スケール語** | `oku`、`k yen`、`k units`、`%`、`円`、`台`、`件` | 保持（決定事項#1） |
| **用語集に一致した語の内部** | `CX-90`、`CX-90単価改善` | 決定事項#4。§3で範囲を定義 |
| 西暦・和暦の年 | `2026年`、`FY2026`、`令和8年`、`26/3期`、`2026年度` | |
| 四半期・期・半期 | `第1四半期`、`1Q`、`Q1`、`上期`、`下期` | |
| 月・日 | `4月`、`3月末`、`4/1` | |
| 「1株当たり」等の定型句の1 | `1株当たり`、`一株当たり`、`1台当たり` | 直後の金額はマスクする |
| 箇条書き・見出しの番号 | `1.`、`(1)`、`①`、`第2章` | |
| 法令・規格・条番号 | `第3条`、`ISO 9001` | |
| バージョン番号 | `V91.60` | |

### マスクする（数値の大きさそのもの）

| 種別 | 例 |
| --- | --- |
| 金額の大きさ | `72`（`72 oku` の `72`） |
| 数量の大きさ | `50`（`50 k units` の `50`） |
| 比率・率の大きさ | `12.3`（`12.3%` の `12.3`） |
| 増減額・増減率の大きさ | `72`（`▲72 oku` の `72`） |
| 単位を伴わない裸の数値 | `1,250` |

### 判断に迷う数値は既定でマスクする

分類器が確信を持てない数値は**マスク側に倒す**。誤ってマスクしても訳文は
プレースホルダー経由で復元されるため実害は小さいが、誤って平文で送ると
取り返しがつかない。

### 「1株当たり」の扱い

「1株当たり」の `1` は非機密だが、**その直後に続く金額の大きさは機密**である。

```
1株当たり配当金は 120円 です。
→ 1株当たり配当金は 【N1】円 です。
```

`1株当たり` は定型句として文字列一致で除外し、金額側は通常どおりマスクする。

## §2 プレースホルダー記法

**`【N1】`〜`【Nn】` が置き換えるのは「数値の大きさ」だけとする。符号と単位は
プレースホルダーの外に残す。**

| 原文 | 単位変換後 | 送信 |
| --- | --- | --- |
| `72億円` | `72 oku` | `【N1】 oku` |
| `▲72億円` | `▲72 oku` | `▲【N2】 oku` |
| `+1,234万円` | `+12,340 k yen` | `+【N3】 k yen` |
| `12.3%` | `12.3%` | `【N4】%` |
| `5万台` | `50 k units` | `【N5】 k units` |
| `10〜20億円` | `10 oku〜20 oku` | `【N6】 oku〜【N7】 oku` |
| `72億円→85億円` | `72 oku→85 oku` | `【N8】 oku→【N9】 oku` |

記法の採用理由:

- 既存の `【…非開示】` と同じ文字クラスであり、モデルが「触ってはいけない塊」として
  扱う実績がある。
- `[[ID:n]]` と文字が重ならない。ファイル一括送信の項目IDと取り違えない。
- 半角山括弧のようにCopilotのレンダラーに隠されない（V91.1で確認済みの問題を回避）。
- Excelへ書き戻しても数式化しない（先頭が `=` `+` `-` `@` でない）。
- `{key}` のテンプレート展開（`PromptBuilder.ps1:584` の `\{(\w+)\}`）と衝突しない。

番号は**1バッチ内で一意**。バッチをまたいで再利用しない。
利用者が自分で書いた `【…非開示】` とは正規表現で区別できる
（`【N\d+】` と `【[^【】]*非開示】`）。両者は共存させる。

## §3 マスキングの適用位置と適用方向

### パイプライン

```
原文
 → Convert-YakuNumericUnits      単位の正規化（両方向。§3-2）
 → 用語集スパンの確定             ★新規: 非マスク範囲を先に決める（§3-3）
 → New-YakuNumericMaskMap        ★新規: 数値の大きさを【N…】へ
 → バッチ分割 → プロンプト → Copilot
 → 応答パース
 → プレースホルダー整合の検証（§6）
 → Restore-YakuNumericMask       ★新規: 【N…】を数値へ戻す
 → 訳文
```

単位変換を先に行う理由: `3兆2,000億円` → `32,000 oku` のような**桁の換算**を
伴うため、先にマスクすると換算できなくなる。

### §3-2 両方向で単位変換を行う（決定事項#2）

現行の単位変換は `to_en` のみに掛かっている
（`Translation.ps1:1282`、`FileTranslation.ps1:1878`）。この方向限定を外し、
**`to_jp` でも `Convert-YakuNumericUnits` を通す。**

`to_jp` の入力は英語・中国語だが、日英混在の資料では日本語単位（`億円`、`万台` 等）が
現れる。これを `to_en` と同じ正規化トークン（`oku` / `k yen` / `k units`）へ揃えることで、
プレースホルダーと単位の並びが方向によらず一定になる。

**`to_jp` で新たに生じる論点:**

- **出力側の単位表記。** 送信テキストが `【N1】 oku` のとき、日本語訳では
  `【N1】億円` になるのが自然である。プロンプトで対応を指示する（§5）。
- **監査の非対称性。** `to_en` は単位を逐語保持させるため「数値+単位」トークンの
  往復を照合できるが、`to_jp` は単位が訳されるため同じ照合ができない。
  方向で監査方法を変える（§6）。
- **英語由来の単位は変換対象外。** `billion` / `million` の入力は
  `Convert-YakuNumericUnits` の対象外であり、本版でも変換しない。
  これらは数値そのものがマスク対象になるため機密上の問題はない
  （`7.2 billion yen` → `【N1】 billion yen`）。

### §3-3 用語集に一致した範囲を保護する（決定事項#4）

`CX-90` のように**語の一部として数字を含む用語**をマスクすると、用語集の一致が
壊れ、訳語が崩れる。用語集に載っている語は非マスクを優先する。

**手順:**

1. 単位変換後・マスク前のテキストに対して、`Get-YakuRelevantGlossaryMatches`
   （`PromptBuilder.ps1:368`）で用語集の一致範囲（開始位置と長さ）を求める。
   対象は `glossary.csv` と `prompt_glossary.csv` の両方。
2. 一致した範囲を**保護スパン**として記録する。
3. マスキングは保護スパンの**外側だけ**に適用する。

**順序が重要である。** 現行は数値前処理の後に用語集照合を行っている
（`Translation.ps1:1289`、`FileTranslation.ps1:1887`）。マスクしてから照合すると
`CX-90単価改善` が `CX-【N1】単価改善` になり一致しなくなる。
**保護スパンは必ずマスク前のテキストから求める。**

**保護スパン内の数字は平文で送信される。** 用語集は利用者が管理するファイルなので、
機密数値を用語集へ登録しない運用が前提になる。§9でこの注意を表示する。

### §3-4 適用方向

マスキングは **`to_en` / `to_jp` の両方向**に適用する。機密性は方向に依存しない。

## §4 符号・単位を外に出すことの効果

符号と単位を出せることで、**当初案で想定していた大きな改造が不要になる**。

### 増減動詞との整合が保たれる

V90.6 で「増益・減益等の方向語が原文の `+` / `▲` を吸収し、数値を符号なしの
大きさに統一する」規則を入れている。これは**文脈依存**でコードでは判断できない。
符号がモデルに見えるため、**この規則は従来どおりモデル側で機能する**。

### 括弧化の規則を変えずに済む

`▲` の括弧化（`PromptBuilder.ps1:566`）は符号を見て行う規則である。
符号が見えるので、`▲【N1】 oku` → `(【N1】) oku` → 復元 → `(72) oku` と
既存の規則のまま通る。整形ロジックをプロンプトからコードへ移す必要がない。

### 訳質への影響が小さい

符号（増減の向き）と単位（金額・数量・比率の別）が見えるため、
モデルが選ぶ動詞・冠詞・単複は従来と同じ判断材料を持つ。隠れるのは大きさだけである。

**結果として、当初案にあった以下の変更は不要になった。**

- 符号を含めた1トークンのマスク
- 復元時のコード側での英語表記決定（括弧・符号の組み立て）
- プロンプトからの数値整形規則の全面削除
- 数値整合監査の全面置き換え

## §5 プロンプトの変更

### `to_en`: `Get-YakuNumericRulesSection`（`PromptBuilder.ps1:560-570`）へ追記

既存の4行は**そのまま残す**。符号・単位が見えるため引き続き機能する。
次の保護規則を追加する（英語で記述する）。

```
- Tokens of the form 【N1】, 【N2】 … are protected placeholders that stand for a
  numeric magnitude. Reproduce every placeholder exactly as written, the same
  number of times as the source. Never translate, reword, split, merge, or drop
  them, and never invent one that is not in the source.
- Signs (+, ▲) and units (oku, k units, k yen, %) around a placeholder follow the
  existing rules above. Apply those rules to the placeholder as if it were a number.
- Never replace a placeholder with a digit, an estimate, or a word such as
  "a certain amount".
```

最後の1行は重要である。プレースホルダーを見たモデルが「具体的な数値に
置き換えるべき」と解釈して数字を捏造する事故を防ぐ。

### `to_jp`: 数値規則セクションを新設する（決定事項#2に伴う）

現行 `numeric_rules` は `to_en` のみ（`PromptBuilder.ps1:609`）。
`to_jp` 用のセクションを追加し、**プレースホルダー保護**と**単位の日本語表記**を指示する。

```
- 【N1】、【N2】 … は保護プレースホルダーです。原文と同じ数だけ、そのままの表記で
  出力してください。翻訳・言い換え・分割・結合・削除をしないでください。
  原文にないプレースホルダーを作らないでください。
- プレースホルダーを数字や「一定額」等の語に置き換えないでください。
- 単位は日本語表記にしてください: oku → 億円 / k yen → 千円 / k units → 千台 /
  % → ％ は使わず % のまま。
- 符号は原文に従ってください。( ) で囲まれた数値は ▲ を用いた表記にしてください。
```

単位の対応は正規化トークンからの逆写像である。`k yen` は `1万円 = 10 k yen` の
関係で作られるため、`12,340 k yen` の自然な訳は `1億2,340万円` だが、
モデルに桁の再計算をさせるのは事故のもとになる。**`千円` への逐語対応を既定とし、
桁の繰り上げはさせない。**

### 発火条件

現行の発火条件（`PromptBuilder.ps1:562`）は数値・記号の存在を見ている。
**`【N\d+】` を含む場合も発火する**よう条件を追加し、`to_jp` でも評価する。

### 対象プロンプト

`prompts/text_translate_to_en.txt`、`text_translate_to_jp.txt`、
`file_translate_to_en.txt`、`file_translate_to_jp.txt`、`style_brief_rules.txt` に
数値の捏造・置換を促す記述がないか点検する。追加は上記の保護規則のみとする。

## §6 監査と再試行の変更

### `to_en`: 数値整合監査は「拡張」で足りる

`Get-YakuNumericAuditExpectations`（`Translation.ps1:362-380`）の数値パターンに
`【N\d+】` を加える。

```
現行: (?<num>[0-9][0-9,]*(?:\.[0-9]+)?|[xX]{2,})\s+(?<unit>oku|k units|k yen)
変更: (?<num>【N\d+】|[0-9][0-9,]*(?:\.[0-9]+)?|[xX]{2,})\s+(?<unit>oku|k units|k yen)
```

パーセントのパターンも同様に拡張する。これにより
`Test-YakuNumericIntegrity`（`Translation.ps1:395-412`）が `【N1】 oku` という
トークンの往復を検証するようになり、**既存の監査・再試行の仕組みがそのまま使える**。

`Get-YakuTokenOccurrenceCount`（`Translation.ps1:382-393`）は `[regex]::Escape` で
トークンを組み立てるため `【N1】` をそのまま扱える。
`ScaleCandidate`（10倍ずれの検出）はプレースホルダーに適用できないため空にする。

### `to_jp`: 単位が訳されるためトークン照合は行わない

`to_jp` では `【N1】 oku` が `【N1】億円` になる。数値+単位のトークン照合は
成立しないため、**`to_jp` では `Test-YakuNumericMaskIntegrity` による
プレースホルダー整合のみを検証する。**

単位の日本語表記が正しいかは §5 のプロンプト指示に委ね、監査対象にしない。

### `New-YakuNumericCorrectionInstruction` は自動的に安全になる

期待トークンが `【N1】 oku` になるため、生成される指示文に平文数値が入らない。

```
- 【N1】 oku: include the token 【N1】 oku exactly as written; it is currently missing.
```

**ただし実装時に必ず確認すること。** マスクされなかった数値（年号、用語集の保護
スパン内の数字など）が監査対象に入ると平文が指示文へ載る。
**指示文の生成時にプレースホルダーを含まない項目を除外する。**
§10-5の受容基準で検証する。

### プレースホルダー整合の追加検証

数値整合監査は「期待トークンが必要数以上あるか」しか見ない。
復元の安全のためには**過不足なく1対1**である必要があるため、
`Test-YakuNumericMaskIntegrity` を両方向で通す。

- 欠落: 訳文に無いプレースホルダー
- 重複: 原文より多く現れたプレースホルダー
- 混入: 原文に無い番号のプレースホルダー

### BRIEF は警告のみとする（決定事項#3）

BRIEF は原文の20〜30%へ圧縮するため、数値そのものが落ちることがある。
プレースホルダーの欠落がモデルの正当な省略なのか事故なのかを区別できない。

**BRIEF ではプレースホルダー欠落を再試行の理由にせず、確認警告に留める。**
FULL では従来どおり再試行対象とする。

欠落した `【N…】` は訳文から取り除き、原文の数値を挿入しない（省略された文脈へ
数値だけを戻すと誤読を招くため）。警告カテゴリは `numeric-placeholder-dropped-brief`。

### 復元順序

**検証に通ってから復元する。** 検証前に復元すると、欠落したプレースホルダーが
「数値が消えた訳文」として確定してしまう。

FULL で再試行上限に達しても解消しない場合は、既存方針（V91.42「翻訳経路に新たな
throw を増やさない」）に従い、**訳文を返しつつ確認警告を出す**。
未解決のプレースホルダーは原文の数値へ機械的に置き換え、
警告カテゴリ `numeric-placeholder-unresolved` を付ける。

### `Test-YakuMaskingPlaceholderIntegrity` は残す

利用者が自分で書いた `【…非開示】` の検証は用途が異なるため別関数として残す。
検出正規表現 `【[^【】]*非開示】` は `【N1】` にマッチしないため衝突しない。

## §7 キャッシュ

`Get-YakuTranslationCacheStore`（`Translation.ps1:41-54`）はプロセス内メモリの
ハッシュテーブルで、ディスクには書かれない。

### キーと値の両方をマスク済みにする

- **キー**: マスク後テキスト（`FileTranslation.ps1:1898` および `Translation.ps1` の
  テキスト経路で `Get-YakuTranslationCacheKey -Text` へ渡す値をマスク後にする）
- **値**: マスク済み訳文。復元は取り出すたびに、その回の `Map` で行う。

副次効果として、**大きさだけが違う定型文がキャッシュにヒットする**。
「売上高は【N1】 oku でした」のような表項目・定型文が多い資料でヒット率が上がる。

符号が本文に残るため `+【N1】 oku` と `▲【N1】 oku` は別キーになる。
訳し分けが必要な組み合わせが混ざらないので、この粒度で正しい。

### 契約フィンガープリントの更新

`Get-YakuTranslationContractFingerprint`（`Translation.ps1:73-115`）の対象に
マスキング仕様のバージョン識別子を含め、**旧キャッシュを確実に無効化する**。
マスクなしで生成された訳文がマスク経路で再利用されると復元が壊れる。

## §8 診断・ログ

- **`Map`（プレースホルダーと数値の対応）をログ・診断ファイル・キャッシュへ書かない。**
  出力してよいのは件数のみ。
- 送信ペイロードを記録する診断は、**マスク後のテキストだけ**を記録する。
- `full_text_diagnostics_enabled`（既定 `false`）が有効なときの原文保存は
  ローカル限定なので現行どおりでよいが、原文と `Map` を同じ場所に並べない。
- 通常ログに出す情報: `masked=12 kept=3 glossaryProtected=2 restored=12 unresolved=0`。

`numeric_masking_enabled` のような設定は**作らない**。機密要件は利用者が

## §10 受容基準

1. `to_en` / `to_jp` の両方向で、Copilot へ送信するプロンプトに §1 のマスク対象
   数値が平文で含まれないこと。**送信ペイロードを直接検査して確認する。**
2. 符号（`+` / `▲`）と単位（`oku` / `k yen` / `k units` / `%`）が送信テキストに
   残っていること。
3. 年号・四半期・箇条書き番号・「1株当たり」の `1` がマスクされずに残ること。
4. **用語集に一致した範囲の数字がマスクされず、用語集の一致が壊れないこと**
   （`CX-90単価改善` が従来どおり訳語へ置換されること）。
5. **再試行プロンプト（`New-YakuNumericCorrectionInstruction`）に平文数値が
   含まれないこと。** 非マスク数値（年号・用語集保護スパン）が指示文へ載らないこと。
6. 訳文で `【N…】` が原文と過不足なく1対1で再現され、復元後の数値が原文と一致すること。
7. `▲72億円` が既存規則どおり `(72) oku` へ、`+72億円` が `+72 oku` へ
   復元されること（従来と同じ出力）。
8. **`to_jp` で日本語単位（`億円` 等）へ訳されたうえで、プレースホルダーが
   保たれ復元されること。**
9. **BRIEF でプレースホルダーが落ちても再試行せず、警告のみで完走すること。**
   FULL では従来どおり再試行すること。
10. キャッシュのキー・値ともにマスク済みで、`Map` が保存されないこと。
11. マスク仕様の変更が契約フィンガープリントに反映され、旧キャッシュが無効化されること。
12. プレースホルダーが復元できない場合でも翻訳が完走し、確認警告が出ること
    （新たな throw を増やさない）。
13. 診断ファイル・ログに `Map` が出力されないこと。
14. 既存の `【…非開示】` の手動マスクが従来どおり機能すること。
15. Excelの数値セル・日付セルが従来どおり送信対象外であること。
16. モデルがプレースホルダーを数字へ置き換えた場合、検証で検出されること。

### 新規回帰テスト

`app/tools/Test-YakuV9160NumericMasking.ps1` を追加する。

- 分類: §1 の各行を最小例文で検証（マスクされる / されない）
- 用語集保護: `CX-90単価改善` を含む文で数字が保護され、用語集一致が保たれること
- 往復: マスク → 疑似応答 → 復元 で原文の数値が戻ること
- 符号・単位: `▲` / `+` / `%` / `oku` / `k yen` / `k units` が残ること
- 範囲・矢印: `【N1】 oku〜【N2】 oku`、`【N1】 oku→【N2】 oku` の往復
- 方向: `to_jp` で `【N1】億円` へ訳された応答からの復元
- BRIEF: 欠落時に再試行せず警告のみで完走すること
- 漏洩: 生成された送信ペイロードに平文数値が含まれないこと（**最重要**）
- 再試行: 補正指示文に平文数値が含まれないこと
- 異常系: プレースホルダーの欠落・重複・混入・数字への置換

## §11 対象外・既知の限界

### 数値マスキングは送信内容を非機密化しない

**本版は「数値の大きさ」だけを秘匿する。**社名、製品名、施策名、組織名、そして
文章そのもの（何がどう増減したかの説明）は平文で送信される。

「営業利益は▲【N1】 oku の減益となり、主因は【N2】 k yen の材料費高騰である」
という文は、金額を伏せても事業内容と**増減の向き**を開示している。

依頼どおり実装を進めるが、**送信内容全体の機密性を担保するものではない**点は
利用者・依頼元と共有しておく必要がある。文章自体の秘匿が必要なら、
外部サーバーを使わない構成の検討が別途要る。

### 決定に伴って受け入れた事項

- **桁のオーダーが単位から推測できる**（決定事項#1）。`oku`（10^8規模）か
  `k yen`（10^3規模）かで規模が分かる。金額そのものは分からない。
- **用語集に登録した語の数字は平文で送信される**（決定事項#4）。
  用語集は利用者が管理するため、運用上の注意で担保する（§9）。
- **BRIEF では数値が落ちても検出できない**（決定事項#3）。警告のみとするため、
  利用者が訳文を確認する前提になる。

### その他の限界

- **大小比較の訳**: 「AはBを上回る」型の文で、モデルは大きさを見られないため
  原文の語順・語彙に従うしかない。原文が明示していれば問題ないが、
  数値の比較から語を選ぶ余地はなくなる。
- **文中で語順が変わる訳**: プレースホルダーの位置は正しくても対応関係が
  入れ替わる可能性がある。検証では対応関係まで確認する。
- **`to_jp` の桁表記**: `12,340 k yen` は `1億2,340万円` が自然だが、
  桁の再計算をモデルにさせず `12,340千円` の逐語対応とする（§5）。
  自然さより事故防止を優先した判断である。

### 残る実装上の判断

   段階4で単独に検証する。
