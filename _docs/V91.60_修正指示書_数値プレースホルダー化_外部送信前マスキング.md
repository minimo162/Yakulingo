# YakuLingo V91.60 修正指示書（Copilot送信前の数値プレースホルダー化）

作成日: 2026-08-03 / 改訂: 2026-08-03（符号の保持と4件の方針決定を反映） / ベース: V91.59

利用者からの依頼:

- **Copilot への依頼は外部サーバーへの送信になるため、年号や「1株当たり」のような
  機密性のない数値を除き、数値はプレースホルダーに置き換えて送信し、受信後に復元する。**
- **数値がプラスかマイナスかという情報は保持してよい。**

本版は送信内容の機密性に関わる変更であり、翻訳品質契約より優先される。

## 背景: 現状で外部へ出ている数値

実装を確認した結果は次のとおり。仕様はこの事実の上に組む。

### 送信経路は2つ

| 経路 | 前処理 | 該当箇所 |
| --- | --- | --- |
| テキスト翻訳 | `Convert-YakuNumericUnits` → バッチ分割 → プロンプト | `Translation.ps1:1282` |
| ファイル翻訳 | 項目ごとに `Convert-YakuNumericUnits` → バッチ → プロンプト | `FileTranslation.ps1:1881` |

### Excelの数値セルは送信されていない

`Test-YakuShouldTranslateCell`（`FileProcessors.ps1:80-104`）が、数値・記号だけの
セル、日付、通貨表記、メール、URL、型式風トークンを翻訳対象から除外している。
`to_en` では日本語を含むセルだけが対象になる。

したがって**露出しているのは「日本語テキストの中に埋め込まれた数値」だけ**である。
表の数値セルはもともと送信されていない。本版の対象はこの埋め込み数値に限られる。

### 既存の数値前処理は「単位の英語化」であって秘匿ではない

`Convert-YakuNumericUnits`（`Translation.ps1:315-360`）は `72億円` → `72 oku`、
`1,234万円` → `12,340 k yen`、`5万台` → `50 k units` のように**単位だけ**を英語化する。
数値そのものは平文のまま送信される。

### 既存のマスキングは利用者の手作業

`Get-YakuMaskingPlaceholderTokens`（`Translation.ps1:300-303`）が拾うのは
`【…非開示】` という**利用者が自分で書いた**印である。`Convert-YakuNumericUnits` が
受け付ける `xx` / `xxx` も同様に手入力を想定している。
`Test-YakuMaskingPlaceholderIntegrity` はそれが往復で保たれたかを検証するだけで、
自動でマスクする機構は存在しない。

### 再試行時に平文数値をプロンプトへ載せている（要対処）

`New-YakuNumericCorrectionInstruction`（`Translation.ps1:414-421`）は
「`72 oku` というトークンを正確に出力せよ」という指示文を組み立て、
`Translation.ps1:962`、`FileTranslation.ps1:1684`、`FileTranslation.ps1:1967` から
**再送プロンプトへ連結している**。

本文をマスクしても、この経路から平文数値が出る。§6で必ず塞ぐ。

| 記法 | 用途 | 該当箇所 |
| --- | --- | --- |
| `[[ID:n]]` | ファイル一括送信の項目ID | `FileTranslation.ps1:145` |
| `【…非開示】` | 利用者による手動マスク | `Translation.ps1:302` |

## §1 マスク対象と非対象の定義

### マスクしない

| 種別 | 例 | 備考 |
| --- | --- | --- |
| **符号** | `+`、`▲`、`△`、`マイナス` | 依頼元の許可により保持（決定事項#1） |
| **単位・スケール語** | `oku`、`k yen`、`k units`、`%`、`円`、`台`、`件` | 保持（決定事項#1） |
| **用語集に一致した語の内部** | `CX-90`、`CX-90単価改善` | 決定事項#4。§3で範囲を定義 |
| **決算期・年度・年** | `2026年3月期`、`FY26/3`、`2026年度`、`FY2026`、`令和8年`、`第151期` | 決定事項#5。§1-2に列挙 |
| 四半期・期・半期 | `第1四半期`、`1Q`、`Q1`、`上期`、`下期` | |
| 月・日 | `4月`、`3月末`、`4/1` | |
| 「1株当たり」等の定型句の1 | `1株当たり`、`一株当たり`、`1台当たり` | 直後の金額はマスクする |
| 箇条書き・見出しの番号 | `1.`、`(1)`、`①`、`第2章` | |
| 法令・規格・条番号 | `第3条`、`ISO 9001` | |
| バージョン番号 | `V91.60` | |
| **証券コード** | `7261`、`(7261)` | 実サンプルに11件。公開情報 |
| **電話番号** | `082-282-1111` | マスクすると意味が壊れる |
| **1株当たり金額の単位語** | `円 銭` | 単位語であり数値ではない |

### マスクする（数値の大きさそのもの）

| 種別 | 例 |
| --- | --- |
| 金額の大きさ | `72`（`72 oku` の `72`） |
| 数量の大きさ | `50`（`50 k units` の `50`） |
| 比率・率の大きさ | `12.3`（`12.3%` の `12.3`） |
| 増減額・増減率の大きさ | `72`（`▲72 oku` の `72`） |
| **ポイント（％ポイント）の大きさ** | `0.7`（`0.7ポイント` の `0.7`） |
| 単位を伴わない裸の数値 | `1,250` |

### 判断に迷う数値は既定でマスクする

分類器が確信を持てない数値は**マスク側に倒す**。誤ってマスクしても訳文は
プレースホルダー経由で復元されるため実害は小さいが、誤って平文で送ると
取り返しがつかない。

### 「1株当たり」の扱い

「1株当たり」の `1` は非機密だが、**その直後に続く金額の大きさは機密**である。

```
1株当たり配当金は 120円 です。
→ 1株当たり配当金は 【N1】円 です。
```

`1株当たり` は定型句として文字列一致で除外し、金額側は通常どおりマスクする。

### §1-2 決算期・年度の表記（決定事項#5）

決算期は資料の見出し・表頭に頻出し、伏せると訳文が読めなくなる。
**次の形は非マスクとする。** 実装では**この列挙に一致するものだけ**を除外する。

| 形 | 例 | 正規表現の目安 |
| --- | --- | --- |
以下の `D` は **`[0-9０-９]`（半角と全角の両方）** を表す。§1-5 のとおり
実サンプルでは全角と半角が混在する。

| 形 | 実サンプルの例 | 正規表現の目安 |
| --- | --- | --- |
| 和文の決算期 | `2027年３月期`(27件)、`2026年3月期`(2件) | `D{2,4}\s*年\s*D{1,2}\s*月期` |
| 四半期 | `第１四半期`(45件)、`第1四半期`(2件) | `第\s*D\s*四半期` |
| 決算期+四半期 | `2027年３月期第１四半期` | 上記の連結として扱う |
| 年月日 | `2026年６月30日`、`2026年４月１日` | `D{4}\s*年\s*D{1,2}\s*月\s*D{1,2}\s*日` |
| 和文の年度 | `2026年度` | `D{2,4}\s*年度` |
| 和文の年 | `2026年`、`令和8年` | `D{2,4}\s*年`、`(?:令和|平成|昭和)\s*D{1,2}\s*年` |
| FY表記 | `FY26/3`、`FY2026`、`ＦＹ２６／３` | `FY\s?D{2,4}(?:\s?[/／]\s?D{1,2})?` |
| スラッシュ期 | `26/3期` | `D{2,4}\s?[/／]\s?D{1,2}\s?期` |
| 期の通番 | `第151期` | `第\s*D{1,3}\s*期` |
| 期間の範囲 | `2026年４月１日～2026年６月30日` | 上記の年月日の組み合わせとして扱う |

実サンプル（決算短信）では `2027年３月期` が27件、`第１四半期` が45件出現し、
**大半が全角**である。半角前提の正規表現では取りこぼす。

### §1-5 全角・半角の混在（実サンプルによる最重要の発見）

決算短信の実サンプルを解析した結果、**全角数字と半角数字が同一文書内どころか
同一トークン内で混在する**ことが分かった。

```
2026年６月30日     年=半角、月=全角、日=半角
2027年３月期       年=半角、月=全角
第１四半期(45件)   全角      第1四半期(2件)  半角
１．セグメント利益  箇条書き番号が全角
43.3％             パーセント記号が全角
△46,115           符号が △（▲ ではない）
```

**要件:**

1. 分類・照合は**全角を半角へ正規化した写像の上**で行う。
2. **置換とマスクは原文の字形を保つ。** 非マスク部分を半角へ書き換えてはならない
   （原文改変になる）。正規化はあくまで判定用の内部処理とする。
3. 復元は**マスクした時点の字形**へ戻す。単位変換を受けた金額は変換器が
   半角化しているため半角で戻り（`５，６０２億円` → `5,602 oku` → `【N1】 oku`
   → `5,602 oku`）、変換を受けなかった数値は原文の字形のまま戻る。
4. `Convert-YakuNumericUnits` は変換したトークンを半角へ正規化して出力する
   （`Translation.ps1:321-327`）。単位変換を受けた金額は半角になり、
   受けなかった数値（年月日・四半期・ポイント・％）は原文の字形のまま残る。
   **両方が混在する前提で分類器を書くこと。**

### §1-6 実サンプルで判明した未対応の単位

| 単位 | 実サンプルの例 | 現状 | 対応 |
| --- | --- | --- | --- |
| `ポイント` | `0.7ポイント増加` | `Convert-YakuNumericUnits` 未対応 | 数値のみマスクし単位は保持。英訳は `points` |
| `百万円` | 表頭に23件 | 同上 | 同上。単位変換の追加は本版の対象外 |
| `円 銭` | 1株当たり四半期純利益 | 同上 | 単位語として非マスク |

`ポイント` と `百万円` を `Convert-YakuNumericUnits` の変換対象へ加えるかは
**本版の対象外**とする。マスキングは単位変換の有無に関わらず数値部分に効くため、
機密性の要件は単位変換なしでも満たせる。

### §1-7 符号は `△` が実際に使われる

実サンプルでは `△` が151件、`▲` は0件だった。

`Get-YakuNumericRulesSection` の発火条件（`PromptBuilder.ps1:562`）は `▲△` の
両方を見ているが、**規則の文言（`PromptBuilder.ps1:566`）は `▲` しか挙げていない**。

```
現行: - ▲, negative minus signs, or マイナス: put parentheses around ...
改訂: - ▲, △, negative minus signs, or マイナス: put parentheses around ...
```

本版で数値規則を触るついでに `△` を明記する。実サンプルで主に使われる符号が
規則に書かれていないのは既存の不備である。

### §1-8 内部資料由来のデータからの補完

提供された実サンプルは**開示資料**（決算短信）であり、社内資料でしか現れない
表記は含まれない。リポジトリに同梱されている**社内資料由来のデータ**で補完した。

#### 回帰用例文（`tools/regression/V91.35_実数金額回帰例文.txt`、非機密化済み）

```
連結売上高は11,577億円、営業利益は343億円、…、前年差は(50)億円、
計画差は(400)億円、改善額は60億円。出荷台数は659千台、2万台。
```

```
売上高5,602億円となった。固定費改善は対前年4Q比248億円。
売上高５，６０２億円となった。固定費改善は対前年4Q比２４８億円。
```

判明した追加パターン:

| 形 | 例 | 扱い |
| --- | --- | --- |
| **半角括弧による負数** | `(50)億円`、`(400)億円` | 大きさをマスク。括弧を壊さない |
| 台数 | `659千台`、`2万台` | 変換後 `659 k units` / `20 k units` をマスク |
| 全角カンマ入り数値 | `５，６０２億円` | 変換器が `5,602 oku` へ正規化。その後マスク |
| 四半期の略記 | `4Q`、`1Q` | 非マスク |

#### `(50)億円` は単位変換を受けない（実測で確認）

`Convert-YakuNumericUnits` の正規表現は数値と単位が隣接する前提のため、
括弧が挟まる `(50)億円` はマッチしない。実測結果:

```
入力: 前年差は(50)億円、計画差は(400)億円  → 変換されず、そのまま
入力: 出荷台数は659千台、2万台            → 659 k units、20 k units
入力: 売上高５，６０２億円となった          → 売上高5,602 okuとなった
入力: 2兆4,967億円                       → 24,967 oku
入力: △46,115百万円                      → 変換されず（百万円は未対応）
入力: 0.7ポイント増加の43.3％              → 変換されず
```

したがって `(50)億円` はマスク後 `(【N1】)億円` となり、**単位の英訳もモデル任せ**
になる。これは既存の挙動であり本版で変えない。回帰テストで往復を確認する。

#### 用語集の source 側に数字を含むエントリが49件ある

`glossary.csv` を解析した結果:

| 種別 | 例 |
| --- | --- |
| 決算期 | `FY24/3 通期`、`FY25/3 上期`、`FY26/3 1Q`、`対 FY25/3 1H` |
| 四半期 | `1Q`、`2Q`、`3Q累計`、`2-3Q累計`、`第3四半期累計` |
| 月名 | `1月`〜`12月` |
| 持分比率 | `AAT 営業利益(50%)`、`MTMUS 営業利益(50%)` |
| ライン番号 | `営業利益 (L23除く評価)`、`(L24,25除く評価)`、`(L29除く評価)` |
| 型式名 | `MTMUS製(CX-50)` |

**§3-3 の用語集保護はこれらに効く。** 特に `AAT 営業利益(50%)` の `50%` や
ライン番号 `L23` は、単体で本文に出ればマスク対象だが、用語集に完全一致する
範囲では保護される。これが意図した挙動である。

`prompt_glossary.csv` 側は `MTMUS製(CX-50)` の1件のみ。

#### 表ラベルの完全一致はそもそも送信されない（重要な安全弁）

`Resolve-YakuFileExactGlossaryTranslations`（`FileTranslation.ps1:975`）は、
セル全体が `glossary.csv` に完全一致した項目を**ローカルで置換し、Copilot へ
送らない**。`FY26/3 1Q` や `AAT 営業利益(50%)` のような表ラベルは、
完全一致する限り外部へ出ない。

マスキングはこの経路を通らなかった項目に対する二段目の防御である。

#### 補完しきれていない範囲

社内資料そのものは入手できないため、次は未検証のまま残る。

- 社内特有の略語・単位（開示資料と回帰例文の範囲を超えるもの）
- 用語集に未登録の型式名（`CX-90` は用語集になく、`CX-50` はある）
- 予算・計画値など開示資料に現れない数値の表記

運用開始後、`masked` / `kept` の件数ログと利用者からの指摘で補正する。

### §1-3 例外の設計原則（決定事項#6）

「上位10社」「従業員5名」「3拠点」のような小さな計数は機密性が低いと思われるが、
**例外を増やすほど誤って平文を送る危険が上がる。**

- **例外は §1 の表と §1-2 に列挙したものだけ**とし、それ以外は一切追加しない。
- 例外の正規表現は**狭く厳密に**書く。広く書いた例外は機密数値を素通しする。
- マスク側は広く、例外側は狭く。判断に迷えばマスクする。
- 小さな計数を例外へ加えるかは、**利用者へのヒアリング結果を待って別途決める。**
  本版では追加しない（`上位【N1】社` のようになる）。

例外を1つ足すたびに §10 の回帰テストへ「その形はマスクされない」「似ているが
別物の形はマスクされる」の2件を追加すること。

### §1-4 手動マスク `【…非開示】` の廃止（決定事項#7）

現在は利用者が自分で `【…非開示】` と書く運用がある。自動マスクの導入により
**この運用は廃止し、保護の仕組みごと撤去する。**

#### なぜ従来は保護していたのか

保護の目的は「非開示という語を英訳させないこと」ではなかった。
`prompts/text_translate_to_en.txt` の R9・R10 と V91.36 修正指示書によれば:

- **R10**: 訳文に印が同じ数・同じ順序で残っているかをモデルに確認させる
- `Test-YakuMaskingPlaceholderIntegrity`: 同じ照合をコード側でも行う
- V91.36: 一般の `【】`（強調・見出し）は普通に訳し、`【…非開示】` だけ保護する
  という二分化を入れた

つまり**目的は「マスク印が消えていないことの検出」**であり、逐語再現は
文字列一致で照合を成立させるための手段だった。

#### 撤去してよい理由

- `【…非開示】` の中身は**利用者が伏せた後の文字列**である。訳されても消えても
  機密は漏れない。
- 英文資料に日本語の `【営業利益額非開示】` が残る方が不自然である。
- 手動マスクを廃止すれば、この記法は**過去資料にしか現れない**。
- 失うのは「印が黙って消えても気づけない」という検出能力だけで、これは機密性では
  なく忠実性の問題である。他のどの文にも同じリスクがある。
- 唯一の懸念「モデルが伏せ字を見て数値を捏造する」は、§5で新設する
  「プレースホルダーを数字や推定値に置き換えるな」の指示でカバーする。

#### 実装

- `Test-YakuMaskingPlaceholderIntegrity`（`Translation.ps1:423-449`）と
  その呼び出し（`Translation.ps1:475`）、`Get-YakuMaskingPlaceholderTokens`
  （`Translation.ps1:300-303`）を削除する。
- プロンプトの R9・R10 から `【…非開示】` の保護指示を外す（§5）。
- 過去資料の `【…非開示】` は通常のテキストとして訳される。
- 利用者へは「手動で伏せ字を書く必要はなくなりました」と案内する（§9）。
- 手入力の `xx` / `xxx`（`Convert-YakuNumericUnits` が受け付ける伏せ字）は
  数値ではないためマスク対象にならない。従来どおり通過させる。

利用者が「伏せた箇所を訳文でも一目で分かるようにしたい」と希望する場合は、
保護を戻す判断もありうる。その場合は §6 の検証を `【N…】` と同じ仕組みで
扱えばよく、後から追加できる。

## §2 プレースホルダー記法

**`【N1】`〜`【Nn】` が置き換えるのは「数値の大きさ」だけとする。符号と単位は
プレースホルダーの外に残す。**

| 原文 | 単位変換後 | 送信 |
| --- | --- | --- |
| `72億円` | `72 oku` | `【N1】 oku` |
| `▲72億円` | `▲72 oku` | `▲【N2】 oku` |
| `+1,234万円` | `+12,340 k yen` | `+【N3】 k yen` |
| `12.3%` | `12.3%` | `【N4】%` |
| `5万台` | `50 k units` | `【N5】 k units` |
| `10〜20億円` | `10 oku〜20 oku` | `【N6】 oku〜【N7】 oku` |
| `72億円→85億円` | `72 oku→85 oku` | `【N8】 oku→【N9】 oku` |

記法の採用理由:

- 既存の `【…非開示】` と同じ文字クラスであり、モデルが「触ってはいけない塊」として
  扱う実績がある。
- `[[ID:n]]` と文字が重ならない。ファイル一括送信の項目IDと取り違えない。
- 半角山括弧のようにCopilotのレンダラーに隠されない（V91.1で確認済みの問題を回避）。
- Excelへ書き戻しても数式化しない（先頭が `=` `+` `-` `@` でない）。
- `{key}` のテンプレート展開（`PromptBuilder.ps1:584` の `\{(\w+)\}`）と衝突しない。

番号は**1バッチ内で一意**。バッチをまたいで再利用しない。
利用者が自分で書いた `【…非開示】` とは正規表現で区別できる
（`【N\d+】` と `【[^【】]*非開示】`）。両者は共存させる。

## §3 マスキングの適用位置と適用方向

### パイプライン

```
原文
 → Convert-YakuNumericUnits      単位の正規化（両方向。§3-2）
 → 用語集スパンの確定             ★新規: 非マスク範囲を先に決める（§3-3）
 → New-YakuNumericMaskMap        ★新規: 数値の大きさを【N…】へ
 → バッチ分割 → プロンプト → Copilot
 → 応答パース
 → プレースホルダー整合の検証（§6）
 → Restore-YakuNumericMask       ★新規: 【N…】を数値へ戻す
 → 訳文
```

単位変換を先に行う理由: `3兆2,000億円` → `32,000 oku` のような**桁の換算**を
伴うため、先にマスクすると換算できなくなる。

### §3-2 両方向で単位変換を行う（決定事項#2）

現行の単位変換は `to_en` のみに掛かっている
（`Translation.ps1:1282`、`FileTranslation.ps1:1878`）。この方向限定を外し、
**`to_jp` でも `Convert-YakuNumericUnits` を通す。**

`to_jp` の入力は英語・中国語だが、日英混在の資料では日本語単位（`億円`、`万台` 等）が
現れる。これを `to_en` と同じ正規化トークン（`oku` / `k yen` / `k units`）へ揃えることで、
プレースホルダーと単位の並びが方向によらず一定になる。

**`to_jp` で新たに生じる論点:**

- **出力側の単位表記。** 送信テキストが `【N1】 oku` のとき、日本語訳では
  `【N1】億円` になるのが自然である。プロンプトで対応を指示する（§5）。
- **監査の非対称性。** `to_en` は単位を逐語保持させるため「数値+単位」トークンの
  往復を照合できるが、`to_jp` は単位が訳されるため同じ照合ができない。
  方向で監査方法を変える（§6）。
- **英語由来の単位は変換対象外。** `billion` / `million` の入力は
  `Convert-YakuNumericUnits` の対象外であり、本版でも変換しない。
  これらは数値そのものがマスク対象になるため機密上の問題はない
  （`7.2 billion yen` → `【N1】 billion yen`）。

### §3-3 用語集に一致した範囲を保護する（決定事項#4）

`CX-90` のように**語の一部として数字を含む用語**をマスクすると、用語集の一致が
壊れ、訳語が崩れる。用語集に載っている語は非マスクを優先する。

**手順:**

1. 単位変換後・マスク前のテキストに対して、`Get-YakuRelevantGlossaryMatches`
   （`PromptBuilder.ps1:368`）で用語集の一致範囲（開始位置と長さ）を求める。
   対象は `glossary.csv` と `prompt_glossary.csv` の両方。
2. 一致した範囲を**保護スパン**として記録する。
3. マスキングは保護スパンの**外側だけ**に適用する。

**順序が重要である。** 現行は数値前処理の後に用語集照合を行っている
（`Translation.ps1:1289`、`FileTranslation.ps1:1887`）。マスクしてから照合すると
`CX-90単価改善` が `CX-【N1】単価改善` になり一致しなくなる。
**保護スパンは必ずマスク前のテキストから求める。**

**保護スパン内の数字は平文で送信される。** 用語集は利用者が管理するファイルなので、
機密数値を用語集へ登録しない運用が前提になる。§9でこの注意を表示する。

### §3-4 バッチ分割はプレースホルダーを跨がない（実装必須）

`Split-YakuHardChunk`（`Translation.ps1:732-754`）は文末や空白が見つからない場合、
**`MaxChars` の位置で機械的に切る**。`【` `】` は文末記号でも空白でもないため、
`【N12】` の途中で切れる。`【N1` と `2】` に分かれると復元が壊れ、
監査はプレースホルダー欠落として検出する。

分割位置がプレースホルダーの内部に来る場合は、**その直前へ後退させる**。
`Split-YakuHardChunk` / `Split-YakuLongSegment` / `Split-YakuTextBatches` の
すべてに同じ保証を入れる。ファイル翻訳のバッチ組み立ても同様に確認する。

プレースホルダーは5〜7文字であり、後退幅は小さいため分割効率への影響はない。

### §3-5 マスク後は文字数が増減する

`1,234,567`（9文字）→ `【N1】`（5文字）は縮み、`72`（2文字）→ `【N1】`（5文字）は
膨らむ。小さい数値が多い資料では**送信文字数が増える**。

バッチ分割・プロンプト長ガード（`copilotPromptCharLimit`、V91.34）はマスク後の
テキストに対して働くため計算は正しいが、期待応答長の推定
（`copilotAnswerRatioText` / `copilotAnswerBaseText`）は入力長から見積もるため
ずれる可能性がある。実機検証で確認し、必要なら係数を再校正する（§12）。

### §3-6 適用方向

マスキングは **`to_en` / `to_jp` の両方向**に適用する。機密性は方向に依存しない。

### §3-7 逆翻訳経路は廃止する（決定事項#14）

`Invoke-YakuBackTranslation`（`Translation.ps1:1411`）は Copilot へプロンプトを
送るが、**現在どこからも呼ばれていない**（`src/` と `www/` を検索して確認済み）。

依頼元の判断により**機能ごと削除する**。マスキングを通さない送信経路を
コード上に残さないため。削除対象:

- `Invoke-YakuBackTranslation`（`Translation.ps1:1411-`）
- `Parse-YakuBackTranslationResponse`（`Translation.ps1:684-`）
- `Convert-YakuBackTranslationToHtml`（`Html.ps1:327-`）
- `New-YakuBackTranslatePrompt`（`PromptBuilder.ps1`）とその参照
- 逆翻訳用のプロンプトテンプレートがあれば同時に削除する

削除後、`Invoke-YakuCopilotPrompt` の呼び出し箇所が
**テキスト翻訳・ファイル翻訳とその再試行だけ**になることを確認する。

## §4 符号・単位を外に出すことの効果

符号と単位を出せることで、**当初案で想定していた大きな改造が不要になる**。

### 増減動詞との整合が保たれる

V90.6 で「増益・減益等の方向語が原文の `+` / `▲` を吸収し、数値を符号なしの
大きさに統一する」規則を入れている。これは**文脈依存**でコードでは判断できない。
符号がモデルに見えるため、**この規則は従来どおりモデル側で機能する**。

### 括弧化の規則を変えずに済む

`▲` の括弧化（`PromptBuilder.ps1:566`）は符号を見て行う規則である。
符号が見えるので、`▲【N1】 oku` → `(【N1】) oku` → 復元 → `(72) oku` と
既存の規則のまま通る。整形ロジックをプロンプトからコードへ移す必要がない。

### 訳質への影響が小さい

符号（増減の向き）と単位（金額・数量・比率の別）が見えるため、
モデルが選ぶ動詞・冠詞・単複は従来と同じ判断材料を持つ。隠れるのは大きさだけである。

**結果として、当初案にあった以下の変更は不要になった。**

- 符号を含めた1トークンのマスク
- 復元時のコード側での英語表記決定（括弧・符号の組み立て）
- プロンプトからの数値整形規則の全面削除
- 数値整合監査の全面置き換え

## §5 プロンプトの変更

> **設計方針との関係**: `_docs/設計方針_翻訳アーキテクチャ見直し.md` のとおり、
> 現在のプロンプトは禁止の散文が中心で、規則の追加が部分最適を生んでいる。
> 本版で追加する `【N…】` の保護規則は、**最初から決定表の形で書く**。
> 同様に、本版の回帰テストは同文書 §4-E の評価基盤の部分実装として設計する。

### R9・R10 から手動マスクの保護指示を外す（決定事項#7）

`prompts/text_translate_to_en.txt` の R9・R10 を改める。

```
現行 R9 : Reproduce every 【...非開示】 masking placeholder exactly as written.
          Other 【...】 are emphasis/heading brackets: translate the content
          normally and keep the 【】 brackets.
改訂 R9 : Reproduce every 【N1】, 【N2】 … placeholder exactly as written.
          Other 【...】 are emphasis/heading brackets: translate the content
          normally and keep the 【】 brackets.
現行 R10: ... and retain every 【...非開示】 masking placeholder in the same
          count and order.
改訂 R10: ... and retain every 【N…】 placeholder in the same count and order.
```

**R9 の後半は必ず残すこと。** 一般の `【】`（強調・見出し）を普通に訳す指示が
失われると、見出しの `【】` まで保護されてしまう。
`【N…】` はその例外として先に書く順序を守る。

同じ点検を `text_translate_to_jp.txt`、`file_translate_to_en.txt`、
`file_translate_to_jp.txt` にも行う。

### `to_en`: `Get-YakuNumericRulesSection`（`PromptBuilder.ps1:560-570`）へ追記

既存の4行は**そのまま残す**。符号・単位が見えるため引き続き機能する。
次の保護規則を追加する（英語で記述する）。

```
- Tokens of the form 【N1】, 【N2】 … are protected placeholders that stand for a
  numeric magnitude. Reproduce every placeholder exactly as written, the same
  number of times as the source. Never translate, reword, split, merge, or drop
  them, and never invent one that is not in the source.
- Signs (+, ▲) and units (oku, k units, k yen, %) around a placeholder follow the
  existing rules above. Apply those rules to the placeholder as if it were a number.
- Never replace a placeholder with a digit, an estimate, or a word such as
  "a certain amount".
```

最後の1行は重要である。プレースホルダーを見たモデルが「具体的な数値に
置き換えるべき」と解釈して数字を捏造する事故を防ぐ。

### `to_jp`: 数値規則セクションを新設する（決定事項#2に伴う）

現行 `numeric_rules` は `to_en` のみ（`PromptBuilder.ps1:609`）。
`to_jp` 用のセクションを追加し、**プレースホルダー保護**と**単位の日本語表記**を指示する。

```
- 【N1】、【N2】 … は保護プレースホルダーです。原文と同じ数だけ、そのままの表記で
  出力してください。翻訳・言い換え・分割・結合・削除をしないでください。
  原文にないプレースホルダーを作らないでください。
- プレースホルダーを数字や「一定額」等の語に置き換えないでください。
- 単位は日本語表記にしてください: oku → 億円 / k yen → 千円 / k units → 千台 /
  % → ％ は使わず % のまま。
- 符号は原文に従ってください。( ) で囲まれた数値は ▲ を用いた表記にしてください。
```

単位の対応は正規化トークンからの逆写像である。`k yen` は `1万円 = 10 k yen` の
関係で作られるため、`12,340 k yen` の自然な訳は `1億2,340万円` だが、
モデルに桁の再計算をさせるのは事故のもとになる。**`千円` への逐語対応を既定とし、
桁の繰り上げはさせない。**

### 発火条件

現行の発火条件（`PromptBuilder.ps1:562`）は数値・記号の存在を見ている。
**`【N\d+】` を含む場合も発火する**よう条件を追加し、`to_jp` でも評価する。

### 対象プロンプト

`prompts/text_translate_to_en.txt`、`text_translate_to_jp.txt`、
`file_translate_to_en.txt`、`file_translate_to_jp.txt`、`style_brief_rules.txt` に
数値の捏造・置換を促す記述がないか点検する。追加は上記の保護規則のみとする。

## §6 監査と再試行の変更

### `to_en`: 数値整合監査は「拡張」で足りる

`Get-YakuNumericAuditExpectations`（`Translation.ps1:362-380`）の数値パターンに
`【N\d+】` を加える。

```
現行: (?<num>[0-9][0-9,]*(?:\.[0-9]+)?|[xX]{2,})\s+(?<unit>oku|k units|k yen)
変更: (?<num>【N\d+】|[0-9][0-9,]*(?:\.[0-9]+)?|[xX]{2,})\s+(?<unit>oku|k units|k yen)
```

パーセントのパターンも同様に拡張する。これにより
`Test-YakuNumericIntegrity`（`Translation.ps1:395-412`）が `【N1】 oku` という
トークンの往復を検証するようになり、**既存の監査・再試行の仕組みがそのまま使える**。

`Get-YakuTokenOccurrenceCount`（`Translation.ps1:382-393`）は `[regex]::Escape` で
トークンを組み立てるため `【N1】` をそのまま扱える。
`ScaleCandidate`（10倍ずれの検出）はプレースホルダーに適用できないため空にする。

### `to_jp`: 単位が訳されるためトークン照合は行わない

`to_jp` では `【N1】 oku` が `【N1】億円` になる。数値+単位のトークン照合は
成立しないため、**`to_jp` では `Test-YakuNumericMaskIntegrity` による
プレースホルダー整合のみを検証する。**

単位の日本語表記が正しいかは §5 のプロンプト指示に委ね、監査対象にしない。

### `New-YakuNumericCorrectionInstruction` は自動的に安全になる

期待トークンが `【N1】 oku` になるため、生成される指示文に平文数値が入らない。

```
- 【N1】 oku: include the token 【N1】 oku exactly as written; it is currently missing.
```

**ただし実装時に必ず確認すること。** マスクされなかった数値（年号、用語集の保護
スパン内の数字など）が監査対象に入ると平文が指示文へ載る。
**指示文の生成時にプレースホルダーを含まない項目を除外する。**
§10-5の受容基準で検証する。

### プレースホルダー整合の追加検証

数値整合監査は「期待トークンが必要数以上あるか」しか見ない。
復元の安全のためには**過不足なく1対1**である必要があるため、
`Test-YakuNumericMaskIntegrity` を両方向で通す。

- 欠落: 訳文に無いプレースホルダー
- 重複: 原文より多く現れたプレースホルダー
- 混入: 原文に無い番号のプレースホルダー

### BRIEF は警告のみとする（決定事項#3）

BRIEF は原文の20〜30%へ圧縮するため、数値そのものが落ちることがある。
プレースホルダーの欠落がモデルの正当な省略なのか事故なのかを区別できない。

**BRIEF ではプレースホルダー欠落を再試行の理由にせず、確認警告に留める。**
FULL では従来どおり再試行対象とする。

欠落した `【N…】` は訳文から取り除き、原文の数値を挿入しない（省略された文脈へ
数値だけを戻すと誤読を招くため）。警告カテゴリは `numeric-placeholder-dropped-brief`。

### 復元順序

**検証に通ってから復元する。** 検証前に復元すると、欠落したプレースホルダーが
「数値が消えた訳文」として確定してしまう。

FULL で再試行上限に達しても解消しない場合は、既存方針（V91.42「翻訳経路に新たな
throw を増やさない」）に従い、**訳文を返しつつ確認警告を出す**。
未解決のプレースホルダーは原文の数値へ機械的に置き換え、
警告カテゴリ `numeric-placeholder-unresolved` を付ける。

### 手動マスクの検証を撤去する（決定事項#7）

検証対象は `【N\d+】` だけとする。`【…非開示】` の照合は行わない（§1-4）。

削除するもの:

- `Test-YakuMaskingPlaceholderIntegrity`（`Translation.ps1:423-449`）
- その呼び出し（`Translation.ps1:475`）
- `Get-YakuMaskingPlaceholderTokens`（`Translation.ps1:300-303`）
- 警告カテゴリ `placeholder-integrity`（`Translation.ps1:987`）のうち
  手動マスク由来の経路

自動マスクの検証は `Test-YakuNumericMaskIntegrity` に一本化する。

## §7 キャッシュ

`Get-YakuTranslationCacheStore`（`Translation.ps1:41-54`）はプロセス内メモリの
ハッシュテーブルで、ディスクには書かれない。

### キーと値の両方をマスク済みにする

- **キー**: マスク後テキスト（`FileTranslation.ps1:1898` および `Translation.ps1` の
  テキスト経路で `Get-YakuTranslationCacheKey -Text` へ渡す値をマスク後にする）
- **値**: マスク済み訳文。復元は取り出すたびに、その回の `Map` で行う。

副次効果として、**大きさだけが違う定型文がキャッシュにヒットする**。
「売上高は【N1】 oku でした」のような表項目・定型文が多い資料でヒット率が上がる。

符号が本文に残るため `+【N1】 oku` と `▲【N1】 oku` は別キーになる。
訳し分けが必要な組み合わせが混ざらないので、この粒度で正しい。

### 契約フィンガープリントの更新

`Get-YakuTranslationContractFingerprint`（`Translation.ps1:73-115`）の対象に
マスキング仕様のバージョン識別子を含め、**旧キャッシュを確実に無効化する**。
マスクなしで生成された訳文がマスク経路で再利用されると復元が壊れる。

## §8 診断・ログ

- **`Map`（プレースホルダーと数値の対応）をログ・診断ファイル・キャッシュへ書かない。**
  出力してよいのは件数のみ。
- **保持範囲は「翻訳要求の処理中（画面表示まで）」とする**（決定事項#12）。
  BRIEF で落ちた数値を平文つきで警告表示するため、応答の描画まで `Map` を
  メモリ上に保持する。描画後に破棄する。ディスクへは書かない。
- 送信ペイロードを記録する診断は、**マスク後のテキストだけ**を記録する。
- `full_text_diagnostics_enabled`（既定 `false`）が有効なときの原文保存は
  ローカル限定なので現行どおりでよいが、原文と `Map` を同じ場所に並べない。
- 通常ログに出す情報: `masked=12 kept=3 glossaryProtected=2 restored=12 unresolved=0`。

## §11 対象外・既知の限界

### 数値マスキングは送信内容を非機密化しない

**本版は「数値の大きさ」だけを秘匿する。**社名、製品名、施策名、組織名、そして
文章そのもの（何がどう増減したかの説明）は平文で送信される。

「営業利益は▲【N1】 oku の減益となり、主因は【N2】 k yen の材料費高騰である」
という文は、金額を伏せても事業内容と**増減の向き**を開示している。

依頼どおり実装を進めるが、**送信内容全体の機密性を担保するものではない**点は
利用者・依頼元と共有しておく必要がある。文章自体の秘匿が必要なら、
外部サーバーを使わない構成の検討が別途要る。

### 決定に伴って受け入れた事項

- **桁のオーダーが単位から推測できる**（決定事項#1）。`oku`（10^8規模）か
  `k yen`（10^3規模）かで規模が分かる。金額そのものは分からない。
- **用語集に登録した語の数字は平文で送信される**（決定事項#4）。
  用語集は利用者が管理するため、運用上の注意で担保する（§9）。
- **M365 Copilot 側にマスク済みの会話履歴が残る**（決定事項#10）。
  送信したテキストは外部サービスの履歴に蓄積される。マスキングはその中身から
  数値を除くだけで、送信と保持そのものは止まらない。マスク済みであれば許容、
  という判断を依頼元から得ている。
- **小さな計数もマスクされる**（決定事項#6）。`上位【N1】社` のような訳文になる。
  読みにくさより漏洩防止を優先した判断である。
- **BRIEF では数値が落ちても検出できない**（決定事項#3）。警告のみとするため、
  利用者が訳文を確認する前提になる。

### その他の限界

- **大小比較の訳**: 「AはBを上回る」型の文で、モデルは大きさを見られないため
  原文の語順・語彙に従うしかない。原文が明示していれば問題ないが、
  数値の比較から語を選ぶ余地はなくなる。
- **文中で語順が変わる訳**: プレースホルダーの位置は正しくても対応関係が
  入れ替わる可能性がある。検証では対応関係まで確認する。
- **`to_jp` の桁表記**: `12,340 k yen` は `1億2,340万円` が自然だが、
  桁の再計算をモデルにさせず `12,340千円` の逐語対応とする（§5）。
  自然さより事故防止を優先した判断である。
