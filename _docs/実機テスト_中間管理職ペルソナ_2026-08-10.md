## シチュエーション5: 未公開の数字を伏せて英訳

「来期の営業利益計画は152億円、売上高計画は2,340億円です。」を英訳。

- 訳文: `152 oku` / `2,340 oku`。**oku 表記の単位規約が効いている**（シチュエーション6の論点も先取り）
- ログで実際のマスクを確認: `Numeric masking. location=text masked=8 kept=0` →
  `protected-receipt-final masked=0 kept=8`。送信時に伏せ、受信後に戻している
- 画面表示: 「2件の数値を伏せてCopilotへ送り、訳案では元の数値に戻しました。」

### 判定: 部分的に不足

マスクは**確実に効いている**。しかし画面が出すのは**件数だけ**で、
「自分のあの数字（152億・2,340億）が伏せられたか」は確認できない。
1件取りこぼしても利用者は気づけない。
「この数字は未公開だから隠したい」という動機で使う人には、件数は答えになっていない。

### 修正（実施済み）

「伏せた数値を確かめる」を折りたたみで追加し、伏せた実値を `[[N1]] 152億` の形で並べる。
6件までは開いた状態、それ以上は畳む。

**実装上の判断**: 対応表(Map)を結果オブジェクトへ運ぶ案は採らなかった。
`Translation.ps1:1744-1745` に「対応表(Map)は結果オブジェクトへ載せない(§8)」という契約があり、
quick 以外の経路の結果まで汚すため。代わりに画面へ渡す直前に**原文から作り直す**。
これは製品自身が再依頼経路（`Translation.ps1:1789-1794`「割り当ては原文だけで決まる」）で
既に依存している前提であり、新しい仮定を持ち込まない。

クライアント側で数値を検出する案は捨てた。漢数字・英語綴り数・保護スパンをJSで再現できず、
照合が本体とずれる。「152億円は伏せました」という嘘を出す危険があり、件数だけの現状より悪い。

**安全弁**: 作り直した件数が保存済みの件数と食い違ったら値を出さず、件数表示へ落とす。

安全性の確認:
- QuickArtifact はメモリのみ・TTL30分。ディスクへ書かないことは既存検査が固定している
- quick経路は `diagnostics_level` を強制的に standard へ落とすので、実値はログに出ない
- `/api/quick/jobs/{id}` の応答は元から `source_text`/`translation` を実値で返しており、露出面は増えない

### 再テスト（合格）
`[[N1]] 152` `[[N2]] 2,340` が最初から開いた状態で並ぶ。値は17px。
注記「この一覧はこのパソコンの中だけで作っています。Copilotへは記号で送りました。」

## シチュエーション6: 社内資料を丸ごと英訳（資料翻訳）

社内資料8行（売上高3,120億円・営業利益152億円・前年138億円・8.2%・10.1%・24億円・18.5%・3.4%）を
「長い文章を貼り付ける」から取り込み、「残りの訳案を作る」を実行。

### 合格した点

**進捗表示・キャンセル・完了通知が、今回の実装どおり実機で動いた。**

| 経過 | 表示 |
|---|---|
| 1秒 | 翻訳中 10% ／ Copilotの返事を待っています ／ 0秒経過 ／ **翻訳をやめる** |
| 2秒 | Copilotへ送っています 28% ／ 入力 421字 |
| 4秒 | Copilotの返事を待っています 39% |
| 6秒 | 訳文を受け取っています 43% ／ Copilotが訳文を書いています（0字ぶん受け取りました。全体はおよそ716字です） |
| 10秒 | 69% ／ 520字ぶん受け取りました |
| 完了 | タスクバーが「✔ 翻訳が終わりました」 |

- 「翻訳をやめる」は全サンプルで存在した（以前は1秒で消えていた）
- タスクバーのタイトルが % を追う
- `oku` 表記が効いている（`3,120 oku` `24 oku`）
- 訳質は良い。「在庫調整の影響により」「期初計画を据え置きます」なども自然

軽微: 1バッチしかないのに「翻訳中（1/1 回目）」と出る → 修正済み（total>1 のときだけ付ける）

### 不合格: 2行が訳文なしで戻る

8行中2行が空。ログ:

```
File batch parsed. expected=8 received=8 missingIds= reason=normal
[WARN] Numeric mask integrity. cat-ID-1 missing=0 duplicated=0 unexpected=0 outOfOrder=True [order=[[N3]],[[N2]],[[N1]]]
[WARN] Numeric mask integrity. cat-ID-3 missing=0 duplicated=0 unexpected=0 outOfOrder=True [order=[[N1]],[[N3]],[[N2]]]
```

**Copilot は全8行返している。アプリが2行を捨てた。**
`Translation.ps1:927` が数値の並び順違いを不合格とし、`CatProject.ps1:2029` が
`$Map.Remove($idx); continue` で訳文ごと破棄している。

捨てられた2行は、いずれも**英語として正しい語順**:
- 「2027年3月期 第1四半期」→ "first quarter of the fiscal year ending March 2027"（2027/3/1 が入れ替わる）
- 「152億円で、前年同期の138億円から10.1%の増益」→ "up 10.1% from 138 oku"（138 と 10.1 が入れ替わる）

`missing=0 duplicated=0 unexpected=0` なので、原文の数値は過不足なく1回ずつ入っている。
日英で語順が変わるのは当然で、決算文では頻出する。

利用者への伝わり方は最低限ある（「訳あり6行・残り2行」「未翻訳 2」「行に未翻訳の印」）が、
**なぜ空なのかは分からない**。もう一度押しても、同じ理由でまた捨てられる。

### 根拠が成立していなかった

`Translation.ps1:904-905` のコメントはこう書いていた:

> 個数が同じでもN1/N2の順序を入れ替えると、売上高と利益など別の勘定へ実値を戻してしまう。

**これは事実と違う。** `Restore-YakuNumericMask`（`Translation.ps1:861-876`）は
`$result.Replace($token, $replacement)` でトークン名で置換する。
`[[N2]]` は文中のどこにあっても N2 の実値に戻る。順序が変わっても実値は取り違えない。

順序検査が実際に見ているのは「モデルが勘定と数値の対応を取り違えたかもしれない」という
意味の疑いであって、復元の安全ではない。そして自然な語順変更と取り違えを、
トークン列だけでは区別できない。**訳文を捨てる根拠が無い。**

### 修正（実施済み）

1. `Translation.ps1:927` の `Ok` から `-not $outOfOrder` を外した。
   `Ok` は「実値へ戻して安全か」だけを表す述語に戻した。`OutOfOrder` は戻り値に残る
2. `CatProject.ps1` の破棄を原因別にした。捨てるのは
   missing / duplicated / unexpected のときだけ（§8「数値が抜けた訳は欠陥」どおり）。
   順序だけなら訳文を残し、「並び順が原文と違います。訳文は取り込みました」と警告する
3. 会計期の除外規則を `Get-YakuFiscalPeriodMaskTokens` に集約し、
   `年度第◯四半期` に加えて `◯年◯月期（第◯四半期）` も扱う。
   従来は Translation.ps1 と CatProject.ps1 に別実装があり、**両方が同じ漏れ**を持っていた
   （§9「検査が、閉じようとした穴と同じ形の穴を持っていた」の再来）
4. `Test-YakuV9162Horizon1.ps1` の該当検査を新しい契約へ更新

**安全性**: 疑わしい行を止める網は残っている。確認時QCの `numeric-value-order-mismatch` が
`Severity='error'` で確定を止め、出力は確認済みの行しか通らない。
違いは「訳文が消える」から「訳文は残るが確定できない」になったこと。人が直せる。

## シチュエーション7: 有価証券報告書の3way翻訳

前年度の日本語・前年度の英語・当年度の日本語を貼り付けて開始。

### 合格した点

- **3wayの分類が正しい**: 前回と同じ2／変更あり1／今回追加1
- **候補ペインに前回訳が出所付きで出る**:
  「前回の資料の訳／有価証券報告書_2027年3月期（前回版）／前回版 段落 1」
  `Ctrl+1` の案内つき、「この訳を挿入」で挿入できる
- **挿入の履歴が残る**: 「この参考訳から挿入（その後編集なし）・…・前回版 段落 1」
  「使った参考訳を確認」で原文・訳文も見られる
- 自動では反映しない（§0の約束どおり）。挿入は利用者の明示操作
- 1兆3,150億円 → `13,150 oku` の桁換算は正しい
- **「確認済みの行だけコピー」が機能する**:
  「全 4 行のうち、確認済みの 1 行だけをコピーしました。まだ確認していない 3 行は入っていません。」

コーパスからの参考訳は、この内容が取り込み済みコーパスに無いため提示されなかった。
§4-3 のとおり pairs が配布物に入らない問題は別途残っている。

### 未解決の欠陥: アプリ自身の単位変換を、アプリ自身のQCが拒否する

原文「当連結会計年度の売上高は1兆3,150億円となりました。」
訳文「Net sales for the current consolidated fiscal year were 13,150 oku.」（換算は正しい）

確認済みにできない。QCの指摘:
> 原文にある数字が、訳文で違う値になっているか、抜けています。
> 原文に無い数字が訳文に入っています。余分な数字を消してください。

原文から `1`（兆）と `3,150` を、訳文から `13,150` を抽出して突き合わせているため。
**1兆単位の金額を含む行は、確認済みにできず出力に載せられない。**
有価証券報告書・決算短信では頻出する。

これは今回直した「登録した略語（1H・Q1）をQCが拒否する」と**まったく同じ型**である。
ロードマップ §4-1 が「CATだけ単位変換を通らない」として既に開いている領域でもある。

今回は手を付けていない。数値QCに二度目の手を入れることになり、
順序の件と同じだけの検証（どの型を許し、どの型を止めるか）が要るため。
当面の回避策は「確認済みの行だけコピー」で、該当行を外して持ち帰れる。

- 「続きから」は1件＋「ほかに保存した作業が 9 件あります」。**「文字を大きく」を押しても

- `3,120 oku` → `3,120億円` の逆方向の換算も正しい

### 目視でしか出なかった欠陥（修正済み）

**1. 「場所」列で日本語が1文字ずつ縦に折り返される**

ボタン名を「次の行と結合」→「次の行とつなげて1文にする」と長くした際、
116px の場所列に入ることを確認していなかった。実機では縦一列になって読めない。
→ 繋ぎ直しのボタンを幅のある訳文セル側へ移し、ボタン内は改行させないようにした。
検査も「CSSのvisibilityで隠す」という字面から「開いている行にだけ描く」という保証へ変えた。

**2. 和訳の作業では「短くする」も「この指示で直す」も一切使えない**

画面に PowerShell の生エラーが出た:
> パラメーター 'Mode の引数を確認できません。引数 "" は、ValidateSet 属性で指定された
> セット "full,brief" に属していません。

`Translation.ps1` が `$mode = if ($Direction -eq 'to_en') { $Style } else { '' }` としており、
和訳で空文字を渡して ValidateSet に弾かれていた。
`Get-YakuTextRequiredLabels` は to_jp では Mode を見ずに JAPANESE_TEXT を返すので、
既定の `full` を渡せばよい。→ 修正し、実機で「短くする」が成功することを確認
（`第1四半期の売上高は3,120億円、前年同期比8.2%増。`）。

既存の Revise 検査は**プロンプト生成しか見ておらず**、その先の解析呼び出しを通していなかった。
そこまでは Copilot 往復なしでは守れないので、空 Mode を渡さないことを回帰に足した。

**3. プライバシー表記が既定のウィンドウで折り返しの下にある**

「金額などの数値は、Copilotへ送る前に自動で伏せます。社名・人名・文章はそのまま送信されます。」

## 追記 2026-08-11 いちばん多く踏んだ穴は「詳細度の継ぎ足し」だった

利用者から「訳文が切れる」「表示する行の数字が色の関係で見えない」と再度の指摘。
原因はひとつに集約できた。`styles.css` の塗りの基本ルールである。

```
button:not(.secondary-button):not(.tab-button):not(.file-clear-button):not([disabled])
```

`:not()` は連ねると1つにつき class 1個ぶん詳細度が積み上がる。無効ボタンのコントラストを
直すために `:not([disabled])` を足した時点で (0,3,1) が (0,4,1) になり、CAT側の部品が
持つ上書き（いずれも (0,3,1)）を全部踏み潰していた。

| 巻き添えになった部品 | 見えていた症状 |
| --- | --- |
| 左ナビの絞り込み | 非選択が紺色で塗られ、件数が **1.05:1**（ほぼ不可視） |
| 点検タブ | 画面右上に紺色の帯が中途半端に見える |
| 一覧の行を開くボタン | 閉じている行の原文・訳文が紺色の箱。脇役がいちばん目立つ |

`:not()` を**リスト形**にすると、詳細度は「引数の中でいちばん強いもの1つぶん」しか
積まない。(0,1,1) まで落として、状態を足すたびに詳細度を継ぎ足す作りをやめた。

```
button:not(.secondary-button, .tab-button, .file-clear-button, [disabled])
```

### 教訓

実測は正しかったが、**測る対象を絞りすぎていた**。行の高さと横幅の配分だけを見て、
「詰めた結果ラベルが入るか」を見ていなかった。数値で確かめるときは、変えた値だけでなく
**その値に依存しているものが壊れていないか**まで測ること。
