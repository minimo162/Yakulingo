- 総語数への影響なし（用語集はマッチベース注入）

## 3.【必須・確認】file経路前処理の generated=0 の妥当性判別

### 背景
ファイル翻訳（250KB・2バッチ・アイテム123件）で前処理が全アイテム
generated=0、監査も checked=0 だった。ログ配線（location=file-ID-n /
file-final-ID-n）は正常稼働している。財務ブックは「数値はセル値・
単位は列見出し」の構造が普通なので、セル原文に単位付きテキストが
無いのが自然な説明だが、「原文に本当に無い」のか「file経路の前処理が
対象テキストを受け取れていない」のかをログだけでは判別できない。

### 判別手順（コード精査済みの前提を反映）
コード確認の結果: file経路の呼び出しは正しい位置にある
（FileTranslation.ps1:1876、unique items生成直後に$item.Textへ適用、
用語集マッチ・キャッシュキーより前）。関数自体はテキスト経路の
generated=14で実証済み。よって容疑は「アイテムのText内容が期待と
違う」ことに絞られる。

1. **ミニブック判別テスト（2分で決着）**: 新規ブックのセルに半角で
   「売上高5,602億円となった。固定費改善は対前年4Q比248億円。」と
   入力して翻訳し、ログの generated を確認:
   - generated=2 → 配線正常。原因は本番ブック側の文字種（全角等）で
     下記2の修正で解決
   - generated=0 → 配線バグ。$item.Text の実内容をダンプして調査
2. **全角対応（判別結果に関わらず実装）**: 数字トークンregexを
   全角対応に拡張する:
   ```powershell
   $num = '(?:[\d０-９][\d０-９,，\.．]*|[xXｘＸ]{2,})'
   ```
   置換時は全角→半角正規化してからトークン生成
   （"２４８億円"→"248 oku"、"ｘｘｘ億円"→"xxx oku"）。
   単位側の直前空白regexは現行維持
3. 翻訳済み出力で「億円を含む説明文がそもそも英訳されているか」も
   確認する。されていない場合はセル外テキスト（図形・テキスト
   ボックス）が抽出対象外という別問題であり、需要と併せて別途判断
4. 恒久策: 上記ミニブック（単位付きセル入り）を回帰テスト資材に加え、
   file経路で generated>0・監査 checked>0 を毎回実証する
