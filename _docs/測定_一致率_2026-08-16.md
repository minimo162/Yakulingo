# 測定: 過去訳の一致率が、翻訳者の役に立つ順に並んでいるか（2026-08-16）

結論。**並んでいなかった。** 文字trigramのDice係数は文の長さで答えが変わり、
**16字未満の文は1語違うだけで必ず閾値を割って隠れていた**。編集距離へ替えた。
費用も編集距離のほうが安い（5,000件で 19ms 対 92ms）。

## 何を測ったか

差の種類が分かっている9組を作り、`Get-YakuTranslationMemorySimilarity` に通した。
文は符号位置から組み立て、使う前に印字して中身を確かめてある
（一時ディレクトリの `.ps1` は BOM が付かず日本語が壊れるため）。

| 組 | 差 | Dice（当時） | 編集距離 |
| --- | --- | ---: | ---: |
| 売上高は◯◯億円でした。 | 数値だけ | **0.462** | 0.733 |
| 売上高は◯◯億円で「した／となりました」 | 数値＋語尾 | 0.690 | 0.778 |
| 増収→減収（9字） | 1字 | 0.857 | 0.889 |
| 営業利益は増加→減少（12字） | 2字 | **0.600** | 0.833 |
| 調達→物流コスト（25字） | 2字 | 0.826 | 0.920 |
| 同上（45字） | 2字 | 0.905 | 0.955 |
| 前後の節を入れ替え（18字） | 語順 | 0.750 | 0.444 |
| 末尾に1文追加 | 追加 | 0.793 | 0.641 |
| 無関係 | — | 0.182 | 0.200 |

閾値は `Find-YakuTranslationMemory` の `MinScore = 0.70`。太字は隠れていたもの。

## Dice の並びは、再利用の価値と逆だった

```
0.905  45字 2字違い          使い回せる
0.857   9字 1字違い          使い回せる
0.826  25字 2字違い          使い回せる
0.793  1文まるごと余計   ← 節を消す手間が要る
0.750  節の入れ替え      ← 語順を直す手間が要る
0.690  数値＋語尾            使い回せる   ← 上の2つより下
0.600  12字 2字違い          使い回せる   ← 隠れる
0.462  数値だけ違う          いちばん使い回せる ← 隠れる
```

編集距離では、使い回せる6組が全部 0.733 以上、手間の要る2組が 0.641 と 0.444、
無関係が 0.200。**間に切れ目があり、順序が入れ替わらない。**

## これは9組の選び方に依らない。算数で出る

n文字の文で隣り合う2字を書き換えると、trigram は n-2 個のうち4個が壊れる。

```
Dice = 2 × (n-2-4) / ((n-2) + (n-2)) = 1 - 4/(n-2)

  n=12 → 0.600（実測 0.600）
  n=25 → 0.826（実測 0.826）
  n=45 → 0.907（実測 0.905）
```

0.70 を越えるには **n ≥ 16** が要る。勘定科目名・表の見出し・短い注記は
ほぼ全部この長さの下である。**サンプルの問題ではなく、尺度の性質である。**

**ただし「長さで変わる」こと自体は Dice 固有ではない。** 正規化する尺度はどれも
そうなる。実測した傾きは次のとおり（同じ「1語だけ違う」を12字と25字で出したとき）。

```
              12字     25字    落差
Dice          0.600 → 0.826   0.226   ← 12字で閾値を割る
Smartcat        75% →   92%   0.17    ← 75% は選べる最低の閾値ちょうど
編集距離      0.833 → 0.920   0.087   ← いちばん緩い
```

問題は傾きの急さである。Dice は2字書き換えると trigram を4つ壊すので、
文字の距離の2倍の速さで落ちる。**その結果、短文だけが門の下へ落ちる。**

## 費用（PowerShell 5.1、5,000件を1文に照合、各40字）

```
Add-Type の初回コンパイル              91ms（プロセスにつき1回）
Dice: n-gram 5,000件の構築（初回）    645ms
Dice: 構築済みで照合（定常）           92ms  ← これが実際に出ていた値
編集距離（C# へ落とす）                19ms  ← 準備も作り置きも無しで
編集距離（PowerShell のまま）        4,558ms
```

**遅さの原因は算法ではなく PowerShell のループだった。**
正確なほうが速いので、前段フィルタ（BM25 など）は要らない。
`Get-YakuCorpusBm25Score` に一致率の仕事は無い。

長さの差だけでの足切りも入れた。編集距離は必ず長さの差以上なので、
`1 - |差|/長いほう` が `MinScore` に届かない候補は計算前に落とせる。

## 数値をマスクして照合する案は、採らなかった

`ConvertTo-YakuAlignmentMaskedText`（対訳突合せ用）を通すと
「売上高は〔数〕円でした。」どうしになり、数値だけ違う組が 1.000 になる。
市販CATの placeable に当たる扱いで、決算翻訳では価値が高い。

安全網は測って確認した。古い数字を持ち越した過去訳は、確定時の点検で
**3つの error が出て止まる**（`numeric-integrity` / `numeric-value-mismatch` /
`numeric-value-extra`）。これは書き出しを止める `segment-qc-failed` に当たる。

```
原文 売上高は5,678億円でした。
  訳 Net sales were 1,234 oku yen. → STOPPED  errors=3
  訳 Net sales were 5,678 oku yen. → passes
  訳 Net sales rose.               → STOPPED  errors=3
```

ただしマスクは他の組の値を下げる（数値＋語尾の組が 0.778 → 0.733）。
編集距離だけで9組とも正しく並ぶので、**今回は入れない**。
入れるなら「完全一致として出すのか、印を付けた別の帯にするのか」を
市販ツールで測ってから決める。

## Smartcat を実機で測った（2026-08-16。同じ9組の文で）

案件 `smartcat-fuzzy-test` / `smartcat-fuzzy-test2`（ja→en、TM は同じ
`smartcat-fuzzy-test(ja-en)`）を作り、4文を確定してから残りを見た。
**PowerShell で測ったのと同じ文**なので、点数がそのまま比べられる。

| 差 | Smartcat | 札の色 | 編集距離 | Dice |
| --- | ---: | --- | ---: | ---: |
| 完全一致 | **100%** | 緑 | 1.00 | 1.00 |
| 25字2字違い（調達→物流） | **92%** | 黄 | 0.92 | 0.83 |
| 数値のみ（1,234→5,678） | **90%** | 黄 | 0.73 | 0.46 |
| 25字→いたしました | **89%** | 黄 | — | — |
| 25字に「大幅に」を足す | **86%** | 黄 | — | — |
| 1節追加 | **77%** | 赤 | 0.64 | 0.79 |
| 12字2字違い（増加→減少） | **75%** | 赤 | 0.83 | 0.60 |
| 語順の入れ替え | **候補なし** | — | 0.44 | 0.75 |

### 表示

- **数字の「%」を出す。** 消してはいない
- **札は3色。** 100%=緑（`sc-badge_green`）、86〜92%=黄（`sc-badge_yellow`）、
  75〜77%=赤（`sc-badge_red`）。境目は実測で 78〜85 の間
- 右に **Match difference** を出す。過去訳の原文と今回の原文の差を、
  消えた側と増えた側で色を分けて見せる
- TM名・作成日時・更新日時・著者も出す
- **100% は訳文欄へ自動で入る。ただし確定はされない**（進捗は 0% のまま）

### 閾値

自動挿入の `Minimum match percentage` は既定 **100%**。選べるのは
**75 / 85 / 95 / 99 / 100 / 101** の6つだけで、**75% が最低**である
（101% は文脈一致）。**YakuLingo の `MinScore = 0.70` は、市販ツールが
選択肢として持っていない低さ。**

### 止める線が違う

| | Smartcat | YakuLingo |
| --- | --- | --- |
| タグ欠け | **Critical。確定できない**（"This segment cannot be confirmed yet"） | `structure-integrity` 等で error |
| 数値の不一致 | **黄色い警告。確定できる**＋ IGNORE の箱がある | **error。書き出しを止める** |

実測した文面: "Tag &lt;1&gt; must be present both in source and target"（止まる）、
"Dates and numbers in source and target do not match"（止まらない。行は緑）。

**YakuLingo のほうが数値に厳しい。** これは緩めない（決まりのとおり
「数値が抜けた訳は警告ではなく欠陥」）。ただし**意図した違いだと測って確かめた**
のであって、たまたまではない。

### 並び順の一致・不一致

```
Smartcat  92 > 90 > 89 > 86 > 77 > 75 > （語順は出さない）
編集距離  92 > 83 > 73 > 64 > 44
Dice      83 > 79 > 75 > 60 > 46
```

- **いちばん上（25字1語違い）は 92 で完全に一致する**
- **語順の入れ替えを出さないことも一致する。** Dice だけが 0.750 で出していた
- 食い違うのは中ほど。Smartcat は**数値のみの違いを2番目に置く**（90%）が、
  編集距離は3番目（0.73）。逆に12字1語違いは編集距離が2番目（0.83）、
  Smartcat は下から2番目（75%）
- Smartcat の点数は語（トークン）単位に見える。12字は4語で1語違い＝75%が合う。
  ただし他の組は合わないので、**式は推測しない**

### 副作用: .txt にもタグが付く

プレーンな .txt を入れたのに、Smartcat は日本語の文へ `scTag O-1 / C-1` の
対を入れた（`営業利益 &lt;1&gt;は&lt;/1&gt; 増加 &lt;2&gt;しました。&lt;/2&gt;`）。
訳文側に同じタグを入れないと確定できない（F8 で挿入）。
比べる組どうしはタグ構造が同じなので、上の測定は成立する。

## 副作用: 「%」を消した理由が消えた

2026-08-15 に、あいまい一致から「%」を外した（`dca2558` 周辺、`www/assets/cat.js`）。
理由は **「中身が Dice で、翻訳者が読む 100 / 95-99 / 85-94 / 75-84 / 50-74 の帯は
編集距離を前提にしているから、別の尺度の数字をその帯へ当てはめさせるのは
誤読させるのと同じ」** だった。

いまの実装はその編集距離である。実測でも「増加→減少」だけが違う20字の文が
0.90 を返し、帯のとおり（85-94＝ほぼそのまま使える）になった。**理由が消えた。**

そして市販ツールを実機で見たところ、**Smartcat は数字の「%」を出しており、
選べる閾値も 75 / 85 / 95 / 99 / 100 / 101 と、その帯そのものだった**（上節）。
数字をやめる方向は、市販ツールの水準から遠ざかる側である。

**2026-08-16、利用者判断で「戻す。3色の帯つきで」に決まった。** 実装済み。

```
100%      is-exact  塗りつぶし
85〜99%   is-high   実線の枠
70〜84%   is-low    破線の枠
```

境目の 85 は実測に合わせた（Smartcat は 100=緑 / 86-92=黄 / 75-77=赤で、
境目は 78〜85 の間。設定が刻む 85 を採った）。**色だけに頼らない。**
塗りの形が3種類とも違うので、色が見えなくても3段が見分けられる。

決めたことが2つある。

- **99% で止める。** 0.999 以上を丸めると1文字だけ違う長文が「100%」と出る。
  数字の 100 は「同じ」の意味で読まれるので、完全一致でないものは 99% までにする
- **前回版の候補（`kind='prior'`）には数字を出さない。** そこの `ratio` は
  一致率ではなく 0 が入る。かつては 1% に丸めて描いていたが、1% は「ほぼ別物」と
  読まれる。実際には「前回の同じ場所の訳」であって、原文が変わったかどうかだけが
  問題なので、「原文が同じ」「原文に変更あり」と言葉で出す

### `MinScore` は 0.70 のまま据え置いた

市販ツールが選択肢として持つ最低は 0.75 で、0.70 はそれより低い。しかし
**上げると「数値だけ違う」候補（実測 0.733）が消える。** それは決算翻訳で
いちばん使い回せる型で、Smartcat は 90% と高く置いている。
**上げるのは、いちばん価値のある候補を捨てることになる。**

上げるなら先に、数値を場所取り（placeable）として扱う必要がある。
その場合も 1.000 にはしない（Smartcat は 90% であって完全一致にはしていない）。
**測ってから決める。それまでは 0.70 のまま。**

## 道具のほうを3回疑った（記録）

1. 「数値だけ違うのだから低くてよい」と予想を書いた。**逆だった。**
   事実は違っても訳は使い回せる。決算翻訳でいちばん多い型である
2. 点検の安全網を測ったら3件とも通った。**「数値を丸ごと落とした訳」まで
   通ったのが実装の欠陥ではなく治具の欠陥の合図**で、実際そうだった
3. `Invoke-YakuCatSegmentValidation` は配列ではなく `.Findings` を持つ
   オブジェクトを返す。配列として `@()` で包み、リスト自体を1要素と数えていた
   （`List[object]` の罠）。**緑が出来すぎているときは自分の読み方を疑う**

## 残っている宿題

- **実文書での確認。** 9組は私が作った文である。順序が入れ替わらないことは
  算数で言えるが、「一致率と実際の手直し量が比例するか」は測っていない。
  `_docs/mazda_2025_full_year_results_ja/en_20250512.pdf` を過去訳、
  `_docs/mazda_2027_Q1_kessan_tanshin_20260804.pdf` を今回分として測る
- **語順の入れ替えが 0.444 で隠れる。** Dice では 0.750 で出ていた。
  日本語では節の入れ替えが同じ意味になることがあるので、
  実文書で頻度を見てから判断する
